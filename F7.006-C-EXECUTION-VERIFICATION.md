## Findings

### Existing Resilience Mechanism (E0)
- The codebase already contains a resilience mechanism implemented in `resilienceService.js` and `circuitBreakerService.js`.
- `resilienceService.js` provides an `executeWithResilience` function that supports:
  * Configurable retry attempts (default 3) with exponential backoff.
  * Per-attempt timeout via promise race.
  * Optional fallback function.
  * Integration with a circuit breaker when `circuitBreakerName` is provided.
- `circuitBreakerService.js` provides a circuit breaker class with states (CLOSED, OPEN, HALF-OPEN), failure threshold, cooldown period, and reset capability.
- Breakers are instantiated for 'youcam', 'gemini', 'deepseek'.

### Current Usage (E0)
- **YouCamClient** calls `executeWithResilience` in four places but does **not** pass:
  * `circuitBreakerName` (so circuit breaker is not used).
  * `fallback` option (errors are caught and re-thrown; fallback logic exists internally but not passed through).
- **GeminiClient** calls `executeWithResilience` in two places but does **not** pass:
  * `circuitBreakerName`.
  * `fallback` option (errors are caught and fallback values returned via internal methods, not via the resilience service's fallback option).
- Both clients hardcode resilience options (retry: 3, retryDelay: 100, timeout: this.timeout) directly in each call.

### Gaps Identified (E0)
1. **Circuit breaker not utilized** by external service clients.
2. **Fallback option not utilized**; clients implement fallback separately.
3. **No centralized policy**: resilience parameters (retry, retryDelay, timeout) are duplicated across calls.
4. **No traceId integration** in the resilience service.
5. **No library evaluation**: the mechanism is custom; no assessment of external libraries (e.g., opossum, resilient) has been performed.

### Design Considerations for F7.006-C (based on directive)
Per F7.006-DIRECTIVA.md section 4.1 (F7.006-C — Diseño del wrapper/políticas centralizadas), the objective is to:
- Design a reusable resilience mechanism (either adapting an external library or creating an internal wrapper) that provides:
  * Retry with exponential backoff configurable.
  * Timeout handling per attempt and cumulative.
  * Circuit breaker with states (closed, open, half-open) and configurable thresholds/recovery timeouts.
  * Event logging (attempts, timeouts, failures, circuit breaker openings) compatible with existing logging.
  * Integration with traceId for correlating attempts and failures.
- Define default policies (e.g., 3 attempts with backoff 100ms/200ms/400ms, 5s timeout per attempt, circuit breaker after 5 failures with 30s recovery timeout) as a starting point, subject to validation.

### Proposed Design (E0-based, no implementation)
Based on the inspection, we propose the following design for a centralized resilience wrapper/policies (to be implemented in F7.006-D):

1. **Adopt or enhance the existing `resilienceService.js`** rather than introducing a new external library, to avoid adding dependencies unless evaluation shows clear benefit. The existing service already implements retry, timeout, fallback, and circuit breaker integration. Enhancements needed:
   * Add default policy configuration (export a `defaultPolicy` object or similar).
   * Integrate traceId extraction from middleware (if available) or accept traceId as an option to include in logs.
   * Enhance logging to capture resilience events (attempts, timeouts, failures, circuit breaker state changes) using the existing logger.
   * Ensure the service is fully backward compatible with current callers.

2. **Define a centralized policy module** (e.g., `/backend/src/services/resiliencePolicy.js`) that exports:
   * Default retry count: 3
   * Default retry delay base: 100ms (exponential backoff)
   * Default timeout per attempt: 5000ms (5 seconds) — note: clients currently use 15000ms; this would be a change but aligns with typical external service timeouts.
   * Default circuit breaker failure threshold: 5
   * Default circuit breaker timeout: 30000ms (30 seconds)
   * These values are starting points and should be validated via testing (F7.006-F).

3. **Update external service clients** (YouCamClient, GeminiClient) to:
   * Remove hardcoded resilience options and instead import the default policy (or allow override).
   * Pass a meaningful `circuitBreakerName` (e.g., 'youcam' for YouCamClient, 'gemini' for GeminiClient) to enable circuit breaker protection.
   * Optionally pass a `fallback` function if desired (though clients already have internal fallback; the resilience service's fallback could be used for a more centralized approach).
   * Ensure traceId is propagated (either via middleware or explicitly passed) to the resilience service for logging.

4. **Maintain compatibility**: The enhanced `executeWithResilience` should accept the same options object, with the addition of optional `traceId` and possibly `policy` overrides.

5. **Testing**: Unit tests should be added to validate the behavior under various scenarios (success, retry exhaustion, timeout, circuit breaker opening/half-open/closed transitions) and that logs include traceId when provided.
