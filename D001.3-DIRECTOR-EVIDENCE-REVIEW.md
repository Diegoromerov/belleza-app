# D-001 RECOMMENDED TENANT MODEL

## CURRENT STATE
No existe ninguna entidad explícita que represente un negocio/salón capaz de agrupar múltiples usuarios o profesionales. El modelo actual asume una equivalencia entre usuario con rol PRESTADOR y salón/profesional independiente (uno-a-uno entre usuario y perfil de prestador).

## RECOMMENDATION
TENANT debe representar el negocio/salon que contrata el servicio de GlowApp. Se requiere introducir una nueva entidad tenants (o salones) con al menos: id, nombre, dirección, información de contacto.

## EVIDENCIA
D001.1-TENANT-DOMAIN-MODEL.md líneas 139-141: "TENANT debe representar el negocio/salon que contrata el servicio de GlowApp. Se requiere introducir una nueva entidad tenants (o salones) con al menos: id, nombre, dirección, información de contacto."

## CONSECUENCIA
Se requiere introducir una entidad explícita tenant para soportar múltiples usuarios y profesionales por salón, rompiendo la equivalencia actual uno-a-uno entre usuario y salón.

# D-001 RECOMMENDED SECURITY MODEL

## CURRENT STATE
Modelo actual: USER (autenticado) → AUTORIZACIÓN (por rol y ownership explícito) → RECURSO. No existe una capa explícita de TENANT MEMBERSHIP.

## RECOMMENDATION
Modelo requerido para multi-tenancy: USER → AUTENTICACIÓN → MEMBRESÍA EN TENANT → AUTORIZACIÓN (rol y ownership dentro del tenant) → RECURSO (con filtrado por tenant). Además, se puede añadir RLS como última barrera en la base de datos.

## EVIDENCIA
D001.1-DECISION-GATE.md líneas 120-122: "Modelo actual: USER (autenticado) → AUTORIZACIÓN (por rol y ownership explícito) → RECURSO. No existe una capa explícita de TENANT MEMBERSHIP."
D001.1-DECISION-GATE.md líneas 123-125: "Modelo requerido para multi-tenancy: USER → AUTENTICACIÓN → MEMBRESÍA EN TENANT → AUTORIZACIÓN (rol y ownership dentro del tenant) → RECURSO (con filtrado por tenant). Además, se puede añadir RLS como última barrera en la base de datos."

## CONSECUENCIA
Se requiere implementar capacidades de membresía en tenant (por ejemplo, mediante columna tenant_id en usuarios o tabla de asociación) y establecer el filtrado por tenant en todas las consultas de aplicación, con RLS como barrera de defensa en profundidad.

# D-001 RECOMMENDED DATABASE MODEL

## CURRENT STATE
Shared schema sin particionamiento. No existen columnas tenant_id ni tablas de tenants. Todas las tablas están en el esquema público sin aislamiento lógico por tenant.

## RECOMMENDATION
Shared Schema + tenant_id + RLS. Añadir columna tenant_id a las tablas relevantes de negocio, habilitar Row Level Security en PostgreSQL y crear políticas que enforquen el aislamiento a nivel de fila basado en el contexto de tenant.

## EVIDENCIA
D001.1-DECISION-GATE.md líneas 198-200 y 202-204 describen la recomendación de arquitectura.
D001.1-RLS-FEASIBILITY.md líneas 78-88: "RLS es técnicamente factible con el stack actual (PostgreSQL 15+, Sequelize, pgPool, Redis)."
D001.1-RLS-FEASIBILITY.md líneas 80-83 lista los requisitos para implementar RLS.

## CONSECUENCIA
Se requerirá modificar el esquema de base de datos para añadir tenant_id a las tablas de negocio, crear una tabla de tenants, poblar tenant_id para datos existentes, habilitar RLS y crear políticas de aislamiento. Todas las consultas de aplicación deberán ejecutarse dentro de un contexto que establezca el tenant_id.

# D-001 RECOMMENDED USER MODEL

## CURRENT STATE
La tabla usuarios almacena tanto clientes como profesionales, diferenciados por el campo rol ('CLIENTE' o 'PRESTADOR'). No hay indicación de pertenencia a una entidad de negocio superior. Cada usuario tiene como máximo un perfil de prestador (relación uno-a-uno).

## RECOMMENDATION
Cada usuario pertenece a exactamente un tenant (muchos usuarios por tenant, pero cada usuario en un solo tenant). Esto requiere añadir una columna tenant_id a la tabla usuarios o crear una tabla de asociación usuario-tenant.

## EVIDENCIA
D001.1-TENANT-DOMAIN-MODEL.md líneas 153-154: "se puede comenzar modelando que cada usuario pertenece a un solo tenant (muchos usuarios por tenant, pero cada usuario en un solo tenant)"

## CONSECUENCIA
Se requerirá modificar la tabla usuarios para añadir tenant_id (o crear tabla de asociación) y poblar este campo para todos los usuarios existentes, estableciendo la relación de pertenencia entre usuarios y tenants.

# D-001 RECOMMENDED PROFESSIONAL MODEL

## CURRENT STATE
La tabla perfiles_prestador está en relación uno-a-uno con usuarios (id como PK y FK a usuarios.id). Esto implica que cada usuario puede tener como máximo un perfil de prestador y cada perfil de prestador pertenece a exactamente un usuario.

## RECOMMENDATION
Dependerá de la decisión específica de modelado:
Opción 1 (profesional como entidad independiente): El profesional (perfiles_prestador) pertenece al tenant mediante una relación muchos-a-uno (un tenant puede tener muchos profesionales).
Opción 2 (profesional como usuario): El profesional es un usuario que pertenece al tenant (relación muchos-a-uno desde usuarios a tenant).

## EVIDENCIA
D001.1-TENANT-DOMAIN-MODEL.md líneas 150-151: "Alternativamente, se puede desacoplar perfiles_prestador de usuarios y vincularlo directamente al tenant, permitiendo que un tenant tenga múltiples profesionales"
D001.1-TENANT-DOMAIN-MODEL.md líneas 152-156: describe la aproximación inicial donde cada profesional es un usuario y por lo tanto pertenece al tenant de su usuario.

## CONSECUENCIA
Se requerirá decidir si mantener o romper la relación uno-a-uno entre usuarios y perfiles_prestador. Si se rompe, se necesitará añadir tenant_id a perfiles_prestador y posiblemente eliminar la restricción de clave foránea a usuarios. Si se mantiene, se necesitará añadir tenant_id a usuarios y derivar la tenencia del profesional a través de su usuario.

# 11. RLS
¿SE RECOMIENDA RLS?
SÍ
¿POR QUÉ?
Equilibrio entre simplicidad, seguridad y costo; la base de datos enforca el filtrado reduciendo riesgo de error de aplicación.
¿CUÁL ES EL PRINCIPAL RIESGO?
Fuga de contexto en el pool de conexiones si se usan variables de sesión sin reset
¿QUÉ CONDICIONES DEBEN CUMPLIRSE?
1. Añadir columna tenant_id a las tablas relevantes
2. Habilitar RLS y crear políticas
3. Implementar mecanismo para establecer contexto de tenant por transacción (preferiblemente SET LOCAL)
4. Asegurar que todas las consultas se ejecuten dentro de ese contexto
EVIDENCIA: D001.1-RLS-FEASIBILITY.md líneas 78-88 y 80-83; D001.1-CONNECTION-CONTEXT-ANALYSIS.md líneas 94-96.

# 12. CONNECTION CONTEXT
¿Existe riesgo de contaminación de contexto entre requests?
SÍ, si se usan variables de sesión sin reset
pgPool: El pool reutiliza conexiones entre requests; si se usa SET sin reset hay riesgo de herencia de tenant entre requests; con SET LOCAL en transacciones el riesgo se minimiza porque el contexto no persiste más allá de la transacción.
Sequelize: Similar riesgo al de pgPool si el contexto se establece a nivel de conexión; puede funcionar si el contexto de tenant se establece en la conexión/transacción; se puede usar namespace de CLS o pasar explícitamente el objeto de transacción.
transactions: Se recomienda usar SET LOCAL app.tenant_id = ... (nivel de transacción) para que el contexto se revierta automáticamente al final de la transacción.
EVIDENCIA: D001.1-CONNECTION-CONTEXT-ANALYSIS.md líneas 93-96 y 98-102; D001.1-RLS-FEASIBILITY.md líneas 98-103.

# 16. RECOMMENDATION
RECOMMENDED:
Shared Schema + tenant_id + RLS (Opción B)
BECAUSE:
Equilibrio entre simplicidad, seguridad y costo; la base de datos enforca el filtrado reduciendo riesgo de error de aplicación.
MAIN RISK:
Fuga de contexto en el pool de conexiones si no se usa mecanismo transaccional adecuado para establecer el contexto de tenant.
MITIGATION:
Usar SET LOCAL app.tenant_id = ... (ámbito de transacción) al inicio de cada transacción que acceda a la base de datos, asegurando que el contexto se revierta automáticamente.
EVIDENCIA: D001.1-DECISION-GATE.md líneas 198-200 y 202-204; D001.1-RLS-FEASIBILITY.md línea 86 y D001.1-CONNECTION-CONTEXT-ANALYSIS.md líneas 94-96; D001.1-DECISION-GATE.md líneas 162-164.
