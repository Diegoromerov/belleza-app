# D002.1-DATA-MODEL.md

## Conceptual Data Model for Workforce Management (D-002)

**Note**: This is a conceptual model only. No implementation is authorized at this stage.

### Goals
- Allow salons to classify workforce members operationally as `EMPLEADO` or `PRESTADOR_SERVICIO` (or other salon-defined categories).
- Ensure that this classification is strictly operational and does not imply any legal relationship with GlowApp.
- Leverage existing D-001 multi-tenancy (Shared Schema + tenant_id + RLS) for data isolation.
- Minimize changes to existing schema and preserve backward compatibility.

### Existing Relevant Tables
1. `usuarios` (id, email, nombre, rol [tipo_rol: CLIENTE or PRESTADOR], tenant_id, ...)
2. `perfiles_prestador` (id PK -> usuarios.id, business_name, descripción, ubicación, etc.)
3. `tenants` (id, name, slug, ...)

### Proposed Changes

#### 1. Add a new ENUM for operational worker type
```sql
CREATE TYPE tipo_trabajador AS ENUM (
    'EMPLEADO',
    'PRESTADOR_SERVICIO',
    'ADMIN_SALON',
    'OTRO'
);
```

#### 2. Add a column to `usuarios` to store the operational classification
```sql
ALTER TABLE usuarios ADD COLUMN worker_type tipo_trabajador;
```

**Rationale**: 
- The `usuarios` table already has `tenant_id` (from D-001) linking each user to a salon.
- Adding `worker_type` here allows any user (whether they are a client, prestador, or salon admin) to be classified operationally by the salon.
- The column is nullable to allow for gradual adoption and to preserve existing data where the classification is not yet defined.

#### 3. Optional: Add a column to `perfiles_prestador` if the classification is only relevant for prestadores
*Alternative approach*: If we decide that the operational classification only applies to users that are prestadores (i.e., service providers), we could add the column to `perfiles_prestador` instead. However, placing it on `usuarios` is more flexible because it allows classifying salon administrators or other users that may not have a prestador profile.

For this specification, we recommend the `usuarios` approach.

### Handling Existing Data
- For existing users with `rol = PRESTADOR`, set `worker_type = 'PRESTADOR_SERVICIO'` (or leave null and let the salon set it).
- For existing users with `rol = CLIENTE`, set `worker_type = NULL` (or optionally 'OTRO' if the salon wants to classify clients in some way, though clients are not typically part of the workforce).
- The salon can later update the `worker_type` for any user as needed.

### Indexing
- No additional index is strictly required for the `worker_type` column alone, but if queries filter by `worker_type` and `tenant_id`, a composite index on `(tenant_id, worker_type)` could be beneficial.
- However, given the likely low cardinality of `worker_type`, separate indexes may suffice. This is left to implementation tuning.

### RLS Considerations
- If the `worker_type` column is considered sensitive (e.g., reveals labor classification), then Row-Level Security policies should be applied to the `usuarios` table (if they are not already) to ensure that users can only see workforce members from their own tenant.
- Since D-001 already mandates `tenant_id` on core tables and RLS policies, we assume that the `usuarios` table is already covered by RLS (or will be). The addition of `worker_type` does not change the RLS requirement; it merely adds a column that must be included in the existing policies.

### Example Queries (Conceptual)
```sql
-- Get all workforce members for a tenant, with their operational type
SELECT u.id, u.email, u.nombre, u.worker_type
FROM usuarios u
WHERE u.tenant_id = :tenant_id;

-- Count employees vs service providers for a tenant
SELECT u.worker_type, COUNT(*)
FROM usuarios u
WHERE u.tenant_id = :tenant_id
GROUP BY u.worker_type;
```

### Impact on Other Tables
- No changes are required to `perfiles_prestador`, `services`, `bookings`, etc., unless the salon wishes to use the `worker_type` for filtering (e.g., only allow SERVICE_PROVIDER to be assigned to services). That would be an application-level decision and does not require schema changes.

### Summary
- **Added**: `tipo_trabajador` ENUM and `usuarios.worker_type` column.
- **Preserved**: All existing tables, columns, and relationships.
- **Leveraged**: Existing `tenant_id` and D-001 multi-tenancy foundation.
- **Compliance**: The model strictly separates operational classification (salon's internal use) from any legal interpretation.
