# TENANT DOMAIN MODEL ANALYSIS FOR GLOWAPP

## 1. CURRENT STATE (EVIDENCE FROM CODEBASE)

### 1.1. Tabla `usuarios` (backend/schema.sql, líneas 43-59)
- Almacena tanto clientes como profesionales.
- Campo `rol` distingue entre 'CLIENTE' y 'PRESTADOR'.
- No hay indicación de pertenencia a una entidad de negocio superior.

### 1.2. Tabla `perfiles_prestador` (backend/schema.sql, líneas 62-80)
- Uno-a-uno con `usuarios` (id como PK y FK a usuarios.id).
- Campos como `business_name`, `descripcion`, `ubicacion` sugieren que representa un profesional o un salón.
- **Evidencia de relación uno-a-uno**:  
  `id INTEGER PRIMARY KEY REFERENCES usuarios(id) ON DELETE CASCADE`  
  Esto implica que cada usuario puede tener como máximo un perfil de prestador, y cada perfil de prestador pertenece a exactamente un usuario.

### 1.3. Otras tablas relevantes
- `services.provider_id` referencia `perfiles_prestador.id` (línea 88).
- `bookings.client_id` referencia `usuarios.id` (línea 101).
- `bookings.provider_id` referencia `perfiles_prestador.id` (línea 102).
- No hay tablas que representen un negocio o salón capaz de agrupar múltiples usuarios o profesionales.

### 1.4. Conclusión sobre el estado actual
**NO EXISTE** una entidad explícita que represente un negocio/salón capaz de tener múltiples usuarios o múltiples profesionales.  
El modelo actual asume que:
- Cada usuario con rol `PRESTADOR` es equivalente a un salón/profesional independiente (uno-a-uno entre usuario y perfil de prestador).
- No hay forma de representar un salón con varios profesionales (pues cada profesional requeriría su propia cuenta de usuario).
- No hay forma de representar un salón con varios usuarios no profesionales (dueño, administrador, etc.) que no tengan rol de prestador.

## 2. HIPÓTESIS DE TRABAJO DEL DIRECTOR
El Director plantea como hipótesis:  
`TENANT = NEGOCIO / SALÓN CONTRATANTE`  
Esta hipótesis **debe validarse contra el código existente**.

### 2.1. Validación de la hipótesis
Dado el estado actual del código:
- No hay tabla `tenants`, `salones`, `businesses`, `organizations`.
- No hay columnas como `tenant_id`, `business_id`, `salon_id` en ninguna tabla.
- La relación entre usuario y perfil de prestador es uno-a-uno, lo que sugiere que actualmente el sistema no está diseñado para soportar un salón con múltiples profesionales o múltiples usuarios.

**Conclusión**: La hipótesis `TENANT = NEGOCIO / SALÓN CONTRATANTE` **no está respaldada por el código actual** porque no existe ninguna entidad que pueda agrupar múltiples usuarios o profesionales bajo un mismo negocio.  
Sin embargo, el concepto de `business_name` en `perfiles_prestador` indica que el modelo aspira a representar un negocio, pero está limitado a una relación uno-a-uno con un usuario.

## 3. MODELO CONCEPTUAL PROPUESTO PARA TENANT

Para soportar un verdadero multi-tenancy donde un salón (negocio) pueda tener múltiples usuarios y múltiples profesionales, se requiere introducir una nueva entidad `tenants` (o `salones`) con las siguientes características:

### 3.1. Entidad `tenants`
- Representa el negocio/salon que contrata el servicio de GlowApp.
- Atributos mínimos: `id`, `nombre`, `dirección`, `información de contacto`, `fecha de creación`, `estado activo`.
- Relaciones:
  - Un tenant tiene muchos usuarios (dueños, administradores, staff).
  - Un tenant tiene muchos profesionales (si el profesional es distinto del usuario).
  - Un tenant tiene muchos servicios.
  - Un tenant tiene muchas reservas.
  - Un tenant tiene muchos pagos/transacciones.
  - Un tenant tiene su propia configuración (sobrescribiendo platform_config si es necesario).

### 3.2. Relaciones conceptualmente requeridas
```
TENANT
   │
   ├── usuarios (varios roles: owner, admin, staff, etc.)
   │
   ├── profesionales (perfiles_prestador, si se separa del usuario)
   │
   ├── clientes
   │
   ├── servicios
   │
   ├── reservas
   │
   ├── pagos/transacciones
   │
   └── configuración (específica del tenant)
```

### 3.3. Compatibilidad con el modelo actual
- El modelo actual puede verse como un caso especial donde cada tenant tiene exactamente un usuario (con rol PRESTADOR) y exactamente un perfil de prestador.
- Para migrar, se podría crear un tenant por cada usuario actual que tenga rol PRESTADOR, y asignar ese tenant_id al usuario y al perfil de prestador.

## 4. ANÁLISIS DE ESCENARIOS (User vs Tenant)

### Escenario A: Un salón tiene un único usuario.
- **CURRENT STATE**: SOPORTADO (implícitamente).  
  Cada usuario PRESTADOR con su perfil de prestador representa un salón con un solo usuario/profesional.
- **PROPOSED MODEL**: Soportado. El tenant tendría un único usuario (tal vez con rol OWNER o ADMIN).

### Escenario B: Un salón tiene varios usuarios.
- **CURRENT STATE**: NO SOPORTADO.  
  No hay forma de asociar múltiples usuarios a un mismo salón porque cada usuario es independiente y no hay entidad de salón que los agrupe.
- **PROPOSED MODEL**: SOPORTADO. Se crea un tenant y se le asocian múltiples usuarios (con roles adecuados).

### Escenario C: Un profesional trabaja para un salón.
- **CURRENT STATE**: NO SOPORTADO (tal como está modelado actualmente).  
  Dado que `perfiles_prestador` está fuertemente acoplado a `usuarios` (uno-a-uno), un profesional no puede pertenecer a un salón sin ser el usuario dueño de ese salón.  
  Si se quiere modelar un profesional que trabaja para un salón (pero no es el dueño), se requeriría desacoplar `perfiles_prestador` de `usuarios` o crear una relación muchos-a-uno entre profesionales y tenants.
- **PROPOSED MODEL**: SOPORTADO si se modela `profesional` como entidad independiente vinculada a `tenant`.  
  Alternativamente, si se mantiene que el profesional es un usuario, entonces el usuario pertenecería al tenant y tendría rol PROFESSIONAL o similar.

### Escenario D: Un usuario pertenece a varios contextos.
- **CURRENT STATE**: NO SOPORTADO.  
  Un usuario tiene exactamente un rol y (si es PRESTADOR) exactamente un perfil de prestador. No hay forma de que un usuario pertenezca a múltiples salones.
- **PROPOSED MODEL**: Depende de las reglas de negocio.  
  Si se permite que un usuario trabaje para múltiples salones, entonces se necesitaría una relación muchos-a-uno entre usuarios y tenants (o una tabla de asociación).  
  Si se restre que un usuario pertenece a un solo salón, entonces es uno-a-uno o muchos-a-uno (muchos usuarios por tenant, pero cada usuario en un solo tenant).

### Escenario E: Un profesional puede pertenecer a más de un salón.
- **CURRENT STATE**: NO SOPORTADO (por la misma razón que el escenario C).  
  Un perfil de prestador está ligado a un único usuario, y ese usuario no puede estar asociado a múltiples salones en el modelo actual.
- **PROPOSED MODEL**: SOPORTADO si se modela al profesional como entidad independiente con relación muchos-a-uno a tenants (un profesional puede trabajar en múltiples salones).  
  Si se mantiene que el profesional es un usuario, entonces se necesitaría que el usuario pudiera pertenecer a múltiples tenants (relación muchos-a-uno inversa o muchos-a- muchos).

## 5. CONCLUSIONES SOBRE LA ENTIDAD TENANT

Basado en la evidencia del código existente:
- **No existe actualmente ninguna entidad que represente un negocio/salón capaz de agrupar múltiples usuarios o profesionales.**
- El modelo actual asume una equivalencia entre `usuario con rol PRESTADOR` y `salon/profesional independiente`.
- Para soportar el modelo de SaaS multi-tenant donde un salón puede tener múltiples usuarios (dueño, admin, staff) y múltiples profesionales, se requiere introducir una nueva entidad `tenant` (o `salon`) y establecer las relaciones apropiadas.
- La hipótesis del Director (`TENANT = NEGOCIO / SALÓN CONTRATANTE`) es **conceptualmente válida** para el futuro del producto, pero **no está implementada ni respaldada por el esquema actual**. Requiere cambios en el modelo de datos.
