# D001.11-EXECUTION-SEQUENCE.md

## Execution Sequences for D-001 Migration Repairs

This document outlines the exact sequence of steps to execute the repaired migrations on both a clean database and the current GlowApp database, including preconditions, actions, validations, and postconditions for each step.

---

### EXISTING DATABASE SEQUENCE

**Starting point**: Current state of GlowApp database as verified in D-001.7 through D-001.10.

#### Step 1: 055 NO-OP / VALIDATION
- **Precondition**: None.
- **Action**: Run migration 055 (as-is, it is idempotent).
- **Validation**: 
  - Confirm `tenants` table exists.
  - Confirm there is a row with `id=1`, `name='Default Tenant'`, `slug='default'`.
- **Postcondition**: Tenants table ready with default tenant.
- **Rollback / Recovery**: Not applicable in this phase; if needed, drop tenants table (only if no dependent data).

#### Step 2: 056-R RECONCILIATION (Add tenant_id column where missing)
- **Precondition**: Tenants table exists (from step 1).
- **Action**: Run repaired migration 056-R (as specified in D001.11-MIGRATION-REPAIR-PLAN.md).
- **Validation**: 
  - For each table in the list (usuarios, servicios, bookings, transactions, reviews, portfolio_items, messages, nail_tryon_jobs, sos_alerts, user_activity_logs, perfiles_prestador):
    - If table exists, verify column `tenant_id` exists (nullable).
    - If table does not exist, no action required (skip).
- **Postcondition**: All existing core tables have the `tenant_id` column (nullable). Tables that do not exist remain unchanged.
- **Rollback / Recovery**: For each table where we added the column, drop the `tenant_id` column (if safe and no dependent data).

#### Step 3: VALIDATION AFTER 056-R
- **Precondition**: 056-R completed.
- **Action**: Run validation checks (can be part of migration or separate script).
- **Validation**: 
  - Confirm that for every existing core table from the 056 list, the `tenant_id` column exists.
  - Confirm that no errors occurred during migration.
- **Postcondition**: Ready for backfill.
- **Rollback / Recovery**: None needed beyond step 2 rollback.

#### Step 4: 057-R BACKFILL (Populate tenant_id, add optional columns, create indexes)
- **Precondition**: 056-R validated (core tables have column).
- **Action**: Run repaired migration 057-R.
- **Validation**:
  - Demo tenant: Confirm a row exists in `tenants` with `slug='demo'`.
  - Core tables: For each existing core table, confirm that `tenant_id` is NOT NULL for all rows (or at least no NULLs where data exists; if table is empty, it's fine).
  - Optional tables: 
    - If table exists, confirm `tenant_id` column exists.
    - For platform_config, admin_mfa, productos: confirm `tenant_id` is NOT NULL where data exists (or no NULLs if data exists).
    - For beauty_knowledge_embeddings: confirm column exists and `tenant_id` is NULL (or no rows).
  - Indexes: Confirm indexes exist on `tenant_id` for each table that exists.
- **Postcondition**: Tenant IDs populated, optional columns added, indexes created.
- **Rollback / Recovery**: 
  - Set `tenant_id` back to NULL in all tables where we updated it (we know we set it to demo tenant ID).
  - Drop optional columns we added (if we want to remove them entirely).
  - Drop indexes we created.

#### Step 5: VALIDATION AFTER 057-R
- **Precondition**: 057-R completed.
- **Action**: Run validation checks.
- **Validation**: Same as step 4 validation.
- **Postcondition**: Ready for RLS enabling.
- **Rollback / Recovery**: None beyond step 4 rollback.

#### Step 6: 058-R RLS ENABLEMENT AND POLICIES
- **Precondition**: 057-R validated (tenant_id column exists and populated where appropriate).
- **Action**: Run repaired migration 058-R.
- **Validation**:
  - For each table in the RLS list (usuarios, perfiles_prestador, servicios, bookings, transactions, reviews, portfolio_items, messages, nail_tryon_jobs, sos_alerts, user_activity_logs, platform_config, admin_mfa, productos):
    - If table exists, confirm RLS is enabled (check `pg_class.relrowsecurity = true`).
    - Confirm policy `tenant_isolation_<table>` exists and uses `USING (tenant_id = current_setting('app.tenant_id')::int)`.
  - Confirm beauty_knowledge_embeddings does NOT have RLS enabled (and no tenant_isolation policy).
- **Postcondition**: RLS enabled and policies in place for tenant isolation.
- **Rollback / Recovery**: 
  - For each table where we enabled RLS, disable RLS (`ALTER TABLE ... DISABLE ROW LEVEL SECURITY;`).
  - Drop the policies we created.

#### Step 7: FINAL VALIDATION
- **Precondition**: 058-R completed.
- **Action**: Run final validation.
- **Validation**: 
  - Confirm RLS is enabled and correct policies are in place (as in step 6).
  - Confirm application compatibility: check that `src/middleware/tenantContext.js` sets `app.tenant_id` (code inspection, not execution).
  - Confirm no unintended side effects.
- **Postcondition**: D-001 multi-tenancy implementation is active.
- **Rollback / Recovery**: Full rollback as per steps 6, 4, 2 if needed.

---

### CLEAN DATABASE SEQUENCE

**Starting point**: Database with schema loaded (from `schema.sql`) but no D-001 migrations run.

#### Step 1: 055 (idempotent)
- **Action**: Run 055.
- **Validation**: Tenants table exists with default tenant.
- **Postcondition**: Tenants table ready.

#### Step 2: 056-R
- **Action**: Run 056-R.
- **Validation**: All core tables (that exist from schema) have `tenant_id` column.
- **Postcondition**: Column added where needed.

#### Step 3: 057-R
- **Action**: Run 057-R.
- **Validation**: 
  - Demo tenant exists.
  - Core tables have `tenant_id` populated (since they were NULL, now set to demo).
  - Optional tables that exist have column and populated (except beauty_knowledge_embeddings left NULL).
  - Indexes created.
- **Postcondition**: Backfill and indexes done.

#### Step 4: 058-R
- **Action**: Run 058-R.
- **Validation**: RLS enabled and policies created for all tables that exist (except beauty_knowledge_embeddings).
- **Postcondition**: D-001 active.

#### Step 5: FINAL VALIDATION
- Same as existing database final validation.

---

Note: All steps are designed to be idempotent and safe for re‑execution. Validation steps can be integrated into the migrations or run as separate verification scripts.
