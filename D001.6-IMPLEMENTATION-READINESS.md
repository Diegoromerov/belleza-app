# FORMAL ARCHITECTURAL CLOSURE & IMPLEMENTATION READINESS

## 1. DECISIONES FORMALES D-001

### D-001-TENANT
```text
APPROVED

TENANT = SALÓN / NEGOCIO CONTRATANTE
```
GlowApp será un SaaS multi-tenant donde cada salón/negocio contratante constituye un tenant independiente.

### D-001-ARCHITECTURE
```text
APPROVED

Shared Schema + tenant_id + RLS
```
La arquitectura multi-tenant aprobada es:
```text
UNA BASE DE DATOS
      ↓
SCHEMA COMPARTIDO
      ↓
TENANTS
      ↓
tenant_id
      ↓
RLS
```
No utilizar:
```text
Schema per Tenant
Database per Tenant
```
para la arquitectura inicial.

### D-001-RLS
```text
APPROVED

RLS = YES
```
RLS será una segunda barrera de aislamiento después de la autorización de aplicación.
La implementación deberá utilizar contexto transaccional seguro.
La evidencia D-001.5 identifica específicamente `SET LOCAL` como mecanismo necesario para evitar contaminación del contexto del pool.

### D-001-CLIENT
```text
APPROVED

CLIENT → TENANT
```
El cliente pertenece directamente al tenant.
El modelo aprobado conceptualmente es:
```text
TENANT
   │
   ├── CLIENT
   ├── CLIENT
   └── CLIENT
```
El cliente deberá tener una relación directa con el tenant.
No implementar todavía.

### D-001-BRANCH
```text
DEFERRED
```
No implementar branches/sedes como parte de D-001.
Debe conservarse la posibilidad de incorporar posteriormente:
```text
branch_id
```
sin romper el modelo tenant.

### D-001-PROFESSIONAL
```text
PENDING DOMAIN DECISION
```
La decisión sobre Professional queda pendiente.
No se autoriza seleccionar entre:
```text
Professional = User
```
y:
```text
Professional = Independent Entity
```
hasta que exista una decisión específica.
Sin embargo:
```text
D-001 MULTI-TENANCY
= APPROVED
```
No bloquear la arquitectura general por esta decisión.

### 7.1 DATABASE
- **CURRENT STATE:** Shared schema sin tenant_id, tabla tenants inexistente
- **REQUIRED CHANGE:** Añadir tabla tenants, añadir columna tenant_id a tablas de negocio (usuarios, servicios, bookings, transactions, etc.)
- **DEPENDENCY:** Ninguna externa
- **RISK:** Riesgo de inconsistencia durante backfill si se asignan incorrectamente los tenant_id

### 7.2 USERS
- **CURRENT STATE:** Tabla usuarios almacena clientes y profesionales, sin indicación de tenant
- **REQUIRED CHANGE:** Añadir columna tenant_id (o tabla de asociación) para establecer pertenencia a tenant
- **DEPENDENCY:** Tabla tenants
- **RISK:** Asignación incorrecta de usuarios a tenants durante migración

### 7.3 CLIENTS
- **CURRENT STATE:** Los clientes están en tabla usuarios sin tenant_id
- **REQUIRED CHANGE:** Añadir tenant_id directo a usuarios (ya que clientes son usuarios con rol CLIENTE)
- **DEPENDENCY:** Tabla tenants
- **RISK:** Bajo (ya que clientes deben pertenecer al mismo tenant que su usuario asociado)

### 7.4 PROFESSIONALS
- **CURRENT STATE:** Tabla perfiles_prestador en relación uno-a-uno con usuarios
- **REQUIRED CHANGE:** Dependerá de decisión de dominio: ya sea añadir tenant_id directo (si entidad independiente) o derivar vía usuario
- **DEPENDENCY:** Tabla tenants y decisión de modelo professional
- **RISK:** Medio (depende de decisión pendiente)

### 7.5 SERVICES
- **CURRENT STATE:** Tabla services con provider_id referencia perfiles_prestador
- **REQUIRED CHANGE:** Añadir columna tenant_id
- **DEPENDENCY:** Tabla tenants y profesional-tenant relationship
- **RISK:** Bajo si professional-tenant relationship está definida

### 7.6 BOOKINGS
- **CURRENT STATE:** Tabla bookings con provider_id y client_id
- **REQUIRED CHANGE:** Añadir columna tenant_id
- **DEPENDENCY:** Tabla tenants y relaciones professional-client
- **RISK:** Bajo si las relaciones están definidas

### 7.7 TRANSACTIONS/PAYMENTS
- **CURRENT STATE:** Tabla transactions asociada a bookings
- **REQUIRED CHANGE:** Añadir columna tenant_id
- **DEPENDENCY:** Tabla tenants y relación bookings
- **RISK:** Bajo

### 7.8 AUTHORIZATION
- **CURRENT STATE:** Middleware auth.js verifica rol y ownership explícito (user.id)
- **REQUIRED CHANGE:** Actualizar para incluir verificación de membresía en tenant (user.tenant_id = resource.tenant_id)
- **DEPENDENCY:** Implementación de tenant_id en usuarios y recursos
- **RISK:** Medio (olvidar verificar tenant_id podría causar accesos no autorizados)

### 7.9 API
- **CURRENT STATE:** Endpoints ejecutan consultas sin contexto de tenant
- **REQUIRED CHANGE:** Añadir middleware o wrapper que establezca contexto de tenant al inicio de cada request
- **DEPENDENCY:** Mecanismo de contexto de tenant (SET LOCAL)
- **RISK:** Alto si el contexto no se establece correctamente (fuga de contexto)

### 7.10 SEQUELIZE
- **CURRENT STATE:** ORM usado para modelos y consultas
- **REQUIRED CHANGE:** Configurar para pasar tenant_id en contexto de transacción o usar CLS
- **DEPENDENCY:** Mecanismo de contexto de tenant
- **RISK:** Medio (riesgo de fuga de contexto si no se maneja correctamente)

### 7.11 RAW SQL
- **CURRENT STATE:** Consultas directas con pgPool (ej. pool.query en controllers)
- **REQUIRED CHANGE:** Añadir SET LOCAL app.tenant_id = ... al inicio de transacciones
- **DEPENDENCY:** Mecanismo de contexto de tenant
- **RISK:** Alto (fuga de contexto en pool si se usa SET sin reset)

### 7.12 RLS
- **CURRENT STATE:** RLS no habilitado, sin políticas
- **REQUIRED CHANGE:** Habilitar RLS y crear políticas para cada tabla de negocio
- **DEPENDENCY:** tenant_id poblado correctamente
- **RISK:** Bajo si políticas están bien definidas

### 7.13 TESTING
- **CURRENT STATE:** Tests existentes no consideran multi-tenancy
- **REQUIRED CHANGE:** Añadir pruebas de aislamiento entre tenants, incluyendo intentos de acceso cross-tenant
- **DEPENDENCY:** Implementación completa de multi-tenancy
- **RISK:** Bajo (mejora la calidad)

### 7.14 MIGRATION
- **CURRENT STATE:** Ninguna estrategia de migración definida
- **REQUIRED CHANGE:** Definir y ejecutar estrategia para poblar tenant_id en datos existentes
- **DEPENDENCY:** Decisiones de modelo (professional, etc.)
- **RISK:** Alto (pérdida de datos o inconsistencia si falla)
