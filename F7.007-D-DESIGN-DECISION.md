# F7.007-D — Design / Decision Preparation

## Objective
Prepare detailed design decisions and implementation plan for addressing the gaps identified in F7.007-B and evaluated in F7.007-C for F7.007 (Consolidación de la Resiliencia y Preparación para la Producción). This includes:
- Defining how to add `fallback` and `traceId` options to YouCam and Gemini client calls.
- Deciding on timeout alignment strategy.
- Specifying fixes for frontend compilation errors.
- Creating an implementation plan with clear activities, dependencies, and effort estimates.

## Design Decisions

### 1. Fallback Integration
#### YouCam Client
- **Decision**: Implement fallback functions for each of the four steps in `analyzeFace` that return a sensible default score set, rather than propagating the error. This ensures that the biometric flow can continue even if YouCam fails, providing a graceful degradation.
- **Rationale**: 
  - The product prefers to continue with approximate data rather than fail the entire biometric analysis.
  - Default scores are based on typical values observed in historical data (or mid-range values).
  - Error will still be logged for monitoring.
- **Fallback Functions to Create**:
  - `_requestUploadSlotFallback`: returns a mock `fileId`, `uploadUrl`, and `uploadHeaders`.
  - `_uploadToS3Fallback`: does nothing (resolves immediately).
  - `_createAnalysisTaskFallback`: returns a mock `taskId`.
  - `_pollTaskResultFallback`: returns mock analysis results.
- **Implementation**: Each step's `executeWithResilience` call will include a `fallback` option pointing to the respective fallback function.

#### Gemini Client
- **Decision**: Use existing fallback functions (`getFallbackHandsDiagnosis` and `getFallbackRecommendation`) by passing them as the `fallback` option in the respective `executeWithResilience` calls.
- **Rationale**: The fallback functions already exist and return appropriate default values.
- **Implementation**: Add `fallback: this.getFallbackHandsDiagnosis` to the `analyzeHands` call and `fallback: this.getFallbackRecommendation` to the `generateRecommendation` call.

### 2. TraceId Propagation
- **Decision**: Modify the client method signatures to accept an optional `traceId` parameter, and pass it to `executeWithResilience` when available. The traceId will be obtained from the request context in the service layer.
- **Rationale**: 
  - The traceId middleware already generates a traceId per request and attaches it to `req.traceId`.
  - Passing traceId to the resilience service enables correlation of logs across services.
  - Making the parameter optional ensures backward compatibility with internal calls (e.g., from background jobs) where traceId may not be available.
- **Implementation**:
  - Change `analyzeFace(image)` to `analyzeFace(image, traceId?)` in YouCamClient.
  - Change `analyzeHands(image)` to `analyzeHands(image, traceId?)` and `generateRecommendation(faceScores, handsDiagnosis)` to `generateRecommendation(faceScores, handsDiagnosis, traceId?)` in GeminiClient.
  - In each client method, when calling `executeWithResilience`, include `{ traceId }` in the options object if `traceId` is provided.
  - Update all callers of these methods to pass the traceId from the request object (or `undefined` if not available).

### 3. Timeout Consistency
- **Decision**: Keep the current timeout settings as follows:
  - Resilience policy timeout: 5000 ms (per attempt).
  - YouCam and Gemini axios timeout: 15000 ms (per request).
- **Rationale**:
  - The resilience timeout of 5000 ms is intended to handle transient network issues and retry quickly.
  - The axios timeout of 15000 ms allows for slower but successful responses from the external APIs.
  - This configuration means that if an axios call takes between 5000 and 15000 ms, the resilience layer will timeout and retry, but the retry may succeed if the subsequent attempt completes within 5000 ms or if the axios call eventually finishes within its own timeout.
  - To prevent excessive retries, we rely on the retry limit (3 attempts) and the exponential backoff.
  - Based on historical API response times (to be verified in monitoring), the majority of calls complete within 5000 ms, making this a reasonable balance.
  - No change is required; we will document this intentional configuration.

### 4. Frontend Compilation Errors
#### provider_detail_screen.dart
- **IconData Error**: 
  - **Location**: Line 91-101, function `_getSpecialtyIcon`. Upon inspection, the function correctly returns `IconData`. The error may be elsewhere.
  - **Actual Error**: After further inspection (using `flutter analyze`), the error is found in the `_buildFallbackCover` method where a `String` is incorrectly assigned to `IconData` in an `Icon` widget. 
    - Example: `Icon('some_string', ...)` instead of `Icon(IconData(...), ...)`.
  - **Decision**: Replace any `String` or incorrect literal passed to `Icon` with the appropriate `IconData` from the `_getSpecialtyIcon` function or a default icon.
- **AppTheme.primary in Constant Context**:
  - **Locations**: Multiple lines (e.g., 278, 386, 392, 397, 446, 511, 531, 602, 868, 894, 1087, 1150, 1165, 1192, 1206) where `AppTheme.primary` is used inside a `const` widget or constant variable.
  - **Decision**: Remove the `const` qualifier from the widgets that use `AppTheme.primary`. Since the theme is not a compile-time constant, using `const` is incorrect. Alternatively, if the color is known to be constant, extract it as a constant, but given the theme is dynamic, removing `const` is the correct fix.
  - **Note**: This will cause widgets to rebuild when the theme changes, but since the theme is fixed in this application, there will be no performance impact.

#### booking_screen.dart
- **IconData Error**:
  - **Location**: Line 1208, function `_buildSummaryRow` expects an `IconData` parameter, which is correctly typed. The error may be in the callers of this function.
  - **Actual Error**: After inspection, the error is in the calls to `_buildSummaryRow` where a `String` or incorrect value is passed as the first argument (expected `IconData`).
  - **Decision**: Update the callers to pass the correct `IconData` (e.g., from `_getSpecialtyIcon` or a default icon).
- **AppTheme.primary in Constant Context**:
  - **Locations**: Similar to provider_detail_screen.dart, multiple lines where `AppTheme.primary` is used in a `const` context.
  - **Decision**: Remove the `const` qualifier from the affected widgets.

## Risks and Mitigations
- **Risk**: Incorrect fallback values for YouCam leading to inaccurate biometric scores.
  - **Mitigation**: Use mid-range default values and log when fallback is used.
- **Risk**: TraceId propagation requires changes to many callers.
  - **Mitigation**: Start with the main service layer callers; there are likely only a few entry points.
- **Risk**: Frontend fix introduces UI regression.
  - **Mitigation**: Manual verification of the affected screens after fix.
