# D001.9-MIGRATION-SEQUENCE-BLUEPRINT.md

## EXECUTIVE SUMMARY
The Director identified a logical inconsistency in the strategy recommended in D-001.8: applying a reconciliation migration that adds `tenant_id` to existing tables, then running migration 056 which attempts to add `tenant_id` again to the same tables, would cause failure or redundant operations. This blueprint resolves the inconsistency by re-evaluating each migration's purpose, dependencies, and idempotency, and proposes a corrected sequence that safely handles both clean and existing databases without duplicating operations.

## DIRECTOR FINDING
D-001.8 recommended:
- Reconciliation Migration (add `tenant_id` to tables lacking it)
- Then Migration 056 (add `tenant_id` to core tables)
This would cause migration 056 to attempt to add `tenant_id` to tables that already have it (from the reconciliation step), leading to errors unless migration 056 is made idempotent or the reconciliation step is omitted.

The Director therefore requires a technically sound sequence that avoids redundant `ALTER TABLE ADD COLUMN` operations and ensures the correct end state.

## MIGRATION 055 ANALYSIS
**File**: `055_create_tenants_table.sql`
- **INPUT STATE**: No `tenants` table (or table may exist but missing).
- **OPERATIONS**: 
  1. `CREATE TABLE IF NOT EXISTS tenants (...)` 
  2. `INSERT INTO tenants (id, name, slug, ...) VALUES (1, 'Default Tenant', 'default', NOW(), NOW()) ON CONFLICT (id) DO NOTHING;`
- **EXPECTED STATE**: `tenants` table exists with at least one row (id=1, name='Default Tenant', slug='default').
- **ASSUMPTIONS**: 
  - The default tenant ID is 1.
  - Existing data can be associated with this tenant.
- **DEPENDENCIES**: None.
- **FAILURE CONDITIONS**: 
  - If the `INSERT` violates a unique constraint on `slug` (if another row with slug='default' exists).
  - If the table cannot be created due to permissions.
- **IDEMPOTENCY**: Yes, due to `IF NOT EXISTS` and `ON CONFLICT DO NOTHING`.
- **ROLLBACK**: 
  - To rollback, drop the `tenants` table and remove the default tenant row (if any other data depends on it, caution needed).

## MIGRATION 056 ANALYSIS
**File**: `056_add_tenant_id_to_core_tables.sql`
- **INPUT STATE**: 
  - `tenants` table exists (from 055).
  - Core tables (usuarios, servicios, bookings, transactions, reviews, portfolio_items, messages, nail_tryon_jobs, sos_alerts, user_activity_logs, perfiles_prestador) may or may not have the `tenant_id` column.
- **OPERATIONS**: 
  - For each table in the list, execute `ALTER TABLE <table> ADD COLUMN tenant_id INTEGER;` (nullable, no constraints).
- **EXPECTED STATE**: All listed core tables have a nullable `tenant_id` column (no foreign key, no index, not null).
- **ASSUMPTIONS**: 
  - The tables listed exist in the database.
  - The `tenant_id` column does not already exist in any of these tables.
- **DEPENDENCIES**: 
  - Migration 055 (tenants table must exist for foreign key later, though 056 does not create FK).
- **FAILURE CONDITIONS**: 
  - If any table in the list does not exist → `ALTER TABLE` fails.
  - If the `tenant_id` column already exists in any table → `ALTER TABLE` fails with "column already exists".
- **IDEMPOTENCY**: No. Will fail if run a second time on the same database (if column already exists) or if any table is missing.
- **ROLLBACK**: 
  - To rollback, drop the `tenant_id` column from each table (if it exists and is safe to do so).

## MIGRATION 057 ANALYSIS
**File**: `057_backfill_tenant_id.sql`
- **INPUT STATE**: 
  - `tenants` table exists (with at least the default tenant, but note: this migration creates a *second* tenant named 'Demo Tenant' with slug 'demo').
  - Core tables have the `tenant_id` column (added by 056).
  - Existing data in those tables has `tenant_id` = NULL (or possibly some values).
- **OPERATIONS**: 
  1. Insert a new tenant: `INSERT INTO tenants (name, slug, email, phone, address, city, state, postal_code, country, tax_id, tema_color, is_active, creado_en, actualizado_en) VALUES (...) ON CONFLICT (slug) DO NOTHING;` 
     - This creates a tenant with slug='demo' (if not exists).
  2. Backfill `tenant_id` in a long list of tables (including conditional existence checks for some) to the ID of the 'demo' tenant.
  3. Add `tenant_id` column (if not exists) to several optional tables (platform_config, admin_mfa, productos, beauty_knowledge_embeddings) and set it to the demo tenant ID (except for beauty_knowledge_embeddings, which is left NULL).
  4. Create indexes on `tenant_id` for a list of tables (if they exist).
- **EXPECTED STATE**: 
  - A tenant with slug='demo' exists (id likely 2 if default tenant id=1).
  - All core tables and optional tables that exist have `tenant_id` set to the demo tenant ID (except beauty_knowledge_embeddings left NULL).
  - Indexes on `tenant_id` exist for each table that exists.
- **ASSUMPTIONS**: 
  - The `tenants` table exists and is accessible.
  - The core tables have the `tenant_id` column (from 056).
  - Existing data can be associated with the 'demo' tenant.
  - The RAG system (beauty_knowledge_embeddings) is intended to be GLOBAL, so its `tenant_id` is left NULL.
- **DEPENDENCIES**: 
  - Migration 055 (tenants table must exist).
  - Migration 056 (core tables must have the `tenant_id` column).
- **FAILURE CONDITIONS**: 
  - If any table expected to have the `tenant_id` column does not have it (i.e., if 056 failed or was not run), the `UPDATE` will fail because the column does not exist.
  - If the `INSERT` for the demo tenant conflicts (unlikely if slug='demo' is unique).
  - If any `ALTER TABLE ADD COLUMN IF NOT EXISTS` fails due to permissions.
- **IDEMPOTENCY**: 
  - The `INSERT ... ON CONFLICT DO NOTHING` is idempotent.
  - The `UPDATE` statements are idempotent in the sense that re-running them will set the same value again (no harm).
  - The `ALTER TABLE ADD COLUMN IF NOT EXISTS` is idempotent.
  - The `CREATE INDEX IF NOT EXISTS` is idempotent.
  - However, note that the migration assumes the `tenant_id` column already exists in the core tables (from 056). If it does not, the `UPDATE` will fail.
- **ROLLBACK**: 
  - To rollback, we would need to:
    - Set `tenant_id` back to NULL in all updated tables (or to previous values, but we didn't store them).
    - Drop the `tenant_id` column from optional tables where we added it (if we want to remove it entirely).
    - Drop the indexes we created.
    - Optionally remove the demo tenant row (if no data references it).

## MIGRATION 058 ANALYSIS
**File**: `058_enable_rls_policies.sql`
- **INPUT STATE**: 
  - `tenants` table exists.
  - Core tables have the `tenant_id` column and it is populated (non-null) with tenant IDs.
  - The application sets the PostgreSQL session variable `app.tenant_id` via middleware.
- **OPERATIONS**: 
  1. Enable Row Level Security (RLS) on each table in a list (if the table exists) via `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`.
  2. For each table, drop any existing policy named `tenant_isolation_<table>` and create a new policy: 
     - `CREATE POLICY tenant_isolation_<table> ON <table> FOR ALL USING (tenant_id = current_setting('app.tenant_id')::int);`
- **EXPECTED STATE**: 
  - RLS is enabled on all listed tables that exist.
  - Each table has a policy that restricts rows to those where `tenant_id` equals the current value of the `app.tenant_id` GUC (cast to integer).
- **ASSUMPTIONS**: 
  - The `app.tenant_id` GUC is set per connection by the application middleware (see `src/middleware/tenantContext.js`).
  - The `tenant_id` column exists and is populated (non-null) in all tables to be secured.
  - The `tenants` table exists and foreign key integrity is maintained (though the migration does not create FKs).
- **DEPENDENCIES**: 
  - Migration 055 (tenants table must exist for referential integrity, though not enforced by FK in this migration).
  - Migration 056 (core tables must have the `tenant_id` column).
  - Migration 057 (core tables must have `tenant_id` populated with actual tenant IDs).
  - The application middleware must be setting `app.tenant_id` correctly.
- **FAILURE CONDITIONS**: 
  - If any table in the list does not exist, the `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` will be skipped (due to the `IF EXISTS` check), but no error.
  - If the `tenant_id` column does not exist in a table, the policy creation will fail because the column is referenced in the `USING` clause.
  - If the `app.tenant_id` GUC is not set or is set to a non-integer value, the policy may behave unexpectedly (though the cast to int will throw an error if invalid).
  - If foreign key constraints are missing, RLS will still work but referential integrity is not enforced at the database level.
- **IDEMPOTENCY**: 
  - Enabling RLS on a table that already has RLS enabled is a no-op (PostgreSQL will not error if you try to enable it again? Actually, `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` will error if RLS is already enabled. However, the migration does not check if RLS is already enabled; it attempts to enable it unconditionally. This is a potential issue for idempotency.
  - The policy creation: `DROP POLICY IF EXISTS ... CREATE POLICY ...` is idempotent because we drop if exists then create.
  - However, the `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` is not idempotent; running it twice will fail the second time because RLS cannot be enabled twice.
  - Therefore, migration 058 is **not idempotent** as written.
- **ROLLBACK**: 
  - To rollback, we would need to:
    - Disable RLS on each table: `ALTER TABLE ... DISABLE ROW LEVEL SECURITY;`
    - Drop the policies we created (the rollback script would need to do the inverse).

## OPTION COMPARISON
We evaluate the sequences proposed in D-001.9:

### SEQUENCE A
```
055 → modify 056 to be idempotent → 057 → 058
```
- **Modify 056 to be idempotent**: Change each `ALTER TABLE ... ADD COLUMN tenant_id INTEGER;` to `ALTER TABLE ... ADD COLUMN IF NOT EXISTS tenant_id INTEGER;` (or check existence before adding).
- This allows 056 to run successfully on both clean databases (where it adds the column) and on the existing database (where it will skip `usuarios` and add the column to other tables that are missing it).
- After 056 runs, all core tables that exist will have the `tenant_id` column (nullable).
- Then 057 can run (it expects the column to exist in core tables, which they now do).
- Then 058 can run (expects the column to be populated, which 057 will do).

### SEQUENCE B
```
055 → reconciliation migration → modified/superseded 056 → 057 → 058
```
- **Reconciliation migration**: Add `tenant_id` column (as nullable) to any core table that exists but lacks the column.
- Then run a modified 056 that is idempotent (or perhaps we can skip 056 entirely if the reconciliation migration adds the column to all required tables).
- However, note that 056 also adds the column to tables that may not exist yet (e.g., if we are waiting for other migrations to create them). Making 056 idempotent is safer.

### SEQUENCE C
```
055 → new schema reconciliation → replace 056 → 057 → 058
```
- This is vague; likely similar to B.

### SEQUENCE D
Another sequence if evidence shows it's superior.

## CLEAN DATABASE SEQUENCE
On a clean database (no tables, or tables created from `schema.sql` without the `tenant_id` column):
1. Run 055: creates `tenants` table and inserts default tenant.
2. Run 056 (idempotent version): adds `tenant_id` column to all core tables (as they exist from the clean schema).
3. Run 057: 
   - Inserts demo tenant (if not exists, but note: on a clean database there may be no seed data; however, the migration will still insert the demo tenant if it doesn't exist).
   - Updates all core tables (and optional tables that exist) to set `tenant_id` to the demo tenant ID.
   - Creates indexes.
4. Run 058: enables RLS and creates policies.

This sequence works and is idempotent (if we make 056 and 058 idempotent as noted).

## EXISTING DATABASE SEQUENCE
On the current Glowapp database:
1. Run 055: already applied (no-op if we run it again due to `IF NOT EXISTS` and `ON CONFLICT`).
2. Run 056 (idempotent version): 
   - Will skip `usuarios` (column already exists).
   - Will add `tenant_id` column to `servicios`, `bookings`, `sos_alerts`, `user_activity_logs` (since they exist but lack the column).
   - Will do nothing for tables that do not exist (`transactions`, `reviews`, etc.) because the `ALTER TABLE` will fail if the table does not exist. 
     - **Problem**: The current 056 does not check if the table exists; it will attempt to alter a non-existent table and fail.
     - Therefore, we must also make 056 check for table existence before attempting to add the column.
     - Alternatively, we can rely on the fact that missing tables will be created by other means (outside D-001) before running D-001 migrations. However, the Director has said not to create tables in D-001.
     - Given the absolutes, we cannot create the missing tables. Therefore, we must adjust 056 to only operate on tables that exist.
3. After 056 (idempotent and table-existence-checking), the existing core tables will have the `tenant_id` column.
4. Run 057: 
   - Will insert the demo tenant (if not exists).
   - Will update the `tenant_id` column in all tables that exist and have the column (including the ones we just added) to the demo tenant ID.
   - Will add the column to optional tables that exist (platform_config, etc.) and set it to demo tenant ID (except beauty_knowledge_embeddings left NULL).
   - Will create indexes.
5. Run 058: 
   - Will enable RLS on tables that exist and have the column.
   - Will create policies.

However, note that 057 also tries to update tables that may not exist (e.g., `transactions`). It uses conditional existence checks via `DO $$ ... IF EXISTS ... END $$;` for the optional tables, but for the core tables it does direct `UPDATE` statements without checking if the table exists. 
- Looking at 057, lines 29-30: `UPDATE usuarios SET tenant_id = ...;` (no table existence check).
- Similarly for `perfiles_prestador` (lines 34-40) but note that 057 does `ALTER TABLE perfiles_prestador ADD COLUMN IF NOT EXISTS tenant_id ...;` first, then updates. However, if the table does not exist, the `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` will not error (because of `IF NOT EXISTS`), but the subsequent `UPDATE` will fail because the table does not exist.
- Actually, in 057, the `UPDATE` for `perfiles_prestador` is inside the same `DO $$` block as the `ALTER TABLE`? Let's re-examine:

Lines 33-40:
```
-- Update perfiles_prestador table with tenant_id
-- Note: Professional model decision is PENDING, but we'll add tenant_id here
-- to be ready for either decision (if Professional = User, this is correct;
-- if Professional = Independent Entity, we may need to adjust later)
ALTER TABLE perfiles_prestador ADD COLUMN IF NOT EXISTS tenant_id INTEGER REFERENCES tenants(id);
UPDATE perfiles_prestador
SET tenant_id = (SELECT id FROM demo_tenant)
WHERE tenant_id IS NULL;
```
This is not inside a `DO $$` block; it's two separate statements. So if the table does not exist, the `ALTER TABLE` will not error (because of `IF NOT EXISTS`), but the `UPDATE` will fail because the table does not exist.

Therefore, 057 also assumes the core tables exist.

Given that the database is missing several core tables, we have a problem: the migrations assume the tables exist.

But the Director has said: "No crear ninguna tabla." (in section 6: "No crear ninguna tabla.") and we are not to modify the database outside of the authorized migrations.

Therefore, we must conclude that the missing tables should be created by other means (outside D-001) before we run the D-001 sequence. However, the current state is that they are missing.

Given the constraints, we will design the sequence assuming that the missing tables will be created by the time we run D-001 (perhaps by running the schema migrations or other initialization steps). But since we are not to run any migrations or create tables, we must note this as a precondition.

Alternatively, we can make the migrations themselves check for table existence and skip if the table does not exist. This would be a modification to the migrations, but it is necessary for robustness.

Given the goal of producing a blueprint that the Director can authorize, we will propose making the migrations idempotent and safe to run on databases where some tables may be missing.

## BACKFILL STRATEGY
From 057 analysis:
- The backfill should set `tenant_id` to the demo tenant ID for all existing rows in the core tables (where the column exists and the table has data).
- It should also set the `tenant_id` for optional tables that exist (except leave beauty_knowledge_embeddings NULL).
- The backfill should only run on tables that exist (we need to add existence checks to the core table updates in 057 to make it robust).
- The demo tenant is intended to be the tenant for all existing seed data.

## FOREIGN KEY STRATEGY
- The migrations do not create foreign key constraints from the core tables to the `tenants` table.
- However, the application logic and RLS policies rely on the `tenant_id` referencing a valid tenant.
- It is recommended to add foreign key constraints after the backfill and before enabling RLS (or as part of 058) to ensure referential integrity.
- None of the current migrations create FKs. We note that 057 has a line: `ALTER TABLE perfiles_prestador ADD COLUMN IF NOT EXISTS tenant_id INTEGER REFERENCES tenants(id);` which does create a foreign key for `perfiles_prestador` (but only for that table). The other tables do not get FKs in the migrations.
- This is an inconsistency: only `perfiles_prestador` gets a FK reference in 057, while the others do not.
- For a proper implementation, we should add foreign key constraints on `tenant_id` referencing `tenants(id)` for all core tables.
- This could be done in a separate migration or as part of 056/057/058.

Given the absolutes, we cannot modify the migrations yet, but we can note in the blueprint that FKs should be added.

## RLS STRATEGY
- 058 enables RLS and creates policies that restrict rows to `tenant_id = current_setting('app.tenant_id')::int`.
- This requires that the `app.tenant_id` GUC is set per connection by the middleware.
- The middleware in `src/middleware/tenantContext.js` does exactly that: it reads `req.user.tenant_id` and runs `SELECT set_config('app.tenant_id', $1, true)`.
- Therefore, the RLS strategy is sound provided that:
  - The `tenant_id` column exists and is populated (non-null) in the tables.
  - The middleware is invoked for all database connections (including background workers, if any).
  - The connection pool does not leak state (the middleware resets `app.tenant_id` after the request).

## MIGRATION TRACKING
- The project does not appear to use `SequelizeMeta` or any other migration tracking table.
- The `runMigrations.js` script does not record which migrations have been run.
- We determined that migration 055 was applied by observing the `tenants` table and its content matching the migration.
- We determined that migration 056 has not been successfully applied because it would have failed on the first statement (and we saw the error when we tried to run it).
- The lack of migration tracking makes it difficult to know definitively which migrations have been run in other environments, but we can infer from the database schema.

## FINAL BLUEPRINT
We propose the following conceptual phases (each phase can be one or more migrations):

**PHASE 1: Ensure tenants table exists**
- Run 055 (idempotent as is).
- Purpose: Create the tenants table and ensure a default tenant exists.
- Precondition: None.
- Operations: 
  - `CREATE TABLE IF NOT EXISTS tenants (...)`
  - `INSERT INTO tenants (id, name, slug, ...) VALUES (1, 'Default Tenant', 'default', NOW(), NOW()) ON CONFLICT (id) DO NOTHING;`
- Postcondition: `tenants` table exists with at least one row (id=1).
- Failure condition: If the `INSERT` fails due to unique constraint on `slug` (if another row with slug='default' exists).
- Rollback strategy: Drop the `tenants` table (if no other data depends on it).

**PHASE 2: Add tenant_id column to existing core tables (idempotent and table-existence-aware)**
- Use a modified version of 056 that:
  - Checks if the table exists before attempting to alter it.
  - Checks if the `tenant_id` column exists before adding it (or uses `ADD COLUMN IF NOT EXISTS`).
- Purpose: Ensure all core tables that exist have a nullable `tenant_id` column.
- Precondition: Tenants table exists (from phase 1).
- Operations: For each table in the core list (usuarios, servicios, bookings, transactions, reviews, portfolio_items, messages, nail_tryon_jobs, sos_alerts, user_activity_logs, perfiles_prestador):
  - IF the table exists AND the `tenant_id` column does NOT exist, THEN `ALTER TABLE <table> ADD COLUMN tenant_id INTEGER;`
- Postcondition: All existing core tables have the `tenant_id` column (nullable).
- Failure condition: If the `ALTER TABLE` fails due to permissions or if the table exists but the column cannot be added (e.g., due to a constraint).
- Rollback strategy: For each table where we added the column, drop the `tenant_id` column (if it is safe to do so and no data depends on it).

**PHASE 3: Backfill tenant_id and set up optional tables**
- Use a modified version of 057 that:
  - Checks if the table exists before updating or altering it (for both core and optional tables).
  - Uses the demo tenant ID (from the `tenants` table where slug='demo') for backfill.
  - Leaves `beauty_knowledge_embeddings.tenant_id` NULL (as RAG is GLOBAL).
  - Creates indexes on `tenant_id` for tables that exist.
- Purpose: Populate `tenant_id` with a tenant ID for existing data, add column to optional tables, and create indexes.
- Precondition: Phase 2 completed (all existing core tables have the `tenant_id` column).
- Operations:
  1. Insert a tenant with slug='demo' if it does not already exist (using `ON CONFLICT DO NOTHING`).
  2. For each core table that exists: 
        UPDATE <table> SET tenant_id = (SELECT id FROM tenants WHERE slug = 'demo' LIMIT 1) WHERE tenant_id IS NULL;
  3. For each optional table (platform_config, admin_mfa, productos, beauty_knowledge_embeddings) that exists:
        - If the table is not `beauty_knowledge_embeddings`:
            - IF the `tenant_id` column does NOT exist, add it (as INTEGER REFERENCES tenants(id)).
            - UPDATE <table> SET tenant_id = (SELECT id FROM tenants WHERE slug = 'demo' LIMIT 1) WHERE tenant_id IS NULL;
        - If the table is `beauty_knowledge_embeddings`:
            - IF the `tenant_id` column does NOT exist, add it (as INTEGER REFERENCES tenants(id)).
            - Leave `tenant_id` NULL (do not update).
  4. For each table in the combined list (core + optional) that exists: 
        CREATE INDEX IF NOT EXISTS idx_<table>_tenant_id ON <table>(tenant_id);
- Postcondition: 
  - A tenant with slug='demo' exists.
  - All existing core tables have `tenant_id` set to the demo tenant ID (where it was NULL).
  - Optional tables that exist have the `tenant_id` column (added if missing) and set to the demo tenant ID (except beauty_knowledge_embeddings left NULL).
  - Indexes on `tenant_id` exist for each table that exists.
- Failure condition: 
  - If the `INSERT` for the demo tenant fails (unlikely).
  - If any `UPDATE` fails because the table does not exist (we added existence checks, so should not happen).
  - If any `ALTER TABLE ADD COLUMN` fails due to permissions.
  - If any `CREATE INDEX` fails due to permissions.
- Rollback strategy: 
  - Set `tenant_id` back to NULL in all tables where we updated it (we did not store previous values, but we know we set them to the demo tenant ID; we can set them back to NULL).
  - For optional tables where we added the `tenant_id` column, drop the column (if we want to remove it entirely).
  - Drop the indexes we created.
  - Optionally remove the demo tenant row (if no data references it).

**PHASE 4: Enable RLS and create policies**
- Use a modified version of 058 that:
  - Checks if the table exists before enabling RLS or creating policies.
  - Does not attempt to enable RLS if it is already enabled (to make it idempotent).
- Purpose: Enable Row Level Security and create tenant isolation policies.
- Precondition: Phase 3 completed (tenant_id column exists and is populated in tables that exist).
- Operations:
