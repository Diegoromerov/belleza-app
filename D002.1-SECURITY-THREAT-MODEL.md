# D002.1-SECURITY-THREAT-MODEL.md

## Security Threat Model for Workforce Management (D-002)

**Note**: This is a conceptual threat model only. No implementation is authorized at this stage.

### Overview
This threat model identifies potential security risks associated with extending GlowApp to support operational workforce classification (EMPLEADO, PRESTADOR_SERVICIO, etc.) under the D-002 decision that GlowApp remains a technology platform only. The model assumes the proposed changes from D002.1-DATA-MODEL.md (adding `worker_type` column to `usuarios`) and corresponding API/UX specifications.

### Assets to Protect
- Workforce member data (including operational classification, personal info like name, email).
- Tenant isolation: ensuring users cannot access workforce data from other tenants.
- Integrity of classification data: preventing unauthorized modification that could misrepresent salon's internal operations.
- Confidentiality: ensuring that workforce data is not exposed to unauthorized parties (e.g., clients, other tenants).

### Threat Agents
- Malicious insider (e.g., a salon employee attempting to access another tenant's data).
- External attacker (compromised credentials, exploiting API vulnerabilities).
- Accidental misconfiguration (e.g., missing tenant scope in a query).

### Threat Scenarios and Mitigations

#### 1. Cross-Tenant Data Access (IDOR)
- **Threat**: A user manipulates API requests to access workforce members belonging to another tenant (e.g., by guessing or altering user IDs).
- **Impact**: Unauthorized disclosure of workforce information; potential privacy violation.
- **Mitigations**:
  - Enforce tenant context in all database queries: every query involving workforce-related tables must include `WHERE tenant_id = :current_tenant_id`.
  - Apply Row-Level Security (RLS) policies on the `usuarios` table (if extended with sensitive data) and any new tables, using the `app.tenant_id` GUC set by the tenantContext middleware.
  - In the API layer, validate that the requested resource ID belongs to the current tenant before returning data.
  - Use indirect references (e.g., UUIDs) instead of sequential IDs where feasible to reduce guessability.

#### 2. Privilege Escalation via Role Confusion
- **Threat**: A user with limited permissions (e.g., a regular prestador) gains access to workforce management endpoints and modifies classifications (e.g., marks themselves as ADMIN_SALON) to gain higher privileges within the salon.
- **Impact**: Unauthorized elevation of salon-level privileges; potential misuse of salon admin functions.
- **Mitigations**:
  - Separate GlowApp platform roles (e.g., salon_admin, owner, prestador, client) from workforce operational categories (EMPLEADO, PRESTADOR_SERVICIO).
  - Workforce management endpoints must check the user's platform role (e.g., via existing `rol` column or a separate role table) and only allow users with appropriate salon-level permissions (e.g., owner or admin) to modify workforce classifications.
  - Do not rely on `worker_type` for authorization decisions within the platform; use only the established role/permission system.

#### 3. Exposure of Sensitive Data via API
- **Threat**: API responses inadvertently include fields that should not be exposed (e.g., internal notes, unclear data that could be misinterpreted as legal obligations).
- **Impact**: Misunderstanding that GlowApp assumes employer obligations; potential legal risk.
- **Mitigations**:
  - Define strict API schemas that include only the necessary fields for workforce management (e.g., id, email, nombre, worker_type, rol, is_active, created_at).
  - Exclude any fields that could imply GlowApp is storing payroll, tax, contract, or salary information.
  - Conduct API documentation reviews to ensure descriptions clarify that `worker_type` is operational only.
  - Apply data minimization: do not collect or store unnecessary personal data.

#### 4. Insecure Direct Object Reference (IDOR) in UI
- **Threat**: A user manipulates frontend requests (e.g., by altering network calls) to view or edit workforce members of another tenant.
- **Impact**: Same as cross-tenant data access.
- **Mitigations**:
  - Ensure the frontend relies on backend endpoints that enforce tenant scope; do not trust client-side filtering.
  - Implement backend validation as the primary defense; frontend validation is for UX only.
  - Use session-scoped tenant context; do not pass tenant_id in client-side tokens or URLs that could be tampered with.

#### 5. RLS Misconfiguration or Bypass
- **Threat**: Row-Level Security policies are not applied, are incorrectly defined, or are bypassed (e.g., by disabling RLS for a session).
- **Impact**: Users can see or modify data from other tenants.
- **Mitigations**:
  - Ensure RLS is enabled on all tables containing tenant-sensitive data (including `usuarios` if extended with workforce data).
  - Test RLS policies to confirm they restrict access correctly.
  - Use the `app.tenant_id` GUC consistently; the tenantContext middleware must set it for every authenticated connection and reset it after.
  - Avoid using raw SQL queries that bypass the ORM or query builders that automatically apply tenant scope.

#### 6. Privilege Escalation via tenant_id Manipulation
- **Threat**: A user somehow changes their own `tenant_id` in the `usuarios` table (or via API) to access another tenant's workforce data.
- **Impact**: Cross-tenant data breach.
- **Mitigations**:
  - The `tenant_id` column should be immutable after creation (except perhaps during onboarding) and protected by authorization checks.
  - API endpoints that update user data must not allow changing `tenant_id` unless explicitly authorized (e.g., only by a super admin, which should not exist in a pure SaaS model; tenant assignment should happen only during initial tenant creation or via a secure, audited process).
  - Log and alert on attempts to modify `tenant_id`.

#### 7. Data Leakage via Logs or Error Messages
- **Threat**: Error messages or logs expose sensitive workforce data or tenant identifiers.
- **Impact**: Information disclosure that could aid further attacks.
- **Mitigations**:
  - Ensure that logs and error messages do not include sensitive data (e.g., emails, names, full IDs).
  - Use structured logging that separates sensitive data into secure stores if needed.
  - Avoid printing raw SQL queries with parameter values in production logs.

#### 8. Insufficient Authentication/Authorization
- **Threat**: Missing or broken authentication allows unauthorized access to workforce management endpoints.
- **Impact**: Full compromise of workforce data.
- **Mitigations**:
  - Ensure all workforce-related endpoints require authentication.
  - Implement centralized authentication checks; do not rely on per-endpoint checks that can be forgotten.
  - Use role-based access control (RBAC) at the API gateway or middleware level.

#### 9. Mass Assignment Vulnerability
- **Threat**: An API endpoint accepts and updates fields that should not be modifiable (e.g., `tenant_id`, `id`, `created_at`) due to unrestricted object mapping.
- **Impact**: Unauthorized modification of protected fields.
- **Mitigations**:
  - Use explicit allow-lists for updatable fields in API endpoints (e.g., only allow `worker_type` and `is_active` to be updated via the workforce update endpoint).
  - Reject any unknown fields in the request payload with a 400 error.

#### 10. Lack of Rate Leading to Brute Force or Enumeration
- **Threat**: An attacker can enumerate workforce member IDs by making repeated requests to guess valid IDs.
- **Impact**: Potential discovery of valid IDs leading to further attacks (if combined with IDOR).
- **Mitigations**:
  - Implement rate limiting on API endpoints, especially those that expose IDs.
  - Consider using UUIDs (already used in many tables) instead of sequential IDs for primary keys to reduce enumerability. For `usuarios`, which uses SERIAL, consider adding a UUID column for public references or relying on strict tenant scoping and rate limiting.

### Data Classification and Handling
- **Public Data**: None of the workforce data should be considered public; all access requires authentication and tenant context.
- **Sensitive Data**: Operational classification (`worker_type`) is considered internal to the salon but not highly sensitive (like salaries or SSNs). However, to be safe, treat it as confidential and ensure it is only accessible within the tenant.
- **Personal Data**: Name and email are personal data; ensure compliance with data protection laws (Ley 1581) by providing salon controls for data access, correction, and deletion as needed.

### Conclusion
The proposed changes for D-002 can be implemented securely by:
- Leveraging the existing D-001 multi-tenancy foundation (tenant_id, RLS, tenantContext middleware).
- Applying strict tenant scoping in all queries and API endpoints.
- Separating platform roles from operational classifications.
- Implementing proper authentication, authorization, and input validation.
- Conducting regular security reviews and penetration testing.

Any implementation must follow these mitigations and be subject to security and legal review before deployment.
