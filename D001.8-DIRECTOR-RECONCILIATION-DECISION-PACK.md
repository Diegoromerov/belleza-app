# D001.8-DIRECTOR-RECONCILIATION-DECISION-PACK.md

## EXECUTIVE SUMMARY
The D-001 multi-tenancy implementation (Shared Schema + tenant_id + RLS) is in a partial state. Migration 055 (create tenants table) has been applied, creating a default tenant. Migration 056 (add tenant_id to core tables) failed because the `usuarios` table already contains a `tenant_id` column (nullable, all NULL). The application code already references and uses this column. No backfill (057) or RLS enabling (058) has been executed. The database schema is inconsistent with the expected schema from `schema.sql` (some tables missing, extra tables present). The goal is to reconcile the existing state with the approved multi-tenant architecture without data loss or introducing a parallel implementation.

## KNOWN FACTS
- Migration 055: APPLIED (tenants table exists with 1 row: id=1, name='Default Tenant', slug='default')
- Migration 056: FAILED (first statement: ALTER TABLE usuarios ADD COLUMN tenant_id; failed due to column already existing)
- Migration 057: NOT EXECUTED
- Migration 058: NOT EXECUTED
- `tenants` table: EXISTS
- `usuarios.tenant_id`: EXISTS (type: INTEGER, nullable: YES, default: NULL), all 3 rows have NULL

- `perfiles_prestador` table: DOES NOT EXIST
- Application code in `src/middleware/auth.js` and `src/middleware/tenantContext.js` reads `usuarios.tenant_id` and uses it to set the PostgreSQL session variable `app.tenant_id`.

- No RLS policies enabled.

## ROOT CAUSE
The `usuarios.tenant_id` column exists prior to the execution of migration 056. The most probable causes, in order of likelihood:

1. **PROBABLE**: A previous attempt at implementing multi-tenancy (possibly using a different approach or experimental branch) added the column manually or via a migration that is no longer present in the current repository state (e.g., due to rebasing, squashing, or branch deletion).
2. **UNKNOWN**: The column was added for testing or development purposes and was never cleaned up, with no record in the migration history or Git.
3. **UNKNOWN**: The column was added by a migration that has since been altered or removed from the migration history (e.g., via a rebase or squash) and is not reflected in the current migration files.

Evidence supporting the probable cause:
- The column is nullable and all existing rows have NULL values, indicating it was not populated with meaningful data.
- The migration 056 that would add this column failed because it already exists, suggesting the column was added outside of the D-001 migration sequence.
- The application code already references `tenant_id` in the auth and tenant context middleware, indicating that the column is expected and used (even if all values are currently NULL).
- Git history shows no commits that add or remove the string "tenant_id" (via `git log -S "tenant_id"` and `git log -G "tenant_id"`), suggesting the column was not added via a commit in the current branch's history.

## OPTIONS
We evaluate the following reconciliation options:

### OPTION A — PRESERVAR (Preserve existing `usuarios.tenant_id` and adapt migration strategy)
Keep the existing `tenant_id` column in `usuarios` and modify the migration strategy to continue using that column.

### OPTION B — RECONCILIATION MIGRATION (Create a conceptual reconciliation migration)
Create a migration that brings the database to a state where migration 056 can run successfully (e.g., by ensuring the `tenant_id` column exists in all required tables) before running 056–058.

### OPTION C — REBUILD (Drop and recreate `usuarios.tenant_id`)
Drop the `tenant_id` column from `usuarios` and then run migration 056 as-is. Considered high risk by default.

### OPTION D — MIGRATION REWRITE (Modify 056 to be idempotent)
Conceptually modify migration 056 to detect existing structures and continue without error.

## NEW DATABASE SCENARIO (Clean / Empty Database)
On a clean database (no tables, or tables created from `schema.sql` without the `tenant_id` column):
- Migration 055: Creates `tenants` table.
- Migration 056: Adds `tenant_id` column to all core tables (nullable).
- Migration 057: Backfills `tenant_id` to the default tenant (if any data exists, or skips if no data).
- Migration 058: Enables RLS policies.
This is the intended path and should work without modification.

## EXISTING DATABASE SCENARIO (Current State)
The current database has:
- The `tenants` table from 055.
- The `usuarios` table already has a `tenant_id` column (nullable, all NULL).
- Some other tables from the core list are missing the `tenant_id` column.
- Some tables expected by `schema.sql` are missing entirely.
- Extra tables from other features are present.

The strategy must reconcile the existing state without breaking the ability to run the same migrations on a clean database.

## MIGRATION 056 RECOMMENDATION
**Conceptually**: Migration 056 should be modified to be idempotent, i.e., it should check if the `tenant_id` column exists before attempting to add it. This allows it to run successfully on both clean databases (where it adds the column) and on the existing database (where it skips the column for `usuarios` and adds it to other tables that are missing it).

However, per the absolute prohibitions of this phase, we are not to modify the migration file yet. We are only to prepare the decision pack.

Thus, we recommend that the Director consider **Option D (Migration Rewrite)** as the preferred approach because it maintains idempotency and traceability (if we keep a record of the change) and works for both clean and existing databases. Alternatively, **Option B (Reconciliation Migration)** is also safe and clear.

## MIGRATION 057 PREREQUISITES
Before executing the backfill migration (057), the following conditions must be met:
1. The `tenant_id` column must exist in all tables that are to be backfilled (i.e., the core tables listed in 056: usuarios, servicios, bookings, transactions, reviews, portfolio_items, messages, nail_tryon_jobs, sos_alerts, user_activity_logs, perfiles_prestador).
2. The `tenants` table must exist and have at least one tenant (the default tenant with id=1).
3. There must be a mapping strategy for existing data. In the case of D-001, the default tenant is used for all existing data.
4. The `tenant_id` column must be nullable (to allow the backfill to run without violating NOT NULL constraints, if any are added later).
5. No foreign key constraints on `tenant_id` should exist yet (they are added after backfill, per the migration comments).
6. The application must be able to handle the `tenant_id` being set during the backfill (though the backfill runs as a migration, not during runtime).

**Evidence for assigning existing users to Default Tenant**:
- The `usuarios` table already has a `tenant_id` column, but all values are NULL.
- The `tenants` table has a default tenant (id=1).
- There is no evidence that any existing data belongs to a specific other tenant (since we only have one tenant).
- The application code does not currently distinguish between tenants (since all are NULL or the same).
- Therefore, it is safe to assign all existing rows in the core tables to the default tenant (id=1) during backfill.

However, note that some core tables (e.g., bookings, transactions) are missing entirely, so there is no data to backfill in those tables. The backfill migration should only affect tables that exist and have data.

## MIGRATION 058 / RLS PREREQUISITES
Before enabling RLS (migration 058), the following must exist or be true:
1. The `tenant_id` column must exist and be populated (non-null) in all tables that are to be secured by RLS.
2. Foreign key constraints from the core tables to the `tenants` table (on `tenant_id`) must exist to ensure referential integrity.
3. Indexes on `tenant_id` in the core tables for performance (though not strictly required, they are recommended).
4. The application must set the `app.tenant_id` PostgreSQL session variable for each connection (which the tenant context middleware does).
5. RLS policies must be created that restrict rows to the current `app.tenant_id`.
6. The connection pool must not leak state between connections (the middleware resets `app.tenant_id` after each request).
7. Service roles (if used) must be configured appropriately.
8. Admin operations and background workers must also set the `app.tenant_id` context if they access tenant-specific data.
9. Raw SQL queries (outside the ORM) must also respect the `app.tenant_id` setting (which they will if they rely on the session variable and RLS is enabled).

## CRITICAL SECURITY QUESTION
> Does the existence of `usuarios.tenant_id` create a false sense of multi-tenancy without real isolation?

**Answer: YES**
- Explanation: The `usuarios.tenant_id` column exists and is readable by the application code (as seen in auth.js and tenantContext.js). However, all values are currently NULL, meaning that no data is actually associated with a tenant. If the application were to use this column for filtering (e.g., "show me only my tenant's data"), it would return no results because all rows have NULL tenant_id. Furthermore, without RLS policies enabled, there is no database-level enforcement preventing a user from seeing data from another tenant (if such data existed). Since there is only one default tenant and no tenant-specific data has been created, the false sense is academic but still present: the column exists and is read, but it does not provide isolation because it is not populated and RLS is not enabled.

## DATA SAFETY DECISION
> Is there sufficient evidence to automatically assign existing data to Tenant 1 during backfill?

**Answer: YES, with the condition that we only assign data in tables that exist and have rows.**
- Evidence: 
  - There is only one tenant in the system (the default tenant, id=1).
  - No data has been explicitly assigned to any other tenant (since no other tenants exist).
  - The `usuarios.tenant_id` column is already present and all values are NULL, indicating that the data is not currently associated with any tenant.
  - The application code already expects to read `tenant_id` from the `usuarios` table and use it for context.
  - Therefore, it is safe to backfill all existing rows in the core tables (where the column exists and the table has data) with the default tenant ID (1).
- However, we note that some core tables (transactions, reviews, portfolio_items, messages, nail_tryon_jobs) are missing from the database, so there is no data to backfill in those tables. The backfill migration should only run on tables that exist.
- **NO AUTOMATIC BACKFILL AUTHORIZED** for tables that do not exist in the database (they must be created first, possibly via schema migrations or the application's table creation logic).
- For tables that exist but lack the `tenant_id` column (like `servicios` and `bookings`), we must first add the column (via a reconciliation step) before backfilling.

## RECOMMENDED PATH
**RECOMMENDED**: Option B (Create a reconciliation migration) followed by the original migrations 056, 057, and 058, with the understanding that migration 056 should be run after the reconciliation migration (which ensures the `tenant_id` column exists in all core tables). The reconciliation migration would:
1. Add the `tenant_id` column (as nullable) to any core table from the 056 list that exists in the database but lacks the column.
2. Do nothing for tables that already have the column (like `usuarios`).
3. Do nothing for tables that do not exist (they will be created by other means, if needed).

This approach is additive, clear, and idempotent (the reconciliation migration can be run multiple times without harm). It preserves the existing `usuarios.tenant_id` column and ensures that all required tables have the column before backfill and RLS.

## FALLBACK PATH
**FALLBACK**: Option D (Rewrite migration 056 to be idempotent) by modifying the migration file to check for the existence of the `tenant_id` column before adding it. This approach avoids creating an extra migration file but alters the original migration. It is also safe and idempotent, and works for both clean and existing databases.

## BLOCKERS
- The absence of core tables (e.g., bookings, transactions) in the database may indicate that the database is not fully migrated to the latest `schema.sql`. These tables may need to be created before adding the `tenant_id` column.
- The presence of extra tables from other features may cause confusion but does not block the multi-tenancy implementation.
- No migration tracking mechanism exists, making it difficult to know which migrations have been run in other environments.

## RISKS
- If we choose to preserve the existing `usuarios.tenant_id` column and proceed with backfill and RLS, we must ensure that the column is properly indexed and foreign-keyed to the `tenants` table for performance and integrity.
- The backfill operation will set `tenant_id` to 1 for all existing rows in the core tables. If any data was intended to belong to a different tenant (which there is no evidence of), this would be incorrect. However, given the single tenant and NULL values, this risk is low.
- Enabling RLS without proper testing could block access to data if the `app.tenant_id` is not set correctly by the middleware.
- The existence of extra tables may lead to inconsistent tenantization if those tables are later found to require multi-tenancy.
