# RLS FEASIBILITY ANALYSIS FOR GLOWAPP

## 1. INTRODUCTION
This document analyzes the feasibility of implementing Row Level Security (RLS) in PostgreSQL for GlowApp, based on the current codebase and stack.

## 2. CURRENT STACK
- **Database**: PostgreSQL 15+ (verified via schema.sql extensions: postgis, vector)
- **ORM**: Sequelize (used in controllers, services, models)
- **Raw SQL**: pgPool (used in controllers for some queries, e.g., bookingController.js)
- **Connection Pool**: pgPool (see `/c/beauty-app/backend/config/db.js` inferred from imports)
- **Authentication**: JWT-based, middleware `authMiddleware` sets `req.user`
- **Middleware**: Express middleware chain
- **Transactions**: Sequelize `transaction()` and raw `pool.query` with explicit transaction handling (seen in bookingController.js)
- **Redis**: Used for token blacklisting and potentially caching (config/redis.js)

## 3. RLS IN POSTGRESQL – REQUIREMENTS
To use RLS effectively:
1. Add a `tenant_id` column (or equivalent) to tables that need row-level isolation.
2. Enable RLS on those tables: `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`
3. Create policies that restrict rows based on the current tenant context, e.g.:
   ```sql
   CREATE POLICY tenant_isolation ON tablename
   USING (tenant_id = current_setting('app.tenant_id')::integer);
   ```
4. Set the context (e.g., `app.tenant_id`) for each database session/connection/transaction, typically via:
   - `SET LOCAL app.tenant_id = ...;` (transaction-scoped)
   - `SET app.tenant_id = ...;` (session-scoped)
   - Using a connection-scoped variable via `pgpool` or a custom wrapper.

## 4. FEASIBILITY ANALYSIS

### 4.1. Database Level
- PostgreSQL version supports RLS (9.5+). Verified: extensions postgis and vector are installed, indicating a recent PostgreSQL.
- No current RLS policies or `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` found in schema.sql.

### 4.2. ORM (Sequelize)
- Sequelize does not have built-in RLS support, but it can work with RLS if the tenant context is set on the connection/transaction.
- Risk: Sequelize uses connection pooling; if tenant context is set at the connection level and not reset, it could leak across requests.
- Mitigation: Set tenant context at transaction scope (`SET LOCAL`) or ensure it is reset after each request.

### 4.3. Raw SQL (pgPool)
- pgPool is used for raw queries (e.g., in bookingController.js lines 208, 262, 364).
- If tenant context is set at the session level, raw queries will automatically see it.
- Same pooling risk applies: need to ensure context is isolated per request.

### 4.4. Connection Pool
- The application uses a pgPool instance (imported as `pool` from `../config/db`).
- pgPool does not automatically reset session variables between connections unless configured to do so (e.g., using `pool.afterConnect` or similar).
- Risk: If a connection is reused and the tenant context is not reset, subsequent requests might see the wrong tenant.
- Mitigation: 
  - Use transaction-scoped context (`SET LOCAL`) so it automatically rolls back at the end of the transaction.
  - Or, explicitly reset the context after each query/request.

### 4.5. Authentication and Middleware
- The `authMiddleware` sets `req.user.id` and `req.user.role`.
- To integrate RLS, a middleware would need to:
  1. Determine the tenant ID for the current user (requires a mapping from user to tenant, which does not exist yet).
  2. Set the PostgreSQL context for the duration of the request (e.g., via a `SET LOCAL` inside a transaction wrapper, or by modifying the connection pool to set session variables on checkout).

### 4.6. Transactions
- The code uses both Sequelize transactions (`sequelize.transaction`) and raw transactions (explicit `BEGIN`/`COMMIT` via `pool.query`).
- For RLS to work, the tenant context must be set within the transaction.
- In Sequelize, one can use `sequelize.query('SET LOCAL app.tenant_id = ...', { transaction: t })` before other queries.
- In raw pgPool, one can include `SET LOCAL ...;` as part of the same transaction block.

### 4.7. Redis and Caching
- Redis is used for token blacklisting and possibly other caching.
- If caching stores data that is tenant-specific, cache keys must include tenant ID to avoid cross-tenant leakage.
- This is orthogonal to RLS but important for overall security.

### 4.8. Raw SQL Count and Locations
From a quick search (not exhaustive but indicative):
- bookingController.js: multiple raw queries (lines 86, 208, 262, 364, 491, 506, 609, 624, 689, 696)
- Other controllers likely contain raw queries as well.
- Total raw queries: **UNDETERMINED without full scan**, but clearly present in multiple places.

### 4.9. Risk of Context Leakage in Connection Pool
- **High risk** if using session-scoped SET without proper reset.
- **Low risk** if using transaction-scoped SET LOCAL and ensuring each request runs within a transaction that sets the context.
- The current code does not uniformly wrap all requests in transactions; some endpoints may execute queries outside of an explicit transaction.

### 4.10. Verdict on Feasibility
RLS is **technically feasible** with the current stack, but requires:
- Adding `tenant_id` columns to relevant tables.
- Enabling RLS and creating policies.
- Implementing a middleware or transaction wrapper that sets the tenant context (preferably transaction-scoped) for each request.
- Ensuring that all code paths (Sequelize, raw SQL, transactions) respect the context.
- Addressing connection pool safety (either by using SET LOCAL or by resetting session variables).

The effort is primarily in the data model changes and the context-setting mechanism, not in the database capability itself.

## 5. RECOMMENDATION
If the decision is to proceed with `tenant_id + RLS`, the implementation should:
- Use transaction-scoped context (`SET LOCAL app.tenant_id = ...`) to minimize leakage risk.
- Wrap all database operations (Sequelize and raw) in a transaction that sets the context, or use a connection pool hook that sets and resets session variables per connection checkout (with caution).
- Update the `authMiddleware` or add a new middleware to resolve tenant ID from user (requires a tenant mapping table).
- Ensure that raw queries and Sequelize queries are executed within the context-setting transaction.
