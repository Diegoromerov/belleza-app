# D002.1-MIGRATION-BLUEPRINT.md

## Conceptual Migration Blueprint for Workforce Management (D-002

**Note**: This is a conceptual migration blueprint only. No implementation is authorized at this stage.

### Overview
This blueprint outlines the conceptual sequence of migrations required to implement the workforce management extension as specified in D002.1-DATA-MODEL.md (adding `worker_type` column to `usuarios` table). The migrations are designed to be safe, idempotent where possible, and compatible with both clean and existing databases.

### Assumptions
- The database already has D-001 multi-tenancy implemented (Shared Schema + tenant_id + RLS).
- The `usuarios` table exists and has a `tenant_id` column (from D-001).
- The `tipo_rol` ENUM exists with values 'CLIENTE' and 'PRESTADOR'.
- We are adding a new ENUM `tipo_trabajador` and a column `worker_type` to the `usuarios` table.

### Migration Principles
1. **Idempotency**: Migrations should be able to run multiple times without causing errors.
2. **Backward Compatibility**: Do not break existing data or functionality.
3. **Safety**: Avoid destructive operations; prefer additive changes.
4. **Clear Rollback**: Each migration should have a clear rollback strategy.
5. **Data Safety**: When migrating existing data, ensure no loss or corruption.

### Proposed Migration Sequence

#### Migration 1: Create the `tipo_trabajador` ENUM type
- **Objective**: Add the new ENUM type for operational worker classification.
- **Preconditions**: 
  - Database connection is available.
  - The ENUM does not already exist (check if needed).
- **Changes**:
  ```sql
  DO $$
  BEGIN
      IF NOT EXISTS (SELECT 1 FROM pg_type WHERE typname = 'tipo_trabajador') THEN
          CREATE TYPE tipo_trabajador AS ENUM ('EMPLEADO', 'PRESTADOR_SERVICIO', 'ADMIN_SALON', 'OTRO');
      END IF;
  END $$;
  ```
- **Rollback**: 
  ```sql
  DROP TYPE IF EXISTS tipo_trabajador;
  ```
  **Note**: Rolling back an ENUM type is only safe if no columns depend on it. Since we will add a column that uses this type in the next migration, the rollback of this migration should only be done before the column is added, or the column must be dropped first.
- **Idempotency**: Yes, checks for existence before creating.
- **Risk**: Low. Only creates a type if it doesn't exist.

#### Migration 2: Add the `worker_type` column to `usuarios`
- **Objective**: Add the operational classification column to the usuarios table.
- **Preconditions**:
  - The `tipo_trabajador` ENUM exists (from migration 1).
  - The `usuarios` table exists and has a `tenant_id` column.
- **Changes**:
  ```sql
  ALTER TABLE usuarios ADD COLUMN IF NOT EXISTS worker_type tipo_trabajador;
  ```
  **Note**: The `IF NOT EXISTS` clause makes the column addition idempotent.
- **Rollback**:
  ```sql
  ALTER TABLE usuarios DROP COLUMN IF EXISTS worker_type;
  ```
- **Idempotency**: Yes, uses `IF NOT EXISTS` for addition and `IF EXISTS` for drop in rollback.
- **Risk**: Low. Adding a nullable column is generally safe.

#### Migration 3: (Optional) Populate default values for existing data
- **Objective**: Set initial values for `worker_type` based on existing `rol` column to provide a sensible default.
- **Preconditions**:
  - The `worker_type` column exists in `usuarios`.
  - The `rol` column exists in `usuarios`.
- **Changes**:
  ```sql
  UPDATE usuarios
  SET worker_type = 
      CASE 
          WHEN rol = 'PRESTADOR' THEN 'PRESTADOR_SERVICIO'
          WHEN rol = 'CLIENTE' THEN NULL -- or 'OTRO' if desired
          ELSE NULL
      END
  WHERE worker_type IS NULL;
  ```
  **Note**: This migration is optional because the salon may want to set the classification themselves. However, providing a default based on existing data can be helpful.
- **Rollback**: 
  ```sql
  -- This update is not easily rolled back without storing previous state.
  -- Since the column is nullable and we are only setting nulls to a value based on rol,
  -- we could set it back to NULL, but that would lose the intentional setting if any.
  -- Therefore, this migration is best made without a rollback, or we note that rollback is not provided.
  -- Alternatively, we can skip this migration and let the salon set the values manually.
  -- For the purpose of this blueprint, we mark it as optional and without rollback.
  ```
- **Idempotency**: Yes, because it only updates rows where `worker_type IS NULL`.
- **Risk**: Low to medium. It updates data, but only sets nulls to a deterministic value based on another column. However, if the salon has already started setting `worker_type` manually, this migration could overwrite those settings if they set it to NULL and then run the migration. To avoid, we can add a condition to only update if the column is NULL and the rol is PRESTADOR or CLIENTE, but if the salon set it to NULL intentionally, it would be overwritten. Given that, it might be safer to omit this migration and let the salon set the values via the UI or API after the column is added.

Given the risk of overwriting intentional NULLs, we recommend **omitting Migration 3** and instead instructing the salon to set the classification for existing users via the UI or API after the migration is applied.

### Final Migration Set (Recommended)
1. Migration 1: Create `tipo_trabajador` ENUM (idempotent)
2. Migration 2: Add `worker_type` column to `usuarios` (idempotent)

### Validation Steps
After running the migrations, verify:
- The `tipo_trabajador` type exists in `pg_type`.
- The `usuarios` table has a `worker_type` column of type `tipo_trabajador`.
- The column is nullable.
- Existing data in `usuarios` has `worker_type` set to NULL (unless Migration 3 is run).

### Compatibility Notes
- This migration does not change any existing columns or tables, so it should not break existing functionality.
- The `usuarios` table already has `tenant_id` (from D-001), so the new column will be automatically included in any tenant-scoped queries and RLS policies that cover the entire table.
- No changes to authentication, API, or frontend are required for the migration to run, but those layers would need updates to utilize the new field (separate from migration).

### Rollback Procedure (if needed)
To roll back the entire feature:
1. Run the rollback for Migration 2: `ALTER TABLE usuarios DROP COLUMN IF EXISTS worker_type;`
2. Run the rollback for Migration 1: `DROP TYPE IF EXISTS tipo_trabajador;`
**Note**: This assumes that no other dependencies have been added on the ENUM or column. If other migrations or features have been built on top, they must be rolled back first.
