## 5. MULTI-TENANCY
### Cómo se comportaría el sistema con TENANT A, TENANT B, TENANT C

Con la arquitectura recomendada (Shared Schema + tenant_id + RLS):
- Cada tenant tendría su propio identificador (tenant_id) en las tablas de negocio
- Los datos de TENANT A, TENANT B y TENANT C estarían lógicamente aislados mediante el valor de tenant_id
- Row Level Security en PostgreSQL enforcaría que las consultas solo puedan acceder a datos con el tenant_id correspondiente al contexto establecido
- Sin tenant_id o RLS, existirían riesgos de acceso horizontal entre tenants mediante omisión de filtros en consultas

**Datos que deben quedar aislados:**
- Usuarios (pertenencia a tenant)
- Profesionales (pertenencia a tenant)
- Clientes (pertenencia a tenant)
- Servicios (pertenencia a tenant)
- Reservas (pertenencia a tenant)
- Pagos/Transacciones (pertenencia a tenant)
- Configuración específica del tenant

## 8. PROFESSIONAL
### ¿PROFESSIONAL ES USER?

**CURRENT EVIDENCE:**
- La tabla perfiles_prestador está en relación uno-a-uno con usuarios (id como PK y FK a usuarios.id). Esto implica que cada usuario puede tener como máximo un perfil de prestador y cada perfil de prestador pertenece a exactamente un usuario. (D001.3-DIRECTOR-EVIDENCE-REVIEW.md, sección "D-001 RECOMMENDED PROFESSIONAL MODEL", líneas 74-76)

**CONCLUSION:**
Dependerá de la decisión específica de modelado:
- Opción 1 (profesional como entidad independiente): El profesional (perfiles_prestador) pertenece al tenant mediante una relación muchos-a-uno (un tenant puede tener muchos profesionales).
- Opción 2 (profesional como usuario): El profesional es un usuario que pertenece al tenant (relación muchos-a-uno desde usuarios a tenant). (D001.3-DIRECTOR-EVIDENCE-REVIEW.md, sección "D-001 RECOMMENDED PROFESSIONAL MODEL", líneas 77-81)
