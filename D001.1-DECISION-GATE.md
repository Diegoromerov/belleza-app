## 4. CURRENT DOMAIN MODEL (EVIDENCE)
- No existe tabla `tenants`, `salones`, `businesses` ni columnas `tenant_id`, `organization_id`, `business_id` o `salon_id` en ninguna tabla.
- La tabla `usuarios` almacena tanto clientes como profesionales (diferenciados por `rol`: 'CLIENTE' o 'PRESTADOR').
- La tabla `perfiles_prestador` está en relación uno-a-uno con `usuarios` (id como PK y FK a usuarios.id).
- No hay forma de representar un salón con múltiples profesionales o múltiples usuarios (dueño, admin, staff) porque cada usuario tiene como máximo un perfil de prestador y viceversa.

## 5. TENANT ENTITY ANALYSIS
- **¿Qué entidad representa actualmente al negocio/salón?**  
  Ninguna entidad explícita representa un negocio/salón capaz de agrupar múltiples usuarios o profesionales.  
  El modelo actual asume que cada usuario con rol `PRESTADOR` es equivalente a un salón/profesional independiente (uno-a-uno entre usuario y perfil de prestador).  
  **EVIDENCIA**:  
  - `backend/schema.sql` líneas 62-80: `perfiles_prestador.id INTEGER PRIMARY KEY REFERENCES usuarios(id) ON DELETE CASCADE` (uno-a-uno).  
  - No hay tabla ni columna que agrupe múltiples `usuarios` o `perfiles_prestador` bajo un mismo identificador de negocio.

- **¿Es actualmente `usuario = salón`?**  
  **UNDETERMINED** sin definición clara de "salon".  
  - Si por salón se entiende un profesional independiente, entonces sí: cada usuario PRESTADOR con su perfil de prestador representa un salón de una persona.  
  - Si por salón se entiende un negocio que puede tener múltiples empleados, entonces no: no hay forma de representar múltiples profesionales bajo un mismo salón.  
  - **EVIDENCIA**:  
    - La relación uno-a-uno entre `usuarios` y `perfiles_prestador` impide que un usuario tenga múltiples perfiles de prestador o que un perfil de prestador pertenezca a múltiples usuarios.  
    - No hay tabla de salón ni de negocio que permita agrupar.

## 6. USER RELATIONSHIP
- En el modelo actual, un usuario no tiene una relación explícita con un salón más allá de su propio rol y perfil (si es PRESTADOR).  
- Para soportar el concepto de tenant como salón, se requeriría introducir una entidad `tenants` y vincular los usuarios a ella (por ejemplo, mediante una columna `tenant_id` en `usuarios` o una tabla de asociación).  
- **EVIDENCIA**:  
  - No existe columna `tenant_id` en `usuarios` (ver schema.sql líneas 43-59).  
  - No existe tabla `tenants`.

## 7. PROFESSIONAL RELATIONSHIP
- En el modelo actual, un profesional (representado por `perfiles_prestador`) está fuertemente acoplado a un usuario (uno-a-uno).  
- Para que un profesional pertenezca a un salón (tenant) que no sea él mismo, se requeriría desacoplar `perfiles_prestador` de `usuarios` o crear una relación muchos-a-uno entre profesionales y tenants.  
- **EVIDENCIA**:  
  - `backend/schema.sql` líneas 62-80: `perfiles_prestador.id` es PK y FK a `usuarios.id` con `ON DELETE CASCADE`.  
  - Esto implica que eliminar al usuario elimina el perfil de prestador, y que cada usuario puede tener como máximo un perfil de prestador.

## 8. MULTI-BRANCH ANALYSIS
- No se encontró entidad `sucursal` o `branch` en el esquema.  
- El modelo actual asume un único lugar de operación por profesional (ubicacion en `perfiles_prestador`).  
- **Comparar `tenant_id` únicamente vs. `tenant_id + branch_id`**:  
  - Dado que no hay concepto de salón ni de sucursal, la discusión es prematura sin un concepto definido de salón o sucursal.  
  - Si en el futuro se quisiera soportar múltiples sucursales bajo un mismo negocio, se necesitaría una entidad `sucursal` vinculada al salón y luego decidir si el tenant es el salón o la sucursal.  
  - Para el análisis actual, se asume que el tenant representa el salón (negocio) y que cada salón tiene una ubicación (o que la ubicación es un atributo del salón).  
  - **EVIDENCIA**:  
    - No se encontró ninguna referencia a `branch`, `sucursal` o `sede` en el código inspeccionado (excepto en skills y node_modules, que no son parte del dominio de GlowApp).

## 10. RLS FEASIBILITY (EVIDENCE)
Ver documento `/c/beauty-app/D001.1-RLS-FEASIBILITY.md` para detalles.  
Resumen:  
- RLS es técnicamente factible con el stack actual (PostgreSQL 15+, Sequelize, pgPool, Redis).  
- Requiere:  
  1. Añadir columna `tenant_id` a las tablas relevantes.  
  2. Habilitar RLS y crear políticas.  
  3. Implementar un mecanismo para establecer el contexto de tenant por transacción (preferiblemente `SET LOCAL`) para evitar fugas en el pool de conexiones.  
  4. Asegurar que todas las consultas (Sequelize y crudas) se ejecuten dentro de ese contexto.  
- Riesgos:  
  - Fuga de contexto en el pool de conexiones si se usan variables de sesión sin reset.  
  - Complejidad en envolver todas las operaciones en transacciones que establezcan el contexto.  
- **Conclusión**: Factible con esfuerzo medio-alto debido a cambios en el modelo de datos y en la capa de acceso a datos.

## 11. CONNECTION POOL ANALYSIS (EVIDENCE)
Ver documento `/c/beauty-app/D001.1-CONNECTION-CONTEXT-ANALYSIS.md` para detalles.  
Resumen:  
- El pool de conexiones (`pgPool`) reutiliza conexiones entre requests.  
- Si se usa `SET app.tenant_id = ...;` (nivel de sesión) sin reset, hay riesgo de que un request herede el tenant de un request anterior.  
- Se recomienda usar `SET LOCAL app.tenant_id = ...;` (nivel de transacción) para que el contexto se revierta automáticamente al final de la transacción.  
- Esto requiere que cada request que accese a la base de datos lo haga dentro de una transacción que establezca el contexto.

## 12. SEQUELIZE ANALYSIS
- Sequelize se usa para operaciones de ORM (por ejemplo, `Booking.create`, `Service.findAll`).  
- No tiene soporte integrado para RLS, pero puede funcionar si el contexto de tenant se establece en la conexión/transacción.  
- Riesgo similar al de pgPool: si el contexto se establece a nivel de conexión y no se reset, puede haber fuga.  
- Se puede usar un namespace de CLS (Continuation Local Storage) o pasar explícitamente el objeto de transacción para asegurar que las operaciones usen la misma transacción que establece el contexto.

## 13. RAW SQL ANALYSIS
- Se encuentran consultas crudas en múltiples controladores (por ejemplo, bookingController.js líneas 86, 208, 262, 364, 491, 506, 609, 624, 689, 696).  
- Total de consultas crudas: **SIN DETERMINAR exactamente sin un escaneo completo**, pero claramente presentes en varios lugares.  
- Todas las consultas crudas deben ser modificadas para incluir el filtro de `tenant_id` si se opta por Shared Schema + tenant_id, o deben ejecutarse dentro de un contexto que establezca el tenant si se usa RLS.

## 14. AUTHENTICATION ANALYSIS
- El middleware `authMiddleware` (backend/src/middleware/auth.js) verifica el JWT y establece `req.user` con `id`, `email`, `role` y `token`.  
- No incluye información de tenant porque no existe un mapeo de usuario a tenant en el modelo actual.  
- Para establecer el contexto de tenant, se requeriría un paso adicional que resuelva el tenant ID a partir de `req.user.id` (requiriendo una tabla de mapeo o asumiendo que el usuario es el tenant).

## 15. AUTHORIZATION ANALYSIS
- La autorización actual se basa en el rol (`req.user.role`) y en la propiedad explícita en las consultas (por ejemplo, `WHERE provider_id = $1` con `$1 = req.user.id`).  
- No hay verificaciones de pertenencia a un tenant más allá del `user_id`.  
- Para autorización a nivel de tenant, se requeriría verificar que el usuario pertenece al tenant en cuestión (requiriendo una tabla de mapeo de usuario a tenant).

## 16. SECURITY MODEL
- **Modelo actual**:  
  USER (autenticado) → AUTORIZACIÓN (por rol y ownership explícito) → RECURSO  
  No existe una capa explícita de TENANT MEMBERSHIP.  
- **Modelo requerido para multi-tenancy**:  
  USER → AUTENTICACIÓN → MEMBRESÍA EN TENANT → AUTORIZACIÓN (rol y ownership dentro del tenant) → RECURSO (con filtrado por tenant)  
  Además, se puede añadir RLS como última barrera en la base de datos.

## 17. RAG ANALYSIS
- La tabla `beauty_knowledge_embeddings` (schema.sql líneas 282-291) no tiene columna `tenant_id`.  
- Su contenido parece ser conocimiento general de belleza (posiblemente global).  
- **¿Existe RAG?** Sí, la tabla sugiere un sistema de embeddings para búsqueda semántica.  
- **¿Tiene metadata tenant?** No.  
- **¿Existe riesgo de cross-tenant retrieval?**  
  - Si el conocimiento es global y compartido, entonces el riesgo es bajo.  
  - Si el conocimiento es específico por salón (por ejemplo, tratamientos propios, promociones), entonces existe riesgo de cross-tenant retrieval si no se filtra por tenant.  
  - **EVIDENCIA**: No se encontró lógica de filtrado en los servicios de IA inspeccionados (por ejemplo, `geminiService.js` no fue inspeccionado en detalle, pero se asume actualmente que el conocimiento es global).  
  - **CONCLUSIÓN**: UNDETERMINED sin conocer el uso previsto del RAG. Se requiere decidir si el conocimiento es global o tenant-específico.

## 18. RECOMENDADO DOMINIO DE TENANT
Basado en la evidencia y el objetivo de soportar un SaaS B2B para salones de belleza donde un salón puede tener múltiples usuarios (dueño, admin, staff) y múltiples profesionales:  
- **TENANT** debe representar el negocio/salon que contrata el servicio de GlowApp.  
- Se requiere introducir una nueva entidad `tenants` (o `salones`) con al menos: `id`, `nombre`, `dirección`, `información de contacto`.  
- Relaciones:  
  - Un tenant tiene muchos usuarios (a través de una columna `tenant_id` en `usuarios` o una tabla de asociación).  
  - Un tenant tiene muchos profesionales (si el profesional se modela como entidad independiente vinculada al tenant, o si el profesional es un usuario entonces a través del usuario).  
  - Un tenant tiene muchos servicios, reservas, pagos, etc. (a través de `tenant_id` en esas tablas o derivado de las relaciones existentes).  
- Para minimizar el cambio, se puede comenzar modelando que cada usuario pertenece a un solo tenant (muchos usuarios por tenant, pero cada usuario en un solo tenant) y que cada profesional es un usuario (por lo tanto, pertenece al mismo tenant que su usuario).  
  Esto requeriría:  
  - Añadir columna `tenant_id` a `usuarios`.  
  - Eliminar la restricción uno-a-uno entre `usuarios` y `perfiles_prestador` si se quiere permitir que un profesional tenga múltiples usuarios (no recomendado inicialmente) o mantenerla si se acepta que cada profesional tiene su propia cuenta de usuario y por lo tanto su propio tenant (lo cual no apoya el escenario de múltiples profesionales bajo un mismo salón).  
  - Alternativamente, se puede desacoplar `perfiles_prestador` de `usuarios` y vincularlo directamente al tenant, permitiendo que un tenant tenga múltiples profesionales y que un profesional pertenezca a un solo tenant (o múltiples si se permite muchos-a-uno).  
  Dado el tiempo y el alcance, se recomienda una aproximación inicial donde:  
  - El tenant es el salón.  
  - Cada usuario pertenece a exactamente un tenant (muchos usuarios por tenant).  
  - Cada profesional es un usuario (por lo tanto, pertenece al tenant de su usuario).  
  Esto apoya el escenario de un salón con múltiples usuarios (dueño, admin, staff) pero no directamente el escenario de un salón con múltiples profesionales a menos que cada profesional tenga su propia cuenta de usuario (lo cual es aceptable si el profesional es considerado un usuario del sistema).  
  Si se quiere que un profesional pueda pertenecer a un salón sin ser un usuario del sistema (por ejemplo, un empleado que solo ingresa servicios pero no tiene acceso al sistema), entonces se requeriría modelar al profesional como entidad independiente vinculada al tenant.

## 19. RECOMENDADO MODELO DE SEGURIDAD
- **Primera línea de defensa**: Filtrado explícito por `tenant_id` en todas las consultas (Sequelize y crudas).  
- **Segunda línea de defensa (opcional pero recomendada)**: RLS en PostgreSQL como última barrera para prevenir acceso accidental debido a errores en el filtrado de aplicación.  
- Mecanismo de contexto de tenant:  
  - Usar `SET LOCAL app.tenant_id = ...;` al inicio de cada transacción que acceda a la base de datos.  
  - Establecer el valor de `app.tenant_id` a partir del tenant ID del usuario autenticado (requiriendo un mapeo de usuario a tenant).  
  - Esto requiere envolver las operaciones de base de datos de cada request en una transacción que establezca el contexto, o usar un middleware de transacción que lo haga automáticamente.

## 20. RIESGOS
- **Técnico**: Errores en la migración de datos (por ejemplo, al poblar `tenant_id` para datos existentes) podrían provocar pérdida o corrupción de información.  
- **Operacional**: Downtime durante la aplicación de migraciones si no se hace de forma adecuada (por ejemplo, usando bloqueos exclusivos en tablas grandes).  
- **Legal**: Incumplimiento de la Ley 1581 de 2012 (protección de datos personales) si se determina que GlowApp actúa como encargado o responsable de los datos de los salones y los datos de distintos tenants no están adecuadamente aislados.  
- **Seguridad**: Fugas de datos entre tenants si la implementación de RLS o el filtrado explícito es defectuoso.  
- **Operacional**: Complejidad en la definición y aplicación correcta de políticas RLS y en el manejo del contexto de tenant en el pool de conexiones.

## 21. BLOQUEADORES
- Falta de decisión jurídica sobre el rol de GlowApp (encargado vs responsable) que afecta la necesidad y el alcance del aislamiento de datos.  
- Necesidad de definir claramente qué constituye un tenant (¿el salón, el profesional, o el usuario?) antes de implementar la columna `tenant_id`.  
- Disponibilidad de recursos para realizar la migración de datos y probar las políticas RLS en un entorno de staging antes de producción.  
- Necesidad de decidir si el conocimiento en RAG es global o tenant-específico, lo que afecta si la tabla `beauty_knowledge_embeddings` requiere `tenant_id`.
