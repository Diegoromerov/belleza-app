# F7.008-D — Design / Decision Preparation

## Objective
Prepare detailed design decisions and implementation plan for addressing the gaps identified in F7.008-B and evaluated in F7.008-C for F7.008 (Gobernanza de Producción, Verificación Frontend/Backend y Cierre Operativo de Resiliencia). This includes:
- Defining how to add `traceId` propagation to YouCam and Gemini client calls.
- Defining how to add `fallback` utilization in `executeWithResilience` calls.
- Deciding on timeout alignment strategy (resilience policy vs client-overridden timeout).
- Creating an implementation plan with clear activities, dependencies, and effort estimates.

## Design Decisions

### 1. TraceId Propagation
- **Decision**: Modify the client method signatures to accept an optional `traceId` parameter, and pass it to `executeWithResilience` when available. The traceId will be obtained from the request context in the service layer.
- **Rationale**: 
  - The traceId middleware already generates a traceId per request and attaches it to `req.traceId`.
  - Passing traceId to the resilience service enables correlation of logs across services.
  - Making the parameter optional ensures backward compatibility with internal calls (e.g., from background jobs) where traceId may not be available.
- **Implementation**:
  - Change `analyzeFace(image)` to `analyzeFace(image, traceId?)` in YouCamClient.
  - Change `analyzeHands(image)` to `analyzeHands(image, traceId?)` and `generateRecommendation(faceScores, handsDiagnosis)` to `generateRecommendation(faceScores, handsDiagnosis, traceId?)` in GeminiClient.
  - In each client method, when calling `executeWithResilience`, include `{ traceId }` in the options object if `traceId` is provided.
  - Update all callers of these methods to pass the traceId from the request object (or `undefined` if not available).
  - For internal calls (if any) that do not have a traceId, pass `undefined`.

### 2. Fallback Utilization
- **Decision**: 
  - For YouCam client: Implement fallback functions for each of the four steps in `analyzeFace` that return a sensible default score set, and pass them as the `fallback` option in the respective `executeWithResilience` calls.
  - For Gemini client: Use the existing fallback functions (`getFallbackHandsDiagnosis` and `getFallbackRecommendation`) by passing them as the `fallback` option in the respective `executeWithResilience` calls.
- **Rationale**: 
  - This leverages the resilience service's built-in fallback mechanism, reducing code duplication and ensuring consistent fallback behavior.
  - The fallback functions will be called when all retries are exhausted or when the circuit breaker is open.
- **Implementation**:
  - **YouCamClient**:
    - Create `_requestUploadSlotFallback`, `_uploadToS3Fallback`, `_createAnalysisTaskFallback`, `_pollTaskResultFallback` functions that return appropriate default values (mock fileId, uploadUrl, etc., or resolve immediately for upload step).
    - In each `executeWithResilience` call, add `fallback: this._<step>Fallback`.
    - Remove or keep the existing try-catch fallback as a last resort (but note that the resilience fallback will be called first on retry exhaustion or circuit open).
  - **GeminiClient**:
    - In the `analyzeHands` call to `executeWithResilience`, add `fallback: this.getFallbackHandsDiagnosis`.
    - In the `generateRecommendation` call to `executeWithResilience`, add `fallback: this.getFallbackRecommendation`.
    - Keep the existing try-catch blocks as a last resort (or remove them if we want to rely solely on the resilience fallback; but we can keep them for errors not covered by resilience, such as parsing errors).

### 3. Timeout Consistency
- **Decision**: Keep the current timeout settings as follows:
  - Resilience policy timeout: 5000 ms (per attempt).
  - YouCam and Gemini axios timeout: 15000 ms (per request).
  - However, note that the clients currently override the resilience timeout to 15000 ms (by passing `timeout: this.timeout` where `this.timeout` is 15000). We will change this to **not** override the resilience timeout, allowing the policy default of 5000 ms to be used for the resilience timeout, while keeping the axios timeout at 15000 ms.
- **Rationale**:
  - The resilience timeout of 5000 ms is intended to handle transient network issues and retry quickly.
  - The axios timeout of 15000 ms allows for slower but successful responses from the external APIs.
  - This configuration means that if an axios call takes between 5000 and 15000 ms, the resilience layer will timeout and retry, but the retry may succeed if the subsequent attempt completes within 5000 ms or if the axios call eventually finishes within its own timeout.
  - To prevent excessive retries, we rely on the retry limit (3 attempts) and the exponential backoff.
  - Based on historical API response times (to be verified in monitoring), the majority of calls complete within 5000 ms, making this a reasonable balance.
  - This change aligns the resilience timeout with the policy default, while preserving the axios timeout for the HTTP request.
- **Implementation**:
  - In YouCamClient and GeminiClient, remove the `timeout: this.timeout` option from the `executeWithResilience` calls (or set it to `undefined` so that the default policy timeout is used).
  - Keep the axios timeout as `timeout: this.timeout` (15000 ms) in the axios config.
  - This way, the resilience layer will use the default policy timeout of 5000 ms per attempt, while the HTTP request will timeout after 15000 ms.

### 4. Additional Considerations
- **Backward Compatibility**: 
  - The changes to client method signatures (adding optional `traceId`) are backward compatible if we make the parameter optional and callers can pass `undefined`.
  - The fallback addition does not break existing functionality; it only adds a fallback path.
  - The timeout change (using policy default for resilience) may affect behavior: retries will happen sooner (after 5000 ms) rather than waiting for the axios timeout (15000 ms). This is considered an improvement and is acceptable.
- **Effort Estimate**:
  - TraceId propagation: 2 hours (YouCam) + 2 hours (Gemini) = 4 hours
  - Fallback utilization: 1.5 hours (YouCam) + 0.5 hours (Gemini) = 2 hours
  - Timeout consistency: 0.5 hours (YouCam) + 0.5 hours (Gemini) = 1 hour
  - Total Estimated Effort: 7 hours

## Dependencies
- None new; all changes use existing resilience service, traceId middleware, and axios.

## Risks and Mitigations
- **Risk**: Incorrect fallback values for YouCam leading to inaccurate biometric scores.
  - **Mitigation**: Use mid-range default values and log when fallback is used.
- **Risk**: TraceId propagation requires changes to many callers.
  - **Mitigation**: Start with the main service layer callers; there are likely only a few entry points.
- **Risk**: Timeout change may cause more retries in case of slow APIs.
  - **Mitigation**: Monitor API response times; if retries become excessive, consider adjusting.
