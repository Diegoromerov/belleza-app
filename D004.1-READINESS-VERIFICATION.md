# D004.1-READINESS-VERIFICATION.md

## Executive Summary

This document presents the findings of the readiness verification for D-004 (Estrategia de retención de datos para RAG y conocimiento organizacional). The verification was conducted in a read-only manner, inspecting the current state of the GlowApp backend, database, and codebase without making any modifications.

Key findings:
- The `beauty_knowledge_embeddings` table, which is central to the RAG system, does **not exist** in the database.
- The migration file `031_aura_pgvector_and_knowledge_table.sql` exists and would create this table, but it has not been executed.
- The RAG service (`src/services/ragService.js`) references the `beauty_knowledge_embeddings` table in its queries, indicating that the service expects the table to exist.
- No retention-related tables (`retention_policies`, `legal_holds`, `retention_audit_log`) exist in the database.
- The `tenants` table exists and is populated, indicating that the multi-tenancy foundation (D-001) is present.
- The `usuarios` and `servicios` tables exist and have `tenant_id` columns, consistent with D-001 implementation.
- There is no evidence of existing retention mechanisms, legal hold, or audit logging for knowledge data.
- The RAG service does not currently reference `tenant_id` in its queries, indicating a global-only knowledge model (as intended by D-001 for the RAG component).
- No scheduled jobs, cron jobs, or background processes related to retention or data lifecycle were found in the codebase.

Given that the core RAG table is missing, the system currently cannot store or retrieve knowledge via the RAG service. This represents a significant gap that must be addressed before implementing any retention strategy.

## Current Tenant Isolation

- **D-001 status**: IMPLEMENTED, VALIDATED, CLOSED (evidence: `tenants` table exists, `tenant_id` columns in core tables, migration files present)
- **RAG service interaction with tenant_id**:
  - The RAG service (`ragService.js`) does **not** reference `tenant_id` in its queries.
  - The service performs global-only queries (no tenant filtering).
  - This is consistent with the decision in D-001 to leave `beauty_knowledge_embeddings` as GLOBAL (tenant_id = NULL).
- **Row Level Security (RLS)**: 
  - Migration 058 (`enable_rls_policies.sql`) exists, indicating RLS was enabled for certain tables.
  - However, no RLS policies are applied to `beauty_knowledge_embeddings` (table missing, but if it existed, migration 031 does not include RLS).
  - The RAG service does not appear to set `app.tenant_id` or use RLS for its queries.
- **Knowledge scoping**: 
  - Currently, all knowledge (if the table existed) would be global (`tenant_id = NULL` by default, as no tenant_id column is present in the table definition).
  - There is no mechanism to store tenant-scoped knowledge in the RAG index.
- **Risk of cross-tenant leakage**: 
  - If tenant-scoped knowledge were somehow inserted into the RAG table (without a `tenant_id` column to scope it), it would be accessible to all tenants.
  - However, since the table lacks a `tenant_id` column, there is no way to distinguish tenant-scoped from global knowledge at the storage level.
  - The current design is global-only, so leakage is not applicable; however, the inability to store tenant-scoped knowledge is a limitation if such a requirement arises.

## Global Knowledge Analysis

- **Evidence of GLOBAL knowledge**: 
  - The RAG service queries the `beauty_knowledge_embeddings` table without any tenant filtering.
  - Migration 031 does not include a `tenant_id` column.
  - The D-001 implementation left the RAG table as global (as noted in the D-001 implementation report: "`beauty_knowledge_embeddings` dejado como GLOBAL").
  - The service uses metadata filters (e.g., `skin_type`, `category`, `ingredients`, `contraindications`) that are not tenant-scoped.
- **Current state**: 
  - Since the table does not exist, there is no actual knowledge stored.
  - The design intent is for the RAG to be global, shared across all tenants.
- **Implications for D-004**: 
  - Any retention strategy must preserve the global nature of the existing knowledge (if any) unless a decision is made to reclassify it.
  - The hybrid model (GLOBAL + TENANT-SCOPED) would require adding a `tenant_id` column to allow both global (NULL) and tenant-scoped (non-NULL) knowledge.

## Tenant-Scoped Knowledge Analysis

- **Evidence of TENANT-SCOPED knowledge**: 
  - ❌ NO EVIDENCE in the current system.
  - The `beauty_knowledge_embeddings` table (as defined in migration 031) lacks a `tenant_id` column.
  - The RAG service does not filter by `tenant_id`.
  - No ingestion scripts or APIs were observed that assign `tenant_id` to knowledge.
- **Current state**: 
  - Tenant-scoped knowledge is not supported in the RAG system.
  - If tenants need to store private knowledge, it is not currently possible via the RAG.
- **Implications for D-004**: 
  - To support tenant-scoped knowledge, the schema must be altered to add a `tenant_id` column (nullable) to `beauty_knowledge_embeddings`.
  - The RAG service must be modified to accept a tenant context and include it in queries (with appropriate logic for global vs. tenant-scoped retrieval).
  - Proper isolation must be enforced at the query level (and optionally via RLS).

## Security Risks

1. **Cross-tenant data leakage**: If tenant-scoped knowledge is introduced without proper query scoping or storage isolation, it could be accessible to unauthorized tenants.
2. **Data persistence beyond retention**: Lack of retention mechanisms leads to indefinite storage, increasing the attack surface and violating data minimization principles.
3. **Inability to delete data**: Without deletion mechanisms, the system cannot comply with user deletion requests (right to be forgotten) or legal orders.
4. **Lack of audit trail**: Without logging, it is impossible to detect or investigate unauthorized access or modification of knowledge data.
5. **Exposure of sensitive data**: If personal data is inadvertently stored in the RAG index, there is no mechanism to redact or delete it.
6. **Ingestion without validation**: Knowledge could be ingested without proper validation of its scoping, leading to misclassification.

## Data Lifecycle Risks

1. **Stale knowledge**: Without retirement or update mechanisms, knowledge becomes obsolete, leading to inaccurate RAG outputs.
2. **Storage bloat**: Indefinite retention increases storage costs and may degrade query performance over time.
3. **Compliance violations**: Failure to retain or delete data as required by law could result in fines or legal action.
4. **Operational inefficiency**: Manual knowledge management does not scale and is error-prone.
5. **Backup and restore complexity**: Without clear lifecycle policies, backup strategies may be over- or under-inclusive.
6. **Knowledge contamination**: Tenant-specific knowledge could accidentally be marked as global, leading to unwanted sharing.

## Implementation Prerequisites

Before any implementation of D-004 can begin, the following prerequisites must be met:

1. **Existence of the RAG table**: The `beauty_knowledge_embeddings` table must exist (by running migration 031 or equivalent). Without this table, the RAG service cannot function, and there is no data to retain.
2. **Legal review**: A professional legal review must be conducted to determine retention periods for different knowledge types under Ley 1581 art. 8, SIC Circ. 022/2023, and other applicable regulations.
3. **Decision on knowledge scoping**: The Director must decide whether the RAG system will remain global-only or support a hybrid model (global + tenant-scoped). This decision impacts schema changes and service modifications.
4. **Resource allocation**: Implementation will require development effort for schema changes, service modifications, policy engine, cron job, and testing.
5. **Testing environment**: A safe environment (e.g., staging) must be available to test changes before production deployment.
