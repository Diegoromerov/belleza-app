# D002.1-WORKFORCE-IMPLEMENTATION-SPEC.md

## Technical Specification for Workforce Management (D-002)

**Status**: Specification only – no implementation authorized.

**Purpose**: Define the technical approach to allow salons to manage workforce members (employees and service providers) as operational categories within the GlowApp SaaS, while strictly maintaining that GlowApp is a technology platform only and does not assume any labor obligations.

### Core Principles

1. **ROLE ≠ RELACIÓN JURÍDICA**: Operational roles in GlowApp (EMPLOYEE, SERVICE_PROVIDER) are strictly for internal salon administration and do not determine or imply any legal relationship between GlowApp and the worker.
2. **Tenant Isolation**: All workforce data must be isolated by `tenant_id` and subject to Row-Level Security (RLS) where appropriate.
3. **Data Minimization**: Store only the data strictly necessary for the SaaS to operate; avoid collecting unnecessary personal or labor-related data.
4. **Salon Control**: The salon (tenant) retains full control over worker classification, data, and operational decisions. GlowApp provides only the tools.
5. **No Payment Obligations**: GlowApp does not process payroll, salaries, or any payments as an obligor. Any payout functionality is strictly facilitative (e.g., via payment gateways) and under salon direction.

### Overview

The current system distinguishes users as `CLIENTE` or `PRESTADOR` via the `usuarios.rol` column (tipo_rol ENUM). Service providers have a profile in `perfiles_prestador`. 

To support workforce management without converting GlowApp into an employer, we propose extending the existing model with an **operational category** (e.g., `worker_type`) that allows the salon to classify workforce members as `EMPLOYEE` or `SERVICE_PROVIDER` (or other salon-defined categories). This classification is purely operational and stored alongside the user or profile.

### Proposed Approach

Option A: Extend `usuarios` or `perfiles_prestador` with a `worker_type` column.
Option B: Create a new `workforce_members` table linked to `usuarios` and `tenant_id`.

Given the desire to minimize impact and reuse existing structures, **Option A** is recommended: add a `worker_type` column to the `usuarios` table (or to `perfiles_prestador` if the classification applies only to service providers). However, since the salon may want to classify both users that are prestadores and potentially other users (e.g., salon admins that are not prestadores), placing it on `usuarios` is more flexible.

#### Recommended Changes

- Add a new ENUM type `tipo_trabajador` with values: `EMPLEADO`, `PRESTADOR_SERVICIO`, `ADMIN_SALON`, `OTRO` (or similar, as defined by the salon).
- Add a column `worker_type tipo_trabajador` to the `usuarios` table, nullable, with a default that reflects existing data (e.g., for existing prestador users, set to `PRESTADOR_SERVICIO`; for client users, `NULL` or `OTRO`).
- Ensure the column is included in the tenant context and RLS policies (i.e., tables with `tenant_id` must have RLS if they contain sensitive workforce data).
- No changes to authentication or core booking/service flows unless the salon chooses to use the classification for filtering (e.g., only show SERVICE_PROVIDER in service assignment).

### Assumptions

- The salon will define what `EMPLEADO` and `PRESTADOR_SERVICIO` mean for their internal operations; GlowApp does not validate or interpret these classifications legally.
- Existing data can be migrated by setting `worker_type` based on the existing `rol` column (e.g., if `rol = PRESTADOR` then `worker_type = PRESTADOR_SERVICIO`; if `rol = CLIENTE` then `worker_type = NULL` or a default like `OTRO`).
- The `tipo_rol` column (CLIENTE/PRESTADOR) remains for distinguishing login capabilities (e.g., clients book appointments, prestadores receive bookings). The `worker_type` is an additional operational tag.

### Impact Summary

- **Database**: Add ENUM and column; ensure `tenant_id` exists on `usuarios` (already from D-001).
- **Backend**: Minimal changes; mainly reading/writing the new column.
- **API**: If exposing workforce data, add field to user/profile endpoints.
- **UI**: Conceptual screens for managing workforce classification (not implemented now).
- **Security**: Ensure RLS policies on `usuarios` (if extended to store sensitive data) or on new tables.

### Next Steps (if implementation authorized)

1. Create migration scripts to add ENUM and column.
2. Update backend models and services to handle the new field.
3. Update API serializations if needed.
4. Update frontend views (if any) to show/use the field.
5. Ensure RLS policies are updated for any new tables or extended tables.
6. Conduct security and legal review.
