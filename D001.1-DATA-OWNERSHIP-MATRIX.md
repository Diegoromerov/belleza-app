# DATA OWNERSHIP AND TENANCY MATRIX FOR GLOWAPP

Based on inspection of the current codebase (schema.sql, controllers, models, etc.), the following matrix analyzes the conceptual ownership and tenancy relationships for core entities. 

**Methodology**: 
- **Propietario conceptual**: Determined from the real-world meaning of the entity as inferred from code comments, field names, and relationships.
- **Tenant directo**: Determined by the presence of a direct foreign key to a tenant table or a `tenant_id` column in the entity's table. Since no tenant table or `tenant_id` column exists in the current schema, this is determinable as absent.
- **Tenant derivado**: Determined by whether the entity can logically inherit a tenant assignment through existing relationships (e.g., if a Service belongs to a Professional, and the Professional belongs to a Tenant, then the Service's tenant is derivable). Given the absence of a tenant concept in the current code, no such derivation path exists without introducing new tenant entities or columns.

| Entidad      | Propietario conceptual                                                                 | Tenant directo                                     | Tenant derivado                                     |
|--------------|--------------------------------------------------------------------------------------|----------------------------------------------------|-----------------------------------------------------|
| User         | The person (human) represented by the user account (either a client or a professional). | **NO DIRECT TENANT COLUMN EXISTS** – No `tenant_id` or tenant table reference in `usuarios` table. | **CANNOT DERIVE TENANT WITHOUT TENANT CONCEPT** – No existing relationship to a tenant entity; derivation would require introducing a tenant concept (e.g., linking `usuarios` to a `tenants` table). |
| Professional | The professional (service provider) represented by the combination of a `usuarios` row (with `rol = 'PRESTADOR'`) and its corresponding `perfiles_prestador` row. | **NO DIRECT TENANT COLUMN EXISTS** – No `tenant_id` or tenant table reference in `perfiles_prestador` or `usuarios` tables. | **CANNOT DERIVE TENANT WITHOUT TENANT CONCEPT** – The `perfiles_prestador.business_name` field is a descriptive string, not a foreign key to a tenant table. Thus, no derivable tenant path exists without introducing a tenant entity and linking `perfiles_prestador` to it. |
| Client       | The client (service recipient) represented by a `usuarios` row (with `rol = 'CLIENTE'`). | **NO DIRECT TENANT COLUMN EXISTS** – No `tenant_id` or tenant table reference in `usuarios` for client users. | **CANNOT DERIVE TENANT WITHOUT TENANT CONCEPT** – Client users lack a `perfiles_prestador` row (since `rol` is mutually exclusive), so there is no relationship to a business or professional profile from which to derive a tenant. |
| Service      | The service offering, owned by the professional (or their business) that provides it. | **NO DIRECT TENANT COLUMN EXISTS** – No `tenant_id` or tenant table reference in `services` table. | **CANNOT DERIVE TENANT WITHOUT TENANT CONCEPT** – While `services.provider_id` references `perfiles_prestador.id`, the `perfiles_prestador` table itself has no determinable tenant link (see Professional row). Thus, no derivable tenant path exists without first resolving the Professional's tenancy. |
| Booking      | The appointment event, jointly involving a client and a professional; ownership is shared in the real world but the data record is system-owned. | **NO DIRECT TENANT COLUMN EXISTS** – No `tenant_id` or tenant table reference in `bookings` table. | **CANNOT DERIVE TENANT WITHOUT TENANT CONCEPT** – `bookings` references both `usuarios` (client_id) and `perfiles_prestador` (provider_id). Since neither the User nor the Professional entities have a determinable tenant link (see User and Professional rows), no derivable tenant path exists for Booking without introducing a tenant concept and linking the referenced entities to it. |
| Payment      | The financial transaction representing payment for a service; conceptually owned by the payer (client) and payee (professional/business). | **NO DIRECT TENANT COLUMN EXISTS** – No `tenant_id` or tenant table reference in `transactions` table (which stores payment records). | **CANNOT DERIVE TENANT WITHOUT TENANT CONCEPT** – `transactions.booking_id` references `bookings.id`. Since Booking has no determinable tenant link (see Booking row), no derivable tenant path exists for Payment without first resolving the Booking's tenancy. |
| Transaction  | Same as Payment; the `transactions` table records the financial transaction details.   | **NO DIRECT TENANT COLUMN EXISTS** – No `tenant_id` or tenant table reference in `transactions` table. | **CANNOT DERIVE TENANT WITHOUT TENANT CONCEPT** – Same reasoning as Payment: depends on Booking, which lacks a determinable tenant link. |

## EVIDENCE SUMMARY

- **No tenant table or `tenant_id` column** was found in any table (`usuarios`, `perfiles_prestador`, `services`, `bookings`, `transactions`, etc.) after inspecting `/c/beauty-app/backend/schema.sql` and related model files.
- **Relationships observed**:
  - `usuarios.id` ←→ `perfiles_prestador.id` (one-to-one, via foreign key)
  - `perfiles_prestador.id` ←→ `services.provider_id`
  - `usuarios.id` ←→ `bookings.client_id`
  - `perfiles_prestador.id` ←→ `bookings.provider_id`
  - `bookings.id` ←→ `transactions.booking_id`
- **Fields suggesting business context** (e.g., `perfiles_prestador.business_name`, `perfiles_prestador.descripcion`) are descriptive attributes, not foreign keys, and do not establish a tenant grouping mechanism.

## CONCLUSION

The current data model **does not implement any tenancy mechanism**. All entities lack direct tenant assignment (`tenant_id` or tenant table foreign key) and cannot derive a tenant from existing relationships because no tenant concept exists in the schema. To support multi-tenancy, a new tenant entity (e.g., `tenants` or `salones`) must be introduced, and the existing entities must be linked to it via foreign keys (e.g., adding `tenant_id` columns or creating association tables).
