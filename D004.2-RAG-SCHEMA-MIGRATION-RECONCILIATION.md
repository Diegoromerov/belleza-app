# D004.2-RAG-SCHEMA-MIGRATION-RECONCILIATION.md

## Executive Summary

This document presents the reconciliation between migration 031, the ragService.js code, D-001 multi-tenancy implementation, and D-004 retention requirements for the RAG system in GlowApp.

**Key Findings:**
- Migration 031 creates the `beauty_knowledge_embeddings` table with columns for a basic RAG system including `title`, `category`, `content`, `metadata` (JSONB), `embedding` (vector), and timestamps (`created_at`, `updated_at`).
- The ragService.js expects exactly this table structure and uses all columns except it does not currently utilize the `metadata` field for tenant scoping.
- The table does **not currently exist** in the database.
- Migration 031 is idempotent (uses `CREATE TABLE IF NOT EXISTS`) and depends only on the pgvector extension (migration 030).
- The table design is currently **global-only** (no `tenant_id` column), which aligns with D-001's decision to keep RAG GLOBAL.
- To support D-004's hybrid GLOBAL + TENANT-SCOPED model, the table would require modification to add a `tenant_id` column and corresponding changes to ragService.js.
- The current table structure supports the foundation for retention (timestamps exist) but lacks explicit retention/ deletion fields (`deleted_at`, `expires_at`, etc.) and audit capabilities.

**Reconciliation Status:** The migration 031 and ragService.js are fully compatible in their current form, representing a global-only RAG system. Evolution to support D-004 requires schema and service modifications.

## 5. D-001 Compatibility Analysis

**D-001 Established:** Shared Schema + tenant_id + RLS, with RAG kept GLOBAL

**Evidence from previous phases:**
- D-001 migrations (055-058) executed: `tenants` table created, `tenant_id` added to core tables
- Workforce controller (D-002) implements tenant filtering via `req.user.tenant_id`
- D-001 implementation report states: "`beauty_knowledge_embeddings` dejado como GLOBAL"
- No `tenant_id` column in migration 031
- ragService.js contains no tenant filtering

**Analysis:**
- ✅ **Can remain GLOBAL:** Migration 031 lacks `tenant_id`, ragService.js has no tenant filtering → consistent with D-001's decision to keep RAG global
- ⚠️ **Can evolve to hybrid later:** Would require adding `tenant_id` column (nullable) and modifying ragService.js to conditionally filter by tenant
- ❌ **Requires tenant_id for tenant-scoped:** Not present in 031; would need schema alteration
- ⚠️ **Requires explicit GLOBAL/TENANT classification:** Could be implemented via `tenant_id IS NULL` (GLOBAL) vs `tenant_id IS NOT NULL` (TENANT)
- ✅ **Compatible with RLS:** Table could be added to RLS policies; currently no RLS on this table (by design for GLOBAL)
- ⚠️ **Should remain outside RLS while GLOBAL:** Appropriate since it's intended to be accessible to all tenants
- ✅ **Can support simultaneous GLOBAL + TENANT-SCOPED:** With `tenant_id` column (NULL = GLOBAL, NOT NULL = TENANT) and appropriate query logic

**Conclusion:** Migration 031 is fully compatible with D-001's global-RAG decision. Evolution to support tenant-scoped knowledge requires backward-compatible changes.

## 10. Architecture Options

### OPCIÓN A: Ejecutar 031 sin modificación y mantener RAG GLOBAL
- **Ventajas:** 
  - Simple, minimal change
  - Preserves existing design intent
  - Compatible with current ragService.js
  - Idempotent and safe
- **Desventajas:** 
  - Does not support D-004's hybrid model requirement
  - No tenant-scoped knowledge capability
  - Limited retention foundation (only timestamps)
- **Riesgo:** 
  - May require rework later if tenant-scoped knowledge is needed
- **Impacto:** 
  - Low immediate value; delays D-004 capabilities
- **Compatibilidad D-001:** ✅ Perfect (maintains GLOBAL decision)
- **Compatibilidad D-004:** ❌ Incomplete (missing tenant-scoped and retention fields)
- **Deuda técnica:** ⚠️ Medium (would need future alteration)
- **Reversibilidad:** ✅ High (easy to alter table later)
- **Recomendación:** ❌ No recomendada como solución final

### OPCIÓN B: Reparar 031 para soportar GLOBAL + TENANT-SCOPED
- **Ventajas:** 
  - Single source of truth for knowledge
  - Atomic schema evolution
  - Preserves existing data if any existed
  - Clear evolution path
- **Desventajas:** 
  - Requires modifying committed migration (risky in some workflows)
  - Would break idempotency if not careful
  - All knowledge (past/future) in same table requires careful querying
- **Riesgo:** 
  - ⚠️ Medium (schema change on existing data if any existed)
  - Since table doesn't exist, risk is actually LOW
- **Impacto:** 
  - Enables D-004 hybrid model
  - Sets foundation for retention
- **Compatibilidad D-001:** ✅ Can maintain GLOBAL via `tenant_id IS NULL`
- **Compatibilidad D-004:** ✅ Enables hybrid model
- **Deuda técnica:** ⚠️ Low (clean evolution)
- **Reversibilidad:** ⚠️ Medium (would require migration to remove column)
- **Recomendación:** ✅ **RECOMENDADA** (given table doesn't exist, safe to modify)

### OPCIÓN C: Nueva migración posterior que evolucione estructura 031
- **Ventajas:** 
  - Preserves original migration integrity
  - Clear separation of concerns
  - Standard evolutionary approach
- **Desventajas:** 
  - Requires two table states to consider
  - May need complex ALTER TABLE or data migration
  - Two-step process increases complexity
- **Riesgo:** 
  - ⚠️ Low-Medium (depends on alteration complexity)
- **Impacto:** 
  - Same end result as Opción B
  - Slightly more complex implementation
- **Compatibilidad D-001:** ✅ 
- **Compatibilidad D-004:** ✅ 
- **Deuda técnica:** ⚠️ Low
- **Reversibilidad:** ✅ High
- **Recomendación:** ⚠️ Acceptable but less optimal than B given table doesn't exist

### OPCIÓN D: Replantear estructura completa antes de crearla
- **Ventajas:** 
  - Opportunity to design optimally from start
  - Could include all D-004 fields upfront
- **Desventajas:** 
  - Over-engineering risk
  - Delays implementation
  - May build features not yet needed
- **Riesgo:** 
  - ⚠️ Low (design risk)
- **Impacto:** 
  - Potential for better initial design
  - Risk of building unnecessary complexity
- **Compatibilidad D-001:** ✅

- **Reversibilidad:** ⚠️ Variable
- **Recomendación:** ⚠️ Consider only if significant redesign needed; current structure is sound

**Overall Recommendation:** **OPCIÓN B** (modificar 031 para añadir `tenant_id` y campos de retención necesarios) es la óptima dado que la tabla no existe actualmente, lo que hace la modificación segura y simple.
