# D001.10-MIGRATION-REPAIR-SPECIFICATION.md

## EXECUTIVE SUMMARY
This document provides a technical specification for repairing the D-001 migration set (055-058) to enable safe, idempotent execution on both a clean database and the current GlowApp database. The specification is based solely on evidence from the inspected migration files, schema.sql, and the actual database state observed in D-001.7 through D-001.9. No modifications to the database, code, or migration files are made in this phase.

## DIRECTOR FINDING
The Director has reviewed D-001.9 and confirmed that the existing migrations are not sufficiently safe/idempotent to run directly on the current database state. The recommended strategy is to repair each migration conceptually: make 056 idempotent and table-existence-aware, make 057 table-existence-aware, and make 058 idempotent with respect to RLS enabling, while preserving 055 as-is.

## 055 ANALYSIS
**File**: `055_create_tenants_table.sql`
- **IDempotencia**: Yes. Uses `CREATE TABLE IF NOT EXISTS` and `INSERT ... ON CONFLICT (id) DO NOTHING`.
- **Existencia de `tenants`**: The table exists in the current database with one row (id=1, name='Default Tenant', slug='default').
- **Tenant default**: Inserts a tenant with id=1, which is used as the default for existing data.
- **Comportamiento ante ejecución repetida**: Safe to run multiple times; no changes after first successful execution.
- **Compatibilidad con la base actual**: Fully compatible; running again results in no-op.
- **DECISION**: `KEEP AS-IS`

## 056 ANALYSIS
**File**: `056_add_tenant_id_to_core_tables.sql`
Current content attempts to add `tenant_id INTEGER` to a list of tables without checking existence of table or column.

### List of tables targeted (from file):
usuarios, servicios, bookings, transactions, reviews, portfolio_items, messages, nail_tryon_jobs, sos_alerts, user_activity_logs, perfiles_prestador

### Case analysis per table (based on current DB state):
- **usuarios**: EXISTS + COLUMN ALREADY EXISTS (nullable, all NULL)
- **servicios**: EXISTS + NEEDS COLUMN
- **bookings**: EXISTS + NEEDS COLUMN
- **transactions**: MISSING TABLE
- **reviews**: MISSING TABLE
- **portfolio_items**: MISSING TABLE
- **messages**: MISSING TABLE
- **nail_tryon_jobs**: MISSING TABLE
- **sos_alerts**: EXISTS + NEEDS COLUMN
- **user_activity_logs**: EXISTS + NEEDS COLUMN
- **perfiles_prestador**: MISSING TABLE

### Required behavior for a repaired migration:
| Case                           | Action   |
|--------------------------------|----------|
| Table exists + column missing  | ADD COLUMN tenant_id INTEGER |
| Table exists + column exists   | SKIP (no error) |
| Table does not exist           | SKIP (no error, do not create table) |
| Table exists but incompatible structure | STOP / BLOCKER (report mismatch) |

### Idempotency requirement:
The repaired migration must be idempotent, meaning it can be run repeatedly on:
- CLEAN DATABASE (where tables exist from schema but column missing)
- CURRENT DATABASE (as described above)
without DROP, data loss, duplication, or failure due to column existing.

### Recommended conceptual change:
Transform each `ALTER TABLE <table> ADD COLUMN tenant_id INTEGER;` into a conditional block that:
1. Checks if the table exists (via `SELECT to_regclass('public.<table>') IS NOT NULL` or similar).
2. If table exists, checks if the column exists (via querying `information_schema.columns`).
3. Only if table exists and column does not exist, execute `ALTER TABLE <table> ADD COLUMN tenant_id INTEGER;`.

### DECISION:
- **MODIFY** the migration to be idempotent and table-existence-aware (conceptually: `056-R`).
- Do not modify the file yet; this is a specification.

## 057 ANALYSIS
**File**: `057_backfill_tenant_id.sql`
Current content performs:
1. Insert a demo tenant (slug='demo') if not exists.
2. Update `tenant_id` in a long list of tables (core and optional) to the demo tenant ID where `tenant_id IS NULL`.
3. Add `tenant_id` column (if not exists) to several optional tables.
4. Create indexes on `tenant_id` for a list of tables.

### Responsibilities (as seen in file):
- **TENANT CREATION**: Insert demo tenant (id likely 2).
- **BACKFILL**: Update existing rows where `tenant_id IS NULL` to demo tenant ID.
- **OPTIONAL COLUMN CREATION**: Add column to optional tables (platform_config, admin_mfa, productos, beauty_knowledge_embeddings).
- **INDEX CREATION**: Create indexes on `tenant_id`.
- **OTHER**: None.

### Safety considerations for backfill:
- Must not execute if table does not exist.
- Must not execute if column does not exist (should be added by prior step).
- Must not overwrite existing non-NULL `tenant_id` values.
- Must handle case where tenant row for slug='demo' does not exist (insert it).
- Must leave `beauty_knowledge_embeddings.tenant_id` NULL (as per GLOBAL RAG) – observed in file: no UPDATE for that table, only column addition.

### Required behavior for a repaired migration:
For each UPDATE statement:
- Only execute if table exists and column exists.
- Only set `tenant_id = <demo_tenant_id>` where `tenant_id IS NULL`.
For each optional column addition:
- Only execute if table exists and column does not exist.
For each index creation:
- Only execute if table exists and index does not exist (use `IF NOT EXISTS`).

### DECISION:
- **MODIFY** the migration to be table-existence-aware and column-existence-aware for all operations (conceptually: `057-R`).
- Preserve the backfill logic as-is (only set NULL values) but add safety checks.
- Do not modify the file yet; this is a specification.

## 058 ANALYSIS
**File**: `058_enable_rls_policies.sql`
Current content:
1. Enables RLS on each table in a list (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`).
2. Drops any existing policy named `tenant_isolation_<table>` and creates a new policy: `USING (tenant_id = current_setting('app.tenant_id')::int)`.

### Idempotency analysis:
- Enabling RLS: `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;` is **not idempotent**; running it twice throws an error because RLS cannot be enabled twice.
- Policy creation: `DROP POLICY IF EXISTS ... CREATE POLICY ...` is idempotent.

### Required behavior for a repaired migration:
For each table:
- Check if table exists.
- If table exists, check if RLS is already enabled (via `SELECT relrowsecurity FROM pg_class WHERE relname = '<table>'`).
- If RLS is not enabled, then enable it.
- Then drop policy if exists and create policy (already idempotent).

### DECISION:
- **MODIFY** the migration to be idempotent by checking RLS status before enabling (conceptually: `058-R`).
- Do not modify the file yet; this is a specification.

## TENANT COLUMN ANALYSIS
- `usuarios.tenant_id`: EXISTS (pre-existing, outside D-001 sequence), nullable, all rows NULL, referenced by `src/middleware/auth.js` and `src/middleware/tenantContext.js`.
- All other core tables that exist (servicios, bookings, sos_alerts, user_activity_logs): column missing.
- Tables that do not exist: column cannot be added until table is created (outside D-001).
- The application expects `usuarios.tenant_id` to exist and uses it to set `app.tenant_id` GUC.

## BACKFILL SAFETY
- **WHAT**: Set `tenant_id` to the demo tenant ID (from `tenants` where slug='demo') for existing rows where `tenant_id IS NULL`.
- **WHERE**: Only in tables that exist and have the `tenant_id` column (after 056-R has ensured column exists where table exists).
- **WHEN**: After structural reconciliation (055 and 056-R) have run, and before RLS enabling.
- **WHY**: To associate existing data with a tenant so that RLS policies can isolate data per tenant.
- **Rule**: Only affect `EXISTING TABLES` and `EXISTING ROWS` where `tenant_id IS NULL`. Do not touch rows where `tenant_id IS NOT NULL` (preserve existing values).
- **Exception**: `beauty_knowledge_embeddings` must be left NULL (GLOBAL RAG) – confirmed by migration 057: no UPDATE statement for this table, only conditional column addition.
- No assumption should be made about creating missing tables; if they are missing, they are simply skipped.

## FOREIGN KEY STRATEGY
- None of the current migrations create foreign key constraints from core tables' `tenant_id` to `tenants.id`.
- For referential integrity, it is recommended to add `FOREIGN KEY (tenant_id) REFERENCES tenants(id)` on each core table that has the column.
- **Where to add**:
  - Could be part of 056-R (when adding the column) or 057-R (after column exists) or a separate migration.
  - Given that 057 already adds a FK for `perfiles_prestador` (see line: `ALTER TABLE perfiles_prestador ADD COLUMN IF NOT EXISTS tenant_id INTEGER REFERENCES tenants(id)`), it is consistent to add FKs for all tables in the same migration where the column is added.
- **Decision**: The FK should be added conceptually in the same migration where the column is added (i.e., in 056-R for core tables, and in 057-R for optional tables where appropriate). However, to keep the specification simple and avoid over-specifying, we note that FKs are **RECOMMENDED** and should be evaluated by the Director for inclusion in the repair.
- For the spec, we mark FK as **FK RECOMMENDED** and leave the exact migration placement to Director decision.

## INDEX STRATEGY
- Migration 057 creates indexes on `tenant_id` for a list of tables (if they exist).
- These indexes are **PERFORMANCE INDEX** (to speed up tenant-based queries) and also support **RLS SUPPORT INDEX** (though PostgreSQL can use the same index for both).
- No uniqueness or foreign key indexes are required beyond the FK index (if FK is added, PostgreSQL automatically creates an index).
- **Who should create them**: The index creation already appears in 057; it is appropriate to keep it there (after ensuring column exists).
- **Idempotency**: Use `CREATE INDEX IF NOT EXISTS`.
- **Decision**: Index strategy remains as in 057 but made table-existence-aware.

## RLS STRATEGY
- Migration 058 enables RLS and creates policies that restrict rows to `tenant_id = current_setting('app.tenant_id')::int`.
- **Tables protected**: All tables listed in 058 (core tables plus optional ones except beauty_knowledge_embeddings, which is correctly excluded because RAG is GLOBAL).
- **Application dependency**: The middleware in `src/middleware/tenantContext.js` sets `app.tenant_id` per connection based on `req.user.tenant_id`. Evidence shows it reads from `usuarios.tenant_id`.
- **Behavior if `app.tenant_id` not set**: The policy will evaluate to NULL, likely returning no rows (or error depending on casting). Must ensure middleware runs for all connections.
- **Behavior if RLS already enabled**: Current migration would fail; repaired version must check first.
- **Behavior if policy already exists**: Drop and recreate is idempotent.
- **Decision**: Keep the policy logic but make RLS enabling idempotent.

## MIGRATION TRACKING
- The project does not use `SequelizeMeta` or any other migration tracking table.
- The `runMigrations.js` script executes migration files in order but does not record which have been run.
- We determined that 055 was applied by observing the `tenants` table and its content matching the migration.
- We determined that 056 has not been successfully applied because it would fail on the first statement (as observed when we attempted to run it).
- **Fact**: There is no formal migration tracking mechanism in place.
- **Implication**: Re-running migrations is unsafe unless they are made idempotent (as specified in this repair).
- **Decision**: Report as fact; no new tracking system to be installed.

## CLEAN DATABASE PATH
On a clean database (schema loaded but no D-001 migrations run):
1. **055**: Create tenants table and insert default tenant (idempotent).
2. **056-R**: Add `tenant_id` column to all core tables (as they exist from schema) – safe because column missing.
3. **057-R**: 
   - Insert demo tenant (if not exists).
   - Update `tenant_id` to demo tenant ID where NULL (all rows will be updated because column just added and NULL).
   - Add column to optional tables that exist (from schema).
   - Create indexes.
4. **058-R**: 
   - Enable RLS on each table (if not already enabled).
   - Create policies.
This path is safe and idempotent.

## CURRENT DATABASE PATH
On the current GlowApp database:
1. **CURRENT STATE**: As verified in D-001.7 through D-001.9.
2. **055 NO-OP / VALIDATION**: Running 055 again will be a no-op (validates that tenants table exists with default tenant).
3. **056 RECONCILIATION**: Run repaired 056:
   - Skip `usuarios` (column exists).
   - Add `tenant_id` to `servicios`, `bookings`, `sos_alerts`, `user_activity_logs` (they exist, column missing).
   - Skip missing tables (transactions, etc.) – no error, no column added.
4. **VALIDATION**: Confirm that all existing core tables now have the `tenant_id` column (nullable).
5. **057 BACKFILL**: Run repaired 057:
   - Insert demo tenant (if not exists).
   - Update `tenant_id` to demo tenant ID where NULL in all existing core tables (and optional tables that exist).
   - Add column to optional tables that exist and missing column.
   - Create indexes.
6. **VALIDATION**: Confirm that `tenant_id` is populated (non-null) in all tables where data exists (except beauty_knowledge_embeddings stays NULL).
7. **058 RLS**: Run repaired 058:
   - For each table that exists, enable RLS if not already enabled.
   - Create/update policies.
8. **FINAL VALIDATION**: Confirm RLS is enabled and policies are in place (by checking `pg_policy` and `pg_class.relrowsecurity`).

- No other references to `tenant_id` found.

## FINAL MIGRATION STRUCTURE
The repaired migration set should conceptually be:
```
055 (KEEP AS-IS)
  ↓
056-R (idempotent, table-existence-aware column addition)
  ↓
VALIDATION (tenant_id column present in existing core tables)
  ↓
057-R (table-existence-aware backfill, optional column addition, index creation)
  ↓
VALIDATION (tenant_id populated where appropriate)
  ↓
058-R (idempotent RLS enabling and policy creation)
  ↓
FINAL VALIDATION (RLS active, policies correct)
```
No new migration files are to be created; the repairs are conceptual modifications to the existing files.

## IMPLEMENTATION ORDER
Each step in the order above must have:
- **PRECONDITION**: As described in the path.
- **ACTION**: Run the migration (or validation script).
- **VALIDATION**: Check the expected state (e.g., column existence, RLS status).
- **POSTCONDITION**: As described.
- **ROLLBACK / RECOVERY**: 
  - For 055: Drop tenants table (if no dependent data).
  - For 056-R: Drop the `tenant_id` column from tables where we added it (if safe).
  - For 057-R: Set `tenant_id` back to NULL where we updated it (we know we set it to demo tenant ID), drop optional columns we added, drop indexes we created.
  - For 058-R: Drop policies, disable RLS where we enabled it.
  - Rollback scripts are not to be created in this phase; they are noted for completeness.

## RISKS
- If missing core tables (transactions, reviews, etc.) are not created by other means before running D-001, the repaired migrations will skip them (due to table-existence checks), leaving those tables without `tenant_id`. This may cause application errors if the code expects those tables to exist and have the column.
- The backfill will set `tenant_id` to the demo tenant ID for all existing rows where NULL. If any data was intended to belong to a different tenant (no evidence of this), this would be incorrect. However, given the single tenant and NULL values, risk is low.
- Enabling RLS without proper testing could block access to data if the `app.tenant_id` is not set correctly by the middleware (e.g., for background workers or raw SQL connections).
- The `beauty_knowledge_embeddings` table is intentionally left without RLS and with `tenant_id` NULL (as RAG is GLOBAL). If this decision changes, the migration would need updating.
- The lack of foreign key constraints (if not added) could lead to orphaned `tenant_id` values if tenants are deleted.
