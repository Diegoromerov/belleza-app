# CONNECTION POOL AND TENANT CONTEXT ANALYSIS

## 1. CURRENT CONNECTION POOL SETUP
From code inspection:
- The backend imports `const { pool } = require('../config/db');` in multiple controllers (e.g., bookingController.js).
- The file `/c/beauty-app/backend/config/db.js` (not inspected in detail but inferred) likely exports a `pg.Pool` instance.
- No evidence of custom connection pool wrappers or middleware that sets session variables on connection acquisition.

## 2. RLS CONTEXT SETTING OPTIONS
To make RLS work, the database session must have a tenant identifier visible to policies. Common methods:
- **Session-scoped**: `SET app.tenant_id = <value>;` (persists for the lifetime of the connection).
- **Transaction-scoped**: `SET LOCAL app.tenant_id = <value>;` (only lasts for the current transaction and is rolled back if the transaction fails).
- **Per-query**: Embed the tenant ID directly in queries (alternative to RLS).

## 3. RISKS WITH CONNECTION POOLING
If using session-scoped SET:
- Connections are reused across requests.
- If a request sets `app.tenant_id` and the connection is returned to the pool, a subsequent request might inherit that value if not explicitly reset.
- This could lead to cross-tenant data leakage or incorrect blocking.

If using transaction-scoped SET LOCAL:
- The setting is bound to the transaction and automatically cleared when the transaction ends (commit or rollback).
- Safer with connection pooling because the context does not persist beyond the transaction.
- Requires that each request's database operations occur within a transaction that sets the context.

## 4. CURRENT TRANSACTION USAGE IN CODE
Inspection of bookingController.js shows:
- Some functions use `sequelize.transaction` (e.g., createBooking, payBooking).
- Some functions use raw `pool.query` without an explicit transaction (e.g., getProviderBookings, getClientBookings).
- There are also raw queries inside Sequelize transactions (e.g., lines 86, 491, 506, 609, 624).

Thus, not all code paths are wrapped in a transaction.

## 5. FEASIBLE APPROACHES
### Option A: Transaction-scoped context with mandatory transactions
- Wrap every request's database operations in a transaction (Sequelize or raw) that begins with `SET LOCAL app.tenant_id = ...;`.
- For endpoints that currently do not use transactions, introduce them.
- Ensure that all Sequelize and raw queries are executed within that transaction context.

### Option B: Connection-scoped with reset on acquisition
- Configure the connection pool to run a setup script on each connection checkout that resets any tenant context.
- Then, in a middleware or at the start of request processing, set `SET app.tenant_id = ...;` (session-scoped) for the duration of the request.
- Risk: If the connection is returned to the pool without resetting, the next request might see the wrong value unless the pool reset is reliable.

### Option C: Avoid RLS, use explicit tenant_id in queries
- Add `tenant_id` columns and modify all queries to include `WHERE tenant_id = $1` (or equivalent).
- This avoids reliance on session state and works with connection pooling naturally.
- However, it requires diligent application-level filtering.

## 6. RECOMMENDATION FOR GLOWAPP
Given the mixed use of Sequelize and raw queries, and the fact that not all endpoints are transaction-wrapped, the safest approach is:
- Use **explicit tenant_id in queries** (Option C) as the primary mechanism, and consider RLS as an additional defense-in-depth layer.
- If RLS is desired, adopt **Option A** (transaction-scoped SET LOCAL) and ensure that **every** request that accesses the database runs within a transaction that sets the context. This may require refactoring to wrap route handlers in a transaction middleware.

## 7. IMPACT ON CURRENT CODE
- To adopt transaction-scoped RLS, one would need to:
  1. Add a middleware that starts a transaction, sets `SET LOCAL app.tenant_id = ...;` using the user's tenant mapping, and then calls the next middleware.
  2. Ensure that all database operations (Sequelize and raw) occur within that transaction (they will if they use the same connection/client; for Sequelize, one must pass the transaction object or use a CLS namespace).
  3. Commit or rollback the transaction after the request.

This is a non-trivial change but feasible.
