# D002.1-API-SPEC.md

## API Specification for Workforce Management (D-002)

**Note**: This is a conceptual API specification only. No implementation is authorized at this stage.

### Overview
This specification defines the API endpoints required to support the operational classification of workforce members (EMPLEADO, PRESTADOR_SERVICIO, etc.) within a tenant (salon). The API assumes that the `usuarios` table has been extended with a `worker_type` column (tipo_trabajador ENUM) as specified in D002.1-DATA-MODEL.md.

### Core Principles
- All endpoints must enforce tenant isolation: users can only access workforce members belonging to their own tenant.
- The API must not expose or imply any legal relationship between GlowApp and the worker.
- The `worker_type` field is strictly for operational use by the salon and must be presented as such in documentation.
- Authentication and authorization must be in place for all endpoints.

### Endpoints

#### 1. Get Workforce Members (List)
- **URL**: `GET /api/v1/workforce`
- **Description**: Retrieve a paginated list of workforce members (users) for the current tenant.
- **Authentication**: Required (Bearer token or session).
- **Tenant Scope**: Derived from the authenticated user's `tenant_id` (via tenantContext middleware).
- **Authorization**: The authenticated user must have permission to view workforce members (e.g., salon admin or owner). This is an application-level role check (not to be confused with labor roles).
- **Query Parameters**:
  - `page` (integer, default: 1)
  - `limit` (integer, default: 20)
  - `worker_type` (optional, filter by one or more types: EMPLEADO, PRESTADOR_SERVICIO, etc.)
  - `search` (optional, search by name or email)
- **Response**:
  ```json
  {
    "data": [
      {
        "id": 123,
        "email": "juan@example.com",
        "nombre": "Juan Pérez",
        "worker_type": "PRESTADOR_SERVICIO",
        "rol": "PRESTADOR",  // existing rol field for login capabilities
        "is_active": true,
        "created_at": "2026-09-01T10:00:00Z"
      }
    ],
    "meta": {
      "page": 1,
      "limit": 20,
      "total": 42,
      "pages": 3
    }
  }
  ```
- **Risks**: 
  - Ensure that the `worker_type` field is not presented as a legal classification.
  - Validate that the tenant context is correctly applied to prevent cross-tenant data leaks.

#### 2. Get Workforce Member by ID
- **URL**: `GET /api/v1/workforce/:id`
- **Description**: Retrieve a single workforce member by ID.
- **Authentication**: Required.
- **Tenant Scope**: The requested ID must belong to the current tenant (enforced via middleware or query condition).
- **Authorization**: Same as list endpoint.
- **Response**: 
  ```json
  {
    "data": {
      "id": 123,
      "email": "juan@example.com",
      "nombre": "Juan Pérez",
      "worker_type": "PRESTADOR_SERVICIO",
      "rol": "PRESTADOR",
      "is_active": true,
      "created_at": "2026-09-01T10:00:00Z"
    }
  }
  ```
- **Errors**: 
  - 404 if not found or does not belong to the tenant.

#### 3. Update Workforce Member
- **URL**: `PATCH /api/v1/workforce/:id`
- **Description**: Update the operational classification (worker_type) and/or other allowed fields (e.g., is_active) for a workforce member.
- **Authentication**: Required.
- **Tenant Scope**: The ID must belong to the current tenant.
- **Authorization**: The authenticated user must have permission to edit workforce members (e.g., salon admin).
- **Request Body**:
  ```json
  {
    "worker_type": "EMPLEADO",
    "is_active": false
  }
  ```
- **Allowed Fields**: 
  - `worker_type` (must be a valid tipo_trabajador value)
  - `is_active` (boolean)
  - Note: Do not allow changing `email`, `nombre`, `rol` via this endpoint if those are managed elsewhere. Adjust as per existing user management endpoints.
- **Response**: 
  ```json
  {
    "data": {
      "id": 123,
      "worker_type": "EMPLEADO",
      "is_active": false
    }
  }
  ```
- **Risks**:
  - Ensure that the update does not allow changing the tenant_id or other protected fields.
  - Validate that the worker_type is one of the allowed ENUM values.

#### 4. Deactivate Workforce Member (Soft Delete)
- **URL**: `DELETE /api/v1/workforce/:id` or `PATCH /api/v1/workforce/:id/deactivate`
- **Description**: Deactivate a workforce member (set is_active to false). Alternatively, use the update endpoint to set is_active.
- **Authentication**: Required.
- **Tenant Scope**: The ID must belong to the current tenant.
- **Authorization**: Same as update endpoint.
- **Response**: 204 No Content or the updated object.

### Additional Considerations

#### Integration with Existing User Endpoints
- If there are existing endpoints for managing users (e.g., `/api/v1/users`), consider adding the `worker_type` field to those endpoints' responses and requests (if appropriate) to avoid duplication.
- Ensure that the `worker_type` field is included in the user profile endpoint if it exists.

#### Validation
- The API must validate that the `worker_type` value is one of the allowed ENUM values.
- The API must validate that the authenticated user's tenant matches the target user's tenant.

#### Documentation
- The API documentation (e.g., Swagger/OpenAPI) must clearly state that the `worker_type` field is for operational use only and does not determine legal relationships.

#### Error Handling
- Return appropriate HTTP status codes (400 for validation errors, 403 for authorization errors, 404 for not found, etc.).
- Do not leak tenant information in error messages (e.g., do not say "User not found in tenant X").

### Security Notes
- All endpoints must be protected by authentication and tenant context middleware.
- The tenant context middleware (from D-001) must be applied to set the `app.tenant_id` GUC for RLS, and the application must also enforce tenant scope in queries (double protection).
- Consider rate limiting to prevent abuse.
