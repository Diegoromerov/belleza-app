## H5 — Eliminación automática por antigüedad (Decisión: C — SOLO PARA CIERTOS DATOS)
### Diseño
Se creará un mecanismo de eliminación automática basado en antigüedad **solo para los tipos de datos expresamente autorizados** por el Director (pendiente de definición). El mecanismo será:
- Un job (o cron) que se ejecute periódicamente (frecuencia por definir).
- Para cada tipo de dato autorizado, eliminará registros cuya antigüedad supere el período de retención definido (pendiente de definición).
- La eliminación será hard delete (eliminación física de filas) para los datos autorizados.
- Se registrará en un log de auditoría cada eliminación (opcional, por definir).
### Datos candidatos (pendiente de autorización explícita)
- Datos biométricos (perfil, historial, derivados) — pero solo si se autoriza.
- Datos de usuario anonimizados (si se autoriza).
- Otros (transacciones, reservas, analytics, legacy, logs) — solo si se autoriza.
### Componentes afectados
- Crear nuevo servicio: `AutomaticRetentionService.js` (o similar).
- Crear job/cron: `automaticRetentionCron.js`.
- Posible actualización de modelos si se necesita agregar un campo de timestamp para cálculo de antigüedad (la mayoría ya tiene `created_at`).
### Migraciones potenciales
- Si se requiere agregar un campo de timestamp (p.ej., `updated_at` o `deleted_at`) a tablas que no lo tengan (pero la mayoría ya lo tiene).
- No se modificarán foreign keys ni se eliminarán columnas.
### Tests
- Unit tests para el servicio de eliminación automática.
- Integración tests que simulen el paso del tiempo y verifiquen la eliminación correcta.
- Tests de seguridad para asegurar que solo se eliminan los datos autorizados.
### Dependencias
- Definición explícita de: 
  - Qué tipos de datos están sujetos a eliminación automática.
  - Período de retención para cada tipo.
  - Frecuencia de ejecución del job.
### Riesgos
- Eliminación accidental de datos no autorizados si la configuración es incorrecta.
- Impacto en cumplimiento legal si se eliminan datos que deben conservarse.
### Rollback
- Dado que es eliminación física, el rollback requeriría restaurar desde backups (no se implementa lógica de undo).

## H6 — Retención automática (Decisión: C — PARCIAL)
### Diseño
Se creará un mecanismo de retención automática basado en antigüedad **solo para los tipos de datos expresamente autorizados** por el Director (pendiente de definición). La retención puede implicar:
- Eliminación física (hard delete) o anonimización (soft delete) según se defina por tipo de dato.
- Un job (o cron) que se ejecute periódicamente.
- Para cada tipo de dato autorizado, se aplicará la acción de retención (eliminación o anonimización) a registros cuya antigüedad supere el período definido.
### Datos candidatos (pendiente de autorización explícita)
- Idénticos a H5.
### Componentes afectados
- Crear nuevo servicio: `AutomaticRetentionService.js` (puede compartirse con H5 si se decide unificar).
- Crear job/cron: `automaticRetentionCron.js`.
- Posible necesidad de agregar campos para marcar anonimización (si se elige soft delete).
### Migraciones potenciales
- Si se elige anonimización para ciertos datos, podría requerirse agregar columnas como `is_anonymized` o `anonymized_at` (o reutilizar campos existentes).
- No se modificarán foreign keys.
### Tests
- Unit tests para el servicio de retención.
- Integración tests que verifiquen la aplicación correcta de la acción (eliminación o anonimización).
- Tests de seguridad para asegurar que solo se afectan los datos autorizados.
### Dependencias
- Definición explícita de:
  - Qué tipos de datos están sujetos a retención automática.
  - Para cada tipo: acción (eliminación o anonimización) y período de retención.
  - Frecuencia de ejecución del job.
### Riesgos
- Aplicar acción incorrecta (por ejemplo, anonimizar cuando debería eliminarse o viceversa).
- Impacto en cumplimiento legal si la acción o período no son adecuados.
### Rollback
- Si se elige eliminación física: mismo que H5.
- Si se elige anonimización: se podría revertir restaurando datos no anonimizados desde backups (no se implementa lógica de undo directo).

## H7 — Datos legacy (Decisión: C — REVISIÓN INDIVIDUAL)
### Diseño
Se realizará una revisión individual de cada conjunto de datos legacy identificado en F7.001-B para decidir si debe incluirse en los mecanismos de eliminación (manual o automática). Los pasos son:
1. Listar todos los conjuntos de datos legacy (tablas, columnas) identificados en F7.001-B y cualquier otro encontrado adicionalmente.
2. Para cada conjunto, evaluar:
   - Utilidad actual (¿todavía usado por algún servicio o funcionalidad?).
   - Sensibilidad (¿contiene datos personales o biométricos?).
   - Dependencias (¿qué servicios o procesos dependen de él?).
   - Posibilidad de eliminación sin afectar funcionalidad.
3. Según la evaluación, decidir:
   - Incluir en mecanismo de eliminación manual (endpoint existente o nuevo).
   - Incluir en mecanismo de eliminación automática (si se autoriza en H5/H6).
   - Excluir de cualquier mecanismo de eliminación (mantener indefinidamente).
4. Documentar la decisión por conjunto.
### Datos legacy identificados (ejemplo, pendiente de lista completa)
- `user_biometrics` (tabla legacy de biométricos).
- Otras tablas relacionadas con academias, etc. (de F7.001-B).
### Componentes afectados
- Ningún cambio inmediato en código o esquema.
- Si se decide incluir algún conjunto en eliminación manual, podría requerirse crear un endpoint o modificar un servicio existente.
- Si se decide incluir en eliminación automática, se alimentaría los mecanismos de H5/H6.
### Migraciones potenciales
- Si se decide agregar un mecanismo de eliminación para un conjunto que no lo tiene, podría requerirse crear un endpoint y su servicio asociado.
- No se modificarán esquemas a menos que se necesite agregar campos para rastrear eliminación (pero se prefiere hard delete o usar campos existentes).
### Tests
- Tests de revisión: verificar que la lista de conjuntos legacy esté completa y documentada.
- Si se crea nuevo endpoint de eliminación: unit y integración tests.
### Dependencias
- Lista completa de conjuntos de datos legacy (debe proporcionarse por el equipo o derivarse de F7.001-B y búsquedas adicionales).
- Para cada conjunto: información de utilidad, sensibilidad y dependencias (requiereinput de negocio/legal y técnicos).
### Riesgos
- Eliminar un conjunto legacy que aún esté en uso, causando fallos de funcionalidad.
- Conservar innecesariamente datos sensibles que podrían eliminarse.
### Rollback
- Si se elimina un conjunto legacy físicamente, el rollback requeriría restaurar desde backups.

## H8 — Retención de logs (Decisión: C — CLASIFICAR LOGS)
### Diseño
Se clasificará cada tipo de log identificado en el sistema y se definirá una política de retención (eliminación o archivado) por categoría. Los pasos son:
1. Listar todos los tipos de logs generados por el sistema (incluyendo pero no limitado a):
   - `biometric_access_log`
   - `auditoria_consentimiento_biometrico`
   - Logs de aplicación (winston, etc.)
   - Logs de acceso HTTP
   - Logs de errores
   - Logs de eventos de negocio
   - Otros logs de servicios externos (YouCam, Gemini, etc. — si se registran localmente)
2. Para cada tipo de log, evaluar:
   - Qué información contiene (¿identificadores personales, datos biométricos, metadata sensible?).
   - Finalidad (auditoría, debugging, monitoreo, seguridad).
   - Obligaciones legales de retención.
3. Según la evaluación, decidir:
   - Aplicar retención automática (eliminación o archivado tras un período).
   - Mantener indefinidamente (sin cambios).
   - Aplicar una política especial (por ejemplo, rotación pero conservación de resúmenes).
4. Definir para cada tipo con retención automática:
   - Período de retención.
   - Acción (eliminación física, anonimización, archivado en storage frío).
   - Frecuencia de trabajo de retención.
### Componentes afectados
- Si se requiere crear trabajos de retención para logs: crear servicio de retención de logs y job/cron.
- Posible necesidad de modificar la configuración de logging para exportar a storage frío (si se elige archivado).
- No se modificarán las tablas de log existentes a menos que se agregue un campo para marcar archivado (pero se prefiere particionamiento o tablas por fecha).
### Migraciones potenciales
- Si se decide particionar tablas de log por fecha para facilitar purgado, podría requerirse crear nuevas tablas y migrar datos existentes.
- Si se decide agregar columnas como `archived_at` o `is_archived`, requeriría migración.
- En muchos casos, se puede purgar mediante `DELETE` basado en timestamp sin cambios de esquema.
### Tests
- Unit tests para el servicio de retención de logs.
- Integración tests que verifiquen que se eliminan o archivan los logs correctos según su antigüedad.
- Tests de seguridad para asegurar que no se eliminan logs que deben conservarse.
### Dependencias
- Lista completa de tipos de logs y su contenido (requiere revisión de código de logging y configuración).
- Para cada tipo de log: decisión de retención (período y acción) pendiente de autorización explícita del Director o negocio/legal.
### Riesgos
- Eliminar logs necesarios para auditoría legal o investigaciones de seguridad.
- Conservar innecesariamente logs que incrementan costo de almacenamiento.
### Rollback
- Si se elimina un log físicamente, el rollback requeriría restaurar desde backups.
- Si se elige archivado, se podría restaurar desde el storage frío.
