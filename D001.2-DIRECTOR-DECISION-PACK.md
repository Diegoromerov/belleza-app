## 8. RLS
Presentar exclusivamente la conclusión documentada sobre:
tenant_id + RLS
Responder:
### ¿Es técnicamente viable?
Sí
EVIDENCIA: D001.1-RLS-FEASIBILITY.md líneas 78-88: "RLS es técnicamente factible con el stack actual (PostgreSQL 15+, Sequelize, pgPool, Redis)."
### ¿Qué requisito debe cumplirse?
1. Añadir columna tenant_id a las tablas relevantes
2. Habilitar RLS y crear políticas
3. Implementar mecanismo para establecer contexto de tenant por transacción (preferiblemente SET LOCAL)
4. Asegurar que todas las consultas se ejecuten dentro de ese contexto
EVIDENCIA: D001.1-RLS-FEASIBILITY.md líneas 80-83 lista los requisitos.
### ¿Cuál es el principal riesgo?
Fuga de contexto en el pool de conexiones si se usan variables de sesión sin reset
EVIDENCIA: D001.1-RLS-FEASIBILITY.md línea 86: "Fuga de contexto en el pool de conexiones si se usan variables de sesión sin reset"
### ¿Qué mecanismo de contexto tenant se recomienda?
SET LOCAL (ámbito de transacción)
EVIDENCIA: D001.1-CONNECTION-CONTEXT-ANALYSIS.md líneas 94-96: "Se recomienda usar SET LOCAL app.tenant_id = ... (nivel de transacción) para que el contexto se revierta automáticamente al final de la transacción."
### ¿Qué sucede con pgPool?
El pool reutiliza conexiones entre requests; si se usa SET sin reset hay riesgo de herencia de tenant entre requests; con SET LOCAL en transacciones el riesgo se minimiza porque el contexto no persiste más allá de la transacción.
EVIDENCIA: D001.1-CONNECTION-CONTEXT-ANALYSIS.md líneas 93-96 describe el comportamiento de pgPool y la recomendación.
### ¿Qué sucede con Sequelize?
Similar riesgo al de pgPool si el contexto se establece a nivel de conexión; puede funcionar si el contexto de tenant se establece en la conexión/transacción; se puede usar namespace de CLS o pasar explícitamente el objeto de transacción.
EVIDENCIA: D001.1-RLS-FEASIBILITY.md líneas 98-103 y D001.1-CONNECTION-CONTEXT-ANALYSIS.md líneas 98-102.

## 12. DECISIÓN ARQUITECTÓNICA
Presentar exactamente estas alternativas:
## A
Shared Schema + tenant_id
## B

## C

## D

Mostrar:
| Criterio            |  A |  B |  C |  D |
| ------------------- | -: | -: | -: | -: |
| Seguridad           | MEDIUM | HIGH | MEDIUM | HIGH |
| Complejidad         | LOW | MEDIUM | MEDIUM-HIGH | HIGH |
| Escalabilidad       | HIGH | HIGH | MEDIUM | LOW |
| Coste               | LOW | LOW | MEDIUM | HIGH |
| Migración           | MEDIUM | MEDIUM | MEDIUM-HIGH | HIGH |
| Compatibilidad      | HIGH | HIGH | MEDIUM | MEDIUM-HIGH |
| Riesgo operativo    | LOW | LOW | MEDIUM | HIGH |
| Riesgo cross-tenant | MEDIUM | LOW | MEDIUM | MUY BAJO |
Justificaciones basadas en D001-MULTITENANCY-COMPARISON.md:
- Seguridad: A depende de filtrado en aplicación (riesgo si se omite where); B agrega RLS como última barrera; C tiene aislamiento a nivel de esquema; D tiene aislamiento total.
- Complejidad: A es más simple (solo añadir where); B agrega políticas RLS; C requiere lógica de cambio de esquema; D requiere múltiples pools de conexión.
- Escalabilidad: A y B altas (miles de tenants); C media-baja (cientos a pocos miles); D baja-media (decenas a cientos).
- Coste: A y B bajos (usa recursos existentes); C medio (más complejo de gestionar esquemas); D alto (múltiples instancias o BDs).
- Migración: A y B requieren backfill de tenant_id; C requiere migrar a esquemas separados; D requiere migrar a nuevas BDs.
- Compatibilidad: A y B alta (solo añadir where); C media (requiere cambiar search_path); D media-alta (requiere múltiples pools).
- Riesgo operativo: A y B bajos (backups simples); C medio (backups y migraciones por esquema); D alto (backups, monitoreo, actualizaciones por cada BD).
- Riesgo cross-tenant: A medio (depende de aplicación); B bajo (RLS reduce riesgo de error de aplicación); C medio (depende de enrutamiento); D muy bajo (aislamiento total).
