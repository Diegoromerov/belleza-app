## 3. FOUNDATION & TENANT RESOLUTION EVIDENCE

### 3.1. Estructura Física de `memberships` (Migración `065`):
```sql
CREATE TABLE IF NOT EXISTS memberships (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id INTEGER NOT NULL REFERENCES tenants(id) ON DELETE RESTRICT,
    establishment_id UUID NOT NULL,
    user_id INTEGER NOT NULL,
    role VARCHAR(50) NOT NULL CHECK (role IN ('OWNER', 'MANAGER', 'PROFESSIONAL', 'RECEPTIONIST')),
    relation_type VARCHAR(50) NOT NULL DEFAULT 'STAFF_EMPLOYEE' CHECK (relation_type IN ('OWNER_PARTNER', 'STAFF_EMPLOYEE', 'INDEPENDENT_PROVIDER')),
    status VARCHAR(30) NOT NULL DEFAULT 'ACTIVE' CHECK (status IN ('INVITED', 'ACTIVE', 'SUSPENDED', 'REVOKED')),
    joined_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    revoked_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_membership_establishment FOREIGN KEY (establishment_id, tenant_id) 
        REFERENCES establishments(id, tenant_id) ON DELETE RESTRICT,
    CONSTRAINT fk_membership_user_tenant FOREIGN KEY (user_id, tenant_id) 
        REFERENCES usuarios(id, tenant_id) ON DELETE RESTRICT,
    CONSTRAINT uq_membership_establishment_user UNIQUE (establishment_id, user_id),
    CONSTRAINT uq_membership_id_establishment_tenant UNIQUE (id, establishment_id, tenant_id) -- Agregada en 068
);
```

### 3.2. Mecanismos de Aislamiento y Resolución:
1. **Doble FK Compuesta:** Cada membresía garantiza integridad referencial estricta contra `establishments(id, tenant_id)` y `usuarios(id, tenant_id)`.
2. **Unicidad de Afinidad:** `UNIQUE (establishment_id, user_id)` asegura que una identidad no tenga membresías duplicadas en la misma sede.
3. **Multi-Tenant RLS:** Política `tenant_isolation_memberships` exige `current_setting('app.tenant_id')`.
4. **Tenant Resolver (`066`):** La función `fn_resolve_user_tenant(p_user_id)` resuelve el tenant autoritativo del usuario de forma protegida con `SECURITY DEFINER`.

## 4. LEGACY USERS VS SAAS MEMBERSHIPS

### 4.1. Separación de Identidades:
- **`usuarios`:** Representa la **Cuenta / Persona** global (email, contraseña cifrada, teléfono, estado activo/inactivo).
- **`usuarios.rol`:** Clasificado como **FROZEN / LEGACY**. Almacena valores B2C (`CLIENTE`, `PRESTADOR`, `ADMIN`). **No debe utilizarse para autorización SaaS.**
- **`memberships.role`:** Representa el **Rol Operativo SaaS** en una sede específica (`OWNER`, `MANAGER`, `PROFESSIONAL`, `RECEPTIONIST`).

### 4.2. Flujo de Registro Actual:
- `POST /api/auth/register` crea registros en `usuarios`.
- El registro asigna `rol = 'CLIENTE'` o `rol = 'PRESTADOR'` y asigna `tenant_id`.
- **No crea automáticamente ninguna membresía de salón** (salvo en los scripts de seed o onboarding guiado de creación de sede).

## 5. MEMBERSHIP LIFECYCLE & OPERATIONAL BOUNDARIES

### 5.1. Máquina de Estados de Membresía:
$$\text{INVITED} \longrightarrow \text{ACTIVE} \longleftrightarrow \text{SUSPENDED} \longrightarrow \text{REVOKED}$$

- **`INVITED`:** La membresía fue creada pero el usuario no ha completado la aceptación/onboarding. `ActiveContextService` rechaza terminantemente membresías en este estado con HTTP 403 `MEMBERSHIP_NOT_ACTIVE`.
- **`ACTIVE`:** Membresía operativa plena. Permite emitir Active Context, asignar servicios, programar horarios, agendar citas y atender tickets.
- **`SUSPENDED`:** Desactivación temporal (ej. vacaciones, suspensión administrativa). `ActiveContextService` bloquea el acceso; el motor de disponibilidad (`NODO-05`) excluye sus slots.
- **`REVOKED`:** Desvinculación definitiva. Se registra `revoked_at`. Las relaciones históricas (`service_assignments`, `staff_schedules`, `appointments`, `tickets`) se preservan inmutables mediante `ON DELETE RESTRICT`.

### 5.2. Pertenencia Multi-Establecimiento:
- La restricción `UNIQUE (establishment_id, user_id)` permite que el **Usuario A** tenga:
  - `Membership 1` en `Establishment 1` con `role = 'OWNER'`
  - `Membership 2` en `Establishment 2` con `role = 'PROFESSIONAL'`
- El usuario selecciona activamente con cuál membresía operar mediante el header `x-active-membership-id`.

## 8. DEACTIVATION & ACCESS CONTROL AUTHORITY

- **Autoridad de Acceso:** La autoridad de acceso a la sede no reside en `establishments.is_active` ni en `usuarios.is_active` de forma aislada, sino en **`memberships.status == 'ACTIVE'`**.
- **Comportamiento ante Desactivación:**
  1. Si `memberships.status` pasa a `'SUSPENDED'` o `'REVOKED'`:
     - El colaborador no puede autenticarse en el contexto de esa sede (ActiveContext retorna 403).
     - La proyección de disponibilidad (`NODO-05`) omite al colaborador de los slots públicos e internos.
     - No se pueden crear nuevas citas (`NODO-06`) ni tickets (`NODO-08`) asignados a esa membresía.
     - Las citas y tickets históricos permanecen íntegros y auditables.

## 11. FRONTERA DE IDENTIDAD ($\text{CUSTOMER} \neq \text{USER} \neq \text{MEMBERSHIP}$)

- **`CUSTOMER` (`saas_customers`):** Directorio local de clientes del salón. No tiene credenciales de acceso al SaaS.
- **`USER` (`usuarios`):** Identidad global autenticada en el sistema.
- **`MEMBERSHIP` (`memberships`):** Pertenencia operacional de un `USER` a una sede (`establishment`) con un rol específico.
- **Regla Inquebrantable:** El dominio de Staff Provisioning opera exclusivamente sobre `usuarios` y `memberships`. **No debe tocar ni reutilizar `saas_customers`.**

## 14. ARCHITECTURAL QUESTIONS (DECISIONES ARQUITECTÓNICAS REQUERIDAS)

Antes de redactar el contrato formal de Staff Provisioning, el Director del Proyecto debe resolver las siguientes decisiones:

### DECISIÓN 1: Modelo de Incorporación de Personal (Directo vs Invitación)
- **Pregunta:** ¿El aprovisionamiento de staff en esta fase será por **Creación Directa / Vinculación por Email** (el Owner ingresa el email/datos del colaborador y se crea la cuenta/membresía de inmediato) o requiere un **Flujo Asíncrono de Invitación con Token y Aceptación por Correo**?
- **Impacto:** Si requiere tokens e invitaciones por correo, exige una nueva tabla `staff_invitations`, endpoints de aceptación pública y servicio de correo transaccional. Si es vinculación directa, opera directamente sobre `usuarios` y `memberships`.

### DECISIÓN 2: Jerarquía de Autoridad de Roles
- **Pregunta:** ¿Un `MANAGER` tiene potestad para invitar/desactivar a otros `MANAGER` o solo a `PROFESSIONAL` y `RECEPTIONIST`? ¿El rol `OWNER` es transferible o exclusivo del creador del tenant/sede?
- **Impacto:** Determina las validaciones en el controlador/servicio backend.

### DECISIÓN 3: Política ante Desactivación (`SUSPENDED` / `REVOKED`)
- **Pregunta:** Al suspender o revocar una membresía, ¿se deben cancelar automáticamente sus citas futuras en `saas_appointments` o deben reasignarse a otro colaborador?
- **Impacto:** Integración transaccional entre Staff Provisioning y `NODO-06` (Citas).
