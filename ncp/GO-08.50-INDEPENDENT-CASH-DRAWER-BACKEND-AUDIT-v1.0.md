## 4. Auditoría de Lógica de Dominio y Transaccionalidad

### 4.1 Ciclo de Vida de Sesión (Apertura y Cierre)
1. **Anti-Doble Apertura:** El índice único parcial `idx_unique_open_cash_session_per_est` garantiza a nivel de motor PostgreSQL que no puedan coexistir dos sesiones `OPEN` en el mismo establecimiento. Los intentos concurrentes disparan violación `23505` retornando HTTP `409 CASH_SESSION_ALREADY_OPEN`.
2. **Cierre Atómico y Lock Transaccional:** `closeSession()` adquiere un bloqueo pesimista de fila `SELECT ... FOR UPDATE` sobre la sesión dentro de un bloque `BEGIN ... COMMIT`, consolidando los movimientos y calculando `expected_cash` y `difference` de forma indivisible.
3. **Inmutabilidad de Sesión Cerrada:** Una sesión `CLOSED` no admite nuevos movimientos ni reaperturas.

### 4.2 Conciliación Matemática
Se verificaron las fórmulas en los 3 escenarios:
$$\text{Expected Cash} = \text{Opening Balance} + \sum \text{CASH\_SALE} + \sum \text{CASH\_IN} - \sum \text{CASH\_OUT}$$
$$\text{Difference} = \text{Counted Cash} - \text{Expected Cash}$$
- $\text{Difference} = 0.00 \rightarrow \mathbf{BALANCED}$ (Verificado en Test 21).
- $\text{Difference} > 0.00 \rightarrow \mathbf{SURPLUS}$ (Verificado en Test 18).
- $\text{Difference} < 0.00 \rightarrow \mathbf{SHORTAGE}$ (Verificado en Test 22).

### 4.3 Auditoría de Blind Close (Cierre Ciego)
- El endpoint `GET /api/saas/cash/current` evalúa el rol del usuario autenticado. Para `RECEPTIONIST`, el campo `expected_cash` se devuelve explícitamente como `null`.
- Los endpoints `/api/saas/cash/history` y `/api/saas/cash/sessions/:id` rechazan solicitudes de `RECEPTIONIST` con `403 FORBIDDEN_ROLE`.
- El operador realiza el conteo físico a ciegas y el servidor ejecuta la reconciliación matemática.

### Observaciones (OBSERVATION)
- **OBS-01 (Verificación de `saas_ticket_payments` en `recordCashSale`):**  
  *Contexto:* `SaasCashService.recordCashSale()` recibe `amount` y `ticketPaymentId` desde el orquestador del servicio. La integridad relacional está garantizada en PostgreSQL por la clave foránea `fk_cash_movements_ticket_payment` y el índice único parcial anti-duplicados.  
  *Recomendación para v1.1:* Agregar una consulta `SELECT payment_method, amount FROM saas_ticket_payments` previa para verificación redundante a nivel de runtime JS.
- **OBS-02 (Verificación de saldo en `CASH_OUT` bajo alta concurrencia):**  
  *Contexto:* `recordManualMovement` verifica el saldo en gaveta antes de insertar un `CASH_OUT`. Para la arquitectura v1.0 de caja física única por establecimiento (DEC-01), esta validación a nivel de aplicación es adecuada.  
  *Recomendación para v1.1:* Si se admite en el futuro múltiples TPVs concurrentes por sede, encapsular el egreso dentro de una transacción con bloqueo pesimista.
