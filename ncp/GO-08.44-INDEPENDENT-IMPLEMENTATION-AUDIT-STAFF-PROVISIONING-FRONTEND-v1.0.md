## 4. In-Depth Surface Verification

### 4.1 SCR-14: StaffDirectoryScreen
- **State Separation:** Invitation State and Membership State remain completely distinct. Tab 1 handles active/suspended/revoked memberships; Tab 2 handles pending invitations with remaining days until expiry.
- **Context Guards:** When `hasActiveContext == false`, gracefully renders `_buildMissingContextState()` with a CTA directing the user to `SCR-04` (`AvailableContextSelectorScreen`).
- **RBAC:** Non-privileged roles (`PROFESSIONAL`, `RECEPTIONIST`) cannot view the `+ Invitar` button or mutation triggers.

### 4.2 SCR-14-M1: StaffInviteModal
- **Validation:** RFC-5322 compliant regex prevents invalid email submissions.
- **Asynchronous Flow:** No user account is created at issuance; only an invitation record is registered with a 7-day TTL token.
- **Dynamic RBAC:** `MANAGER` actor is strictly constrained to operative roles (`PROFESSIONAL`, `RECEPTIONIST`). `OWNER` can issue all roles.

### 4.3 SCR-14-M2: StaffRoleDialog
- **Self-Mutation Guard:** Physical inspection verified that when `member.userId == currentUserId`, the submission button is hidden and an informative banner explains the governance restriction.
- **Backend Anti-Orphan Integration:** Handles `422 CANNOT_ORPHAN_ESTABLISHMENT` error code and displays actionable guidance.

### 4.4 SCR-14-M3: StaffStatusDialog
- **Lifecycle Machine:**
  - `ACTIVE` $\rightarrow$ `SUSPENDED` $\rightarrow$ `ACTIVE`
  - `ACTIVE` / `SUSPENDED` $\rightarrow$ `REVOKED` (Requires typing `"CONFIRMAR"`)
  - `REVOKED` $\rightarrow$ Terminal (No reactivation allowed; CTA suggests issuing a new invitation).
- **Retention Messaging:** UI clearly states that historic appointments and tickets are retained for operational and fiscal integrity.

### 4.5 SCR-14-M4: StaffRelationTypeDialog
- **Owner Privilege:** Restricted to actors with `role == 'OWNER'`. Mutates commercial relationship type (`STAFF_EMPLOYEE`, `INDEPENDENT_PROVIDER`, `OWNER_PARTNER`) without affecting RBAC permissions.

### 4.6 SCR-15: InvitationAcceptanceScreen
- **Public Surface:** Does not require pre-existing JWT or active context header to load inspection data.
- **Bifurcated Acceptance Flow:**
  - **Existing User:** Displays salon/organization branding and one-click button *"Aceptar y Unirme al Salón"*.
  - **New User:** Renders registration form with client-side password strength validation ($\ge 8$ characters, matching confirmation). On submit, claims token, logs in via `AuthService.login`, and loads the new `membership_id` into `ActiveContextHolder`.
- **Identity Invariant:** Salons/Owners never handle or persist passwords. Credentials are submitted directly to the auth subsystem.
