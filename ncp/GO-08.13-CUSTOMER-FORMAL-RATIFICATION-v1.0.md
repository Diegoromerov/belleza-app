## 2. MODELO CANÓNICO RATIFICADO

Queda formal y contractualmente establecido el modelo ontológico y relacional:

```
                       ┌─────────────────────────────────────┐
                       │           SAAS TENANT               │
                       └──────────────────┬──────────────────┘
                                          │
                                          ▼
                       ┌─────────────────────────────────────┐
                       │          SAAS CUSTOMER              │
                       │    (Identidad Canónica en Tenant)   │
                       │                                     │
                       │ - first_name, last_name             │
                       │ - phone, email, birth_date          │
                       │ - user_id (NULLABLE Link)           │
                       │ - status (ACTIVE, INACTIVE, ARCHIVED│
                       └──────────────────┬──────────────────┘
                                          │
                    ┌─────────────────────┴─────────────────────┐
                    │                                           │
                    ▼                                           ▼
       ┌─────────────────────────┐                 ┌─────────────────────────┐
       │  CUSTOMER-ESTABLISHMENT │                 │  CUSTOMER-ESTABLISHMENT │
       │        RELATION         │                 │        RELATION         │
       │       (Sede A)          │                 │       (Sede B)          │
       │                         │                 │                         │
       │ - local_notes           │                 │ - local_notes           │
       │ - first_visited_at      │                 │ - first_visited_at      │
       │ - last_visited_at       │                 │ - last_visited_at       │
       │ - is_active             │                 │ - is_active             │
       └─────────────────────────┘                 └─────────────────────────┘
```

1. **Distinciones Ontológicas:**  
   `CUSTOMER ≠ PERSONA ≠ ACCOUNT / public.usuarios ≠ MEMBERSHIP ≠ GUEST`.
2. **Identidad Canónica (Scope Tenant):**  
   `saas_customers` pertenece estrictamente a un `tenant_id`. Permite a una empresa compartir el directorio entre sus distintas sedes.
3. **Relación Operacional (Scope Establecimiento):**  
   `saas_customer_establishments` preserva de manera privada las notas locales de servicio (`local_notes`), estado de actividad local y métricas temporales de visita en cada sede física.

## 3. DECISIONES ARQUITECTÓNICAS RATIFICADAS

| Código | Decisión Ratificada | Especificación Contractual |
| :--- | :--- | :--- |
| **`DEC-CUST-001`** | **Separación Identidad Tenant vs Relación Sede** | Modelo dual de dos entidades: `saas_customers` (Tenant) $\to$ `saas_customer_establishments` (Sede). |
| **`DEC-CUST-002`** | **Autonomía Total sin Cuenta de App** | `user_id` es estrictamente `NULLABLE`. El cliente opera en salón con nombre y teléfono sin requerir cuenta global en `public.usuarios`. |
| **`DEC-CUST-003`** | **Account Linking Explícito y Reversible** | La vinculación con `usuarios` requiere acción explícita de `OWNER`/`MANAGER` o verificación autenticada. Cero matching automático silencioso. Teléfono/email son *Contact Data Match*, no *Identity Match*. |
| **`DEC-CUST-004`** | **Invarianza de NODO-06 y NODO-08** | Cero cambios en esquemas físicos 071 y 072. Historial de visitas y tickets derivado por consultas de agregación de lectura. |
| **`DEC-CUST-005`** | **Control No Bloqueante de Duplicados** | Búsqueda predictiva (typeahead) en frontend + advertencia suave (*Soft Warning*) en backend + decisión humana del operador en mostrador. Sin `UNIQUE` rígido en teléfono. |
| **`DEC-CUST-006`** | **Minimización de Datos y Exclusión Clínica** | Exclusión taxativa de datos médicos, diagnósticos, recetas o fichas de salud. Alcance 100% comercial/operacional de salón. |
| **`DEC-CUST-007`** | **Autoridad Contextual vía Active Context** | Validación estricta a través de `x-active-membership-id: <UUID>` y RLS `app_fn_saas_context_establishment_id()`. Rechazo de headers sintéticos. |
| **`DEC-CUST-008`** | **Ciclo de Vida Normalizado** | Estados: `ACTIVE` (operativo), `INACTIVE` (sin visitas recientes), `ARCHIVED` (duplicado histórico o baja). |
