## 1. CONTEXT

Tras ratificarse en `GO-08.33` el **Modelo de Invitación Asíncrona (Opción B)** para la incorporación de personal a un establecimiento, es imperativo establecer las fronteras normativas de autoridad dentro del contexto operativo de la sede (`establishment`).

Actualmente, las migraciones fundacionales (`065`) y los nodos operativos cerrados (`NODO-01` a `NODO-08`) definen cuatro roles contextuales (`OWNER`, `MANAGER`, `PROFESSIONAL`, `RECEPTIONIST`), pero no formalizan la jerarquía de mutabilidad que rige qué actor puede crear, promover, degradar, suspender o revocar membresías de otros colaboradores.

---

## 2. DECISION QUESTION

$$\mathbf{¿Qué\ autoridad\ posee\ un\ OWNER\ frente\ a\ un\ MANAGER\ para\ crear,\ invitar,\ modificar\ roles,\ suspender\ y\ revocar\ membresías\ de\ Staff\ dentro\ de\ una\ sede?}$$

---

## 3. EXISTING EVIDENCE (EVIDENCIA FÍSICA EN BASE DE DATOS)

### 3.1. Definición Física de `memberships` (`065_saas_foundation_core.sql:72-89`):
```sql
CREATE TABLE IF NOT EXISTS memberships (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id INTEGER NOT NULL REFERENCES tenants(id) ON DELETE RESTRICT,
    establishment_id UUID NOT NULL,
    user_id INTEGER NOT NULL,
    role VARCHAR(50) NOT NULL CHECK (role IN ('OWNER', 'MANAGER', 'PROFESSIONAL', 'RECEPTIONIST')),
    relation_type VARCHAR(50) NOT NULL DEFAULT 'STAFF_EMPLOYEE' CHECK (relation_type IN ('OWNER_PARTNER', 'STAFF_EMPLOYEE', 'INDEPENDENT_PROVIDER')),
    status VARCHAR(30) NOT NULL DEFAULT 'ACTIVE' CHECK (status IN ('INVITED', 'ACTIVE', 'SUSPENDED', 'REVOKED')),
    joined_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    revoked_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_membership_establishment FOREIGN KEY (establishment_id, tenant_id) 
        REFERENCES establishments(id, tenant_id) ON DELETE RESTRICT,
    CONSTRAINT fk_membership_user_tenant FOREIGN KEY (user_id, tenant_id) 
        REFERENCES usuarios(id, tenant_id) ON DELETE RESTRICT,
    CONSTRAINT uq_membership_establishment_user UNIQUE (establishment_id, user_id),
    CONSTRAINT uq_membership_id_establishment_tenant UNIQUE (id, establishment_id, tenant_id)
);
```

### 3.2. Autoridad de Identidad Global vs Rol Contextual:
- **`usuarios.rol`:** `CHECK (rol IN ('CLIENTE', 'PRESTADOR', 'ADMIN'))` $\to$ **FROZEN / LEGACY**. Almacena la categoría B2C global. **No debe utilizarse como autoridad de permisos en el SaaS.**
- **`memberships.role`:** Rol contextual específico a una sede (`establishment_id`) y tenant (`tenant_id`).

## 5. ROLE MUTATION ANALYSIS (SEPARACIÓN DE MANDO)

La arquitectura define dos dominios de gestión:

1. **Staff Administration (Administración Operativa del Personal):**
   - Incorporación y gestión de personal de mostrador y especialistas (`PROFESSIONAL`, `RECEPTIONIST`).
   - Autoridad compartida: **`OWNER`** y **`MANAGER`**.
2. **Ownership Governance (Gobernanza de Mando y Titularidad):**
   - Incorporación, promoción, degradación y revocación de administradores (`MANAGER`) y titulares (`OWNER`).
   - Modificación de la naturaleza contractual (`relation_type`) y revocación definitiva de vínculos (`REVOKED`).
   - Autoridad exclusiva: **`OWNER`**.

---

## 6. SELF-MODIFICATION & ANTI-PRIVILEGE ESCALATION ANALYSIS

Para evitar ataques de elevación de privilegios y disrupción operativa:

1. **Auto-Promoción Prohibida:** Ningún usuario (incluido `MANAGER`) puede modificar su propio rol en `memberships`.
2. **Auto-Desactivación Prohibida para Personal Operativo:** `PROFESSIONAL` y `RECEPTIONIST` no pueden auto-suspenderse ni auto-revocarse.
3. **Regla de No Orfandad de Sede (*Non-Orphan Establishment Invariant*):**
   - Toda sede debe contar siempre con **al menos un (1) `OWNER` en estado `ACTIVE`**.
   - Un `OWNER` **no puede auto-suspenderse ni auto-revocarse** si es el único titular activo del establecimiento.
4. **Inmutabilidad de Anclaje:** Ni `OWNER` ni `MANAGER` pueden reasignar el `establishment_id` o `tenant_id` de una membresía existente.

---

## 7. OWNERSHIP ANALYSIS (TITULARIDAD DE SEDE)

- **Evidencia Física:** No existe columna `is_primary_owner` ni entidad `owner_transfers` en las migraciones 001–073.
- **Dictamen:** Todas las membresías con `role = 'OWNER'` operan como **Co-Titulares Simétricos** a nivel de sede.
- **Declaración:** La noción de *Primary Owner vs Co-Owner* queda clasificada como **NO DEFINIDA** en el esquema actual. La regla de no orfandad salvaguarda la continuidad del salón sin requerir jerarquías complejas de co-propietarios.

---

## 8. RELATION TYPE ANALYSIS (`relation_type`)

### 8.1. Valores Físicos en Base de Datos (`065:78`):
- `OWNER_PARTNER` (Socio Propietario)
- `STAFF_EMPLOYEE` (Empleado de Planta / Contrato Laboral)
- `INDEPENDENT_PROVIDER` (Prestador Independiente / Por Comisión)

### 8.2. Análisis de Impacto en Autoridad y Operación:
- **Impacto en Autoridad (RBAC):** `relation_type` **NO otorga permisos de acceso por sí mismo**. Los permisos se derivan estrictamente de `memberships.role`. Un `INDEPENDENT_PROVIDER` con rol `PROFESSIONAL` tiene exactamente los mismos permisos de sistema que un `STAFF_EMPLOYEE` con rol `PROFESSIONAL`.
- **Impacto en Asignaciones y Horarios:** No restringe la asignación de ofertas (`service_assignments`) ni horarios (`staff_schedules`).
- **Impacto Contractual / Financiero:** `relation_type` servirá como base para el futuro dominio de Liquidación de Comisiones (*Commissions & Settlements*).
- **Mutabilidad:** La modificación de `relation_type` queda **reservada exclusivamente al `OWNER`**, ya que define la naturaleza jurídica/laboral de la relación entre el salón y la persona.

## 9. SECURITY ANALYSIS

| Vector de Riesgo | Riesgo Potencial | Mitigación Arquitectónica |
| :--- | :--- | :--- |
| **Escalamiento Vertical** | Un Manager se auto-promueve a Owner. | Backend valida que `actorRole === 'OWNER'` para asignar rol `OWNER` o `MANAGER`. |
| **Escalamiento Horizontal** | Un Manager degrada o suspende a otro Manager rival. | Manager tiene denegada cualquier mutación sobre target con rol `MANAGER` o `OWNER`. |
| **Orfandad de Sede** | El único Owner se revoca a sí mismo dejando la sede sin titular. | Validación backend: conteo de `COUNT(*) WHERE role='OWNER' AND status='ACTIVE' > 1` antes de suspender/revocar a un Owner. |
| **Cross-Tenant Mutation** | Un Owner intenta modificar membresías de otra sede/tenant. | Verificación de doble FK y aislamiento RLS con `app.tenant_id`. |

---

## 10. COMPATIBILITY ANALYSIS CON DOMINIOS CERRADOS

1. **NODO-02 / 068 (Asignaciones):** `service_assignments` requiere membresía activa. Si un colaborador es suspendido, el catálogo no sufre cambios estructurales pero el colaborador queda inhabilitado.
2. **NODO-05 / 069 (Horarios):** `staff_schedules` mantiene sus registros físicos; el motor de disponibilidad ignora automáticamente horarios de membresías que no estén en `status = 'ACTIVE'`.
3. **NODO-06 / 071 & NODO-08 / 072 (Citas y Tickets):** `ON DELETE RESTRICT` protege citas y tickets históricos contra eliminación física de membresías.
