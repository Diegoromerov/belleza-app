## 4. Database & DDL Physical Audit

Direct inspection of the PostgreSQL database confirmed:
1. **Table Structure:** `staff_invitations` table is created with `id UUID PRIMARY KEY`.
2. **Foreign Keys:**
   - `fk_staff_invitations_establishment`: `(establishment_id, tenant_id) REFERENCES establishments(id, tenant_id) ON DELETE RESTRICT`.
   - `fk_staff_invitations_inviter`: `(invited_by_membership_id, establishment_id, tenant_id) REFERENCES memberships(id, establishment_id, tenant_id) ON DELETE RESTRICT`.
   - `fk_staff_invitations_accepted_user`: `(accepted_user_id, tenant_id) REFERENCES usuarios(id, tenant_id) ON DELETE RESTRICT`.
   - `staff_invitations_tenant_id_fkey`: `(tenant_id) REFERENCES tenants(id) ON DELETE RESTRICT`.
3. **Check Constraints:**
   - `role IN ('OWNER', 'MANAGER', 'PROFESSIONAL', 'RECEPTIONIST')`
   - `relation_type IN ('OWNER_PARTNER', 'STAFF_EMPLOYEE', 'INDEPENDENT_PROVIDER')`
   - `status IN ('PENDING', 'ACCEPTED', 'EXPIRED', 'REVOKED')`
4. **Indices:**
   - `uq_staff_invitations_pending`: Unique partial index on `(establishment_id, lower(email)) WHERE status = 'PENDING'`.
   - `staff_invitations_token_hash_key`: Unique index on `token_hash`.
5. **Row-Level Security:** RLS is enabled on `staff_invitations` with policy `tenant_isolation_staff_invitations`.

## 5. Security & Attack Surface Audit

1. **Token Entropy & Storage:**
   - Raw tokens are generated with 256 bits of cryptographically secure entropy (`crypto.randomBytes(32)`).
   - Only the SHA-256 digest is stored in the database.
   - Plaintext tokens are returned once during invitation creation/resend and never logged or persisted.
2. **Public Endpoint Sanitization:**
   - `GET /api/saas/public/invitations/:token` returns strictly: `valid`, `email`, `role`, `relation_type`, `establishment_name`, `tenant_name`, `expires_at`, `user_exists`.
   - Internal credentials, hashes, and foreign establishment data are not leaked.
3. **Anti-IDOR & Multi-Tenant Isolation:**
   - All management queries enforce `tenant_id` and `establishment_id` from the resolved server-side Active Context.
   - Cross-tenant and cross-establishment requests return `404` or `403`.
4. **Anti-Orphan & Anti-Self-Escalation:**
   - Managers cannot assign `OWNER` or `MANAGER` roles.
   - Owners cannot demote or de-escalate the sole active owner of an establishment.

## 8. Findings & Observations

### Findings Summary:
- **CRITICAL:** 0
- **MAJOR:** 0
- **MINOR / OBSERVATIONS:** 2

#### [OBS-01] State-Based Audit Trail vs Dedicated Audit Log Table
- **Severity:** OBSERVATION
- **Description:** Governance state transitions (invitation creation, resend, revocation, acceptance, role change, deactivation) are recorded via timestamps and foreign keys on `staff_invitations` (`created_at`, `expires_at`, `accepted_at`, `accepted_user_id`, `updated_at`) and `memberships` (`created_at`, `joined_at`, `revoked_at`, `updated_at`). There is currently no separate global `saas_audit_events` append-only table.
- **Impact:** Minimal for v1.0, as all contractual events and timestamps are fully traceable within the entity tables.
- **Recommendation:** When a unified enterprise audit trail is introduced platform-wide, staff governance events can be tapped to stream into that log.

#### [OBS-02] Test Suite Fixture Setup Privileges
- **Severity:** OBSERVATION
- **Description:** Automated test suites creating root organization and establishment fixtures require either superuser privileges or explicitly setting `app.tenant_id` during raw SQL fixture insertion.
- **Impact:** None on runtime API operations, as all runtime operations execute within authenticated session scopes where `app.tenant_id` is set.
- **Recommendation:** Maintain the isolated test runner conventions used across SaaS test suites.
