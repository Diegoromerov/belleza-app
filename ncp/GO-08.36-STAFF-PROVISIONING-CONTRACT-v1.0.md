## 1. EXECUTIVE SUMMARY

El presente contrato formaliza la especificación técnica, arquitectónica y funcional del dominio **`Staff Provisioning`** (Aprovisionamiento y Gobernanza de Personal) para GlowApp SaaS.

Este contrato consolida de forma vinculante las tres decisiones arquitectónicas previas:
1. **`GO-08.33` (Modelo de Incorporación):** Adopción del flujo asíncrono de **Invitación por Correo y Aceptación Explícita** con token criptográfico seguro.
2. **`GO-08.34` (Jerarquía de Mando):** Separación estricta entre **Staff Administration** (operada por `OWNER` y `MANAGER` sobre personal operativo) y **Ownership Governance** (reservada exclusivamente a `OWNER` para la estructura de mando).
3. **`GO-08.35` (Política de Desactivación):** Adopción de la **Opción C: Retención + Bloqueo de Ejecución + Resolución Humana Informada** para salvaguardar la integridad de citas, horarios, catálogos y liquidaciones de tickets.

## 3. CANONICAL ARCHITECTURE & IDENTITY CHAIN

El sistema desacopla rígidamente la persona natural de su pertenencia a un establecimiento:

$$\text{PERSON} \longrightarrow \text{ACCOUNT / IDENTITY (usuarios)} \longrightarrow \text{MEMBERSHIP (memberships)} \longrightarrow \text{ROLE contextual}$$
$$\text{TENANT (tenants)} \longrightarrow \text{ESTABLISHMENT (establishments)} \longrightarrow \text{MEMBERSHIP (memberships)}$$

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ PERSONA NATURAL                                                                        │
│ Posee nombre, correo personal y número telefónico.                                     │
└───────────────────────────────────────────┬────────────────────────────────────────────┘
                                            │
                                            ▼
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ CUENTA / IDENTIDAD GLOBAL (usuarios)                                                   │
│ Autenticable con credenciales (email + bcrypt password). Asociada a tenant_id.         │
└───────────────────────────────────────────┬────────────────────────────────────────────┘
                                            │
                                            ▼
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ MEMBRESÍA CONTEXTUAL (memberships)                                                     │
│ Pertenencia operacional formal a un establishment específico con un rol y estado.      │
│ Invariante: UNIQUE (establishment_id, user_id).                                        │
└───────────────────────────────────────────┬────────────────────────────────────────────┘
                                            │
                                            ▼
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ ROL CONTEXTUAL (role)                                                                  │
│ Define la autoridad en la sede: OWNER, MANAGER, PROFESSIONAL, RECEPTIONIST.            │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

## 4. IDENTITY & DOMAIN BOUNDARIES

1. **$\text{CUSTOMER} \neq \text{USER} \neq \text{MEMBERSHIP}$:**
   - `saas_customers` (N09 / SCR-13) es el directorio de clientes del salón.
   - `usuarios` es la cuenta global de acceso al sistema.
   - `memberships` es la asignación de un operador a la sede.
   - **Proscripción:** El aprovisionamiento de personal opera exclusivamente sobre `usuarios` y `memberships`. No utiliza ni contamina el dominio `saas_customers`.
2. **Soberanía de Credenciales:**
   - Ningún Owner o Manager puede definir, conocer ni resetear directamente la contraseña de un colaborador. La contraseña siempre es establecida por el propio usuario.

---

## 5. INCORPORATION MODEL (ASYNCHRONOUS INVITATION)

En cumplimiento de `GO-08.33`, el flujo formal de incorporación de colaboradores es:

$$\text{Owner / Manager} \xrightarrow{\text{Invita (Email + Rol)}} \text{staff\_invitations (PENDING)} \xrightarrow{\text{Email}} \text{Colaborador} \xrightarrow{\text{Aceptación}} \text{memberships (ACTIVE)}$$

1. **Emisión:** El Owner o Manager emite la invitación para un correo electrónico, asignando `role` y `relation_type`.
2. **Generación de Token:** El backend crea un registro en `staff_invitations` con token criptográfico (SHA-256 hash almacenado), con vigencia de **7 días calendario**.
3. **Notificación:** Se envía un correo electrónico al destinatario con el enlace único de aceptación.
4. **Handoff y Resolución:**
   - **Caso Usuario Nuevo:** El enlace redirige al registro guiado. El usuario define su nombre y contraseña. Al registrarse, se crea su cuenta en `usuarios` vinculada al `tenant_id` de la sede y se activa de inmediato su membresía.
   - **Caso Usuario Existente:** El usuario inicia sesión con sus credenciales y aprueba la vinculación a la sede.
5. **Cierre de Invitación:** La invitación pasa a estado `ACCEPTED` y se inserta la fila correspondiente en `memberships` con `status = 'ACTIVE'`, `joined_at = CURRENT_TIMESTAMP`.

## 6. INVITATION LIFECYCLE CONTRACT (`staff_invitations`)

### 6.1. Máquina de Estados de la Invitación:
$$\text{PENDING} \xrightarrow{\text{accept}} \text{ACCEPTED} \quad (\text{Terminal})$$
$$\text{PENDING} \xrightarrow{\text{revoke}} \text{REVOKED} \quad (\text{Terminal})$$
$$\text{PENDING} \xrightarrow{\text{expires (7d)}} \text{EXPIRED} \quad (\text{Terminal})$$

### 6.2. Reglas del Ciclo de Vida:
- **Unicidad Pendiente:** No pueden existir dos invitaciones en estado `PENDING` para la misma tupla `(establishment_id, email)`.
- **Reenvío:** Al reenviar una invitación pendiente, se renueva la fecha `expires_at` a $+7$ días y se actualiza el token, invalidando el enlace anterior.
- **Revocación:** Un Owner (o Manager para roles operativos) puede cancelar una invitación `PENDING`, transicionándola a `REVOKED`.

---

## 7. MEMBERSHIP LIFECYCLE CONTRACT (`memberships`)

### 7.1. Máquina de Estados de la Membresía:
$$\text{INVITED} \xrightarrow{\text{accept}} \text{ACTIVE} \longleftrightarrow \text{SUSPENDED} \xrightarrow{\text{revoke}} \text{REVOKED} \quad (\text{Terminal})$$

### 7.2. Semántica de Estados:
- **`INVITED`:** Membresía preliminar. No emite Active Context (`403 MEMBERSHIP_NOT_ACTIVE`), no participa en disponibilidad ni en agendas.
- **`ACTIVE`:** Membresía operativa plena. Habilita emisión de contexto, asignación de catálogo (`service_assignments`), horarios (`staff_schedules`), agendas (`saas_appointments`) y cobros (`saas_service_tickets`).
- **`SUSPENDED`:** Desactivación temporal reversible. Bloquea emisión de contexto (`403`) y disponibilidad (0 slots). Citas futuras quedan alertadas para resolución humana.
- **`REVOKED`:** Desvinculación definitiva e irreversible. Registra `revoked_at`. Preserva historial inmutable (`ON DELETE RESTRICT`).

## 8. ROLE MODEL

Se formalizan exclusivamente los cuatro roles contextuales canónicos:

1. **`OWNER` (Titular / Socio Propietario):** Máxima autoridad de gobernanza, titularidad de sede y administración de personal.
2. **`MANAGER` (Administrador de Sede):** Autoridad operativa para administrar el salón y el personal de piso (`PROFESSIONAL`, `RECEPTIONIST`).
3. **`PROFESSIONAL` (Especialista / Estilista):** Ejecutor de servicios. Visualiza su agenda y sus ítems de cobro. Cero autoridad administrativa.
4. **`RECEPTIONIST` (Recepcionista / Cajero):** Operador de mostrador. Gestiona agendas, citas y cobro en mostrador. Cero autoridad sobre personal.

## 10. ANTI-ORPHAN INVARIANT RULE

$$\mathbf{Regla:\ En\ todo\ momento,\ un\ establecimiento\ DEBE\ poseer\ al\ menos\ un\ (1)\ OWNER\ en\ status\ ='\text{ACTIVE}'.}$$

### Restricciones Contractuales:
1. El backend **rechazará con `HTTP 422 CANNOT_ORPHAN_ESTABLISHMENT`** cualquier intento de suspender, revocar o degradar a un `OWNER` si es el único `OWNER` activo registrado en la sede.
2. Un `OWNER` no puede auto-suspenderse ni auto-revocarse salvo que exista previamente otro `OWNER` en estado `ACTIVE` en el mismo `establishment_id`.

## 11. RELATION TYPE CONTRACT (`relation_type`)

- **Valores Permitidos:** `OWNER_PARTNER`, `STAFF_EMPLOYEE`, `INDEPENDENT_PROVIDER`.
- **Efecto de Seguridad:** `relation_type` **no confiere privilegios RBAC**. Los permisos de acceso derivan exclusivamente de `memberships.role`.
- **Autoridad de Modificación:** Reservada exclusivamente a usuarios con rol `OWNER`.

## 12. ESTABLISHMENT CONTEXT & MULTI-TENANT ISOLATION

- Toda operación sobre invitaciones o miembros de personal requiere autenticación JWT y el header `x-active-membership-id`.
- El middleware `activeContextMiddleware` resuelve `tenant_id` y `establishment_id`.
- El aislamiento de datos se garantiza en base de datos mediante políticas PostgreSQL RLS vinculadas a `app.tenant_id`.

## 13. EXISTING USER ONBOARDING FLOW

```
1. Owner emite invitación para email existente (ej. juan@pro.com).
2. Juan recibe correo con enlace a /saas/invitation/accept?token=XYZ.
3. Juan ingresa a GlowApp, se autentica con su contraseña habitual.
4. UI presenta la pantalla de Confirmación: "Aceptar unión a Salón Chicó como PROFESSIONAL".
5. Juan confirma -> Backend valida token -> Crea membership (status = 'ACTIVE') -> Marca invitación ACCEPTED.
6. Juan ahora dispone de una nueva membresía en su lista de sedes de ActiveContextHolder.
```

---

## 14. NEW USER ONBOARDING FLOW

```
1. Owner emite invitación para email no registrado (ej. nueva@estilista.com).
2. La estilista abre el enlace de invitación.
3. UI detecta que el email no posee cuenta y despliega el Registro de Colaborador.
4. La estilista ingresa su Nombre Completo y define su Contraseña personal.
5. Backend ejecuta en una única transacción atómica:
   a) Crea usuario en usuarios (tenant_id de la invitación, password cifrado bcrypt).
   b) Crea membresía en memberships (status = 'ACTIVE').
   c) Marca invitación como ACCEPTED.
6. La estilista queda autenticada e ingresa directamente al Hub Salón de la sede.
```

## 15. STATUS MUTATION CONTRACT

| Transición de Estado | Actor con Permiso | Efectos Inmediatos en Backend |
| :--- | :--- | :--- |
| **`INVITED` $\to$ `ACTIVE`** | Usuario Invitado (vía token) | `joined_at = NOW()`. Membresía operativa. |
| **`ACTIVE` $\to$ `SUSPENDED`** | Owner (todos) / Manager (operativos) | Bloqueo Active Context (`403`). Availability = 0 slots. Alerta en citas futuras. |
| **`SUSPENDED` $\to$ `ACTIVE`** | Owner (todos) / Manager (operativos) | Reactivación de Active Context y proyección de horarios. |
| **`ACTIVE` $\to$ `REVOKED`** | Exclusivo `OWNER` | `revoked_at = NOW()`. Bloqueo terminal irreversible. |
| **`SUSPENDED` $\to$ `REVOKED`** | Exclusivo `OWNER` | `revoked_at = NOW()`. Bloqueo terminal irreversible. |

## 16. DEACTIVATION POLICY (RETAIN + BLOCK + HUMAN RESOLUTION)

En cumplimiento de `GO-08.35`:
1. **Efecto de Suspensión / Revocación:**
   - Cero slots disponibles proyectados en `NODO-05`.
   - Bloqueo inmediato de sesión de la sede en `ActiveContextService`.
2. **Tratamiento de Citas Futuras:**
   - Las citas `SCHEDULED` o `CONFIRMED` se retienen sin cancelación automática.
   - En la Agenda Operativa (`SCR-10`), se despliega la bandera `STAFF_INACTIVE_ACTION_REQUIRED`.
   - Se bloquea la transición a `IN_SERVICE` hasta que un operador humano reasigne la cita a un profesional activo con asignación de servicio válida.

---

## 17. APPOINTMENT INTEGRITY

- Las citas pasadas (`COMPLETED`, `CANCELLED`, `NO_SHOW`) permanecen inmutables.
- Las citas en curso (`IN_SERVICE`) deben finalizarse o reasignarse antes de que la suspensión administrativa afecte el cierre de la transacción.
- Clave foránea `ON DELETE RESTRICT` impide la pérdida de traza histórica de atenciones.

---

## 18. SERVICE TICKET INTEGRITY (NODO-08)

- **Tickets en `DRAFT`:** El operador puede reasignar el `performed_by_membership_id` antes de confirmar la cuenta.
- **Tickets en `OPEN`, `PAID`, `CLOSED`, `VOID`:** Preservan inmutablemente el `performed_by_membership_id` original para auditoría financiera y cálculo de comisiones.

---

## 19. AVAILABILITY & CATALOG DEPENDENCY

- **Asignaciones (`service_assignments`):** Permanecen asociadas a la membresía. Quedan inactivas operativamente mientras el estado sea distinto de `ACTIVE`.
- **Horarios (`staff_schedules`):** Permanecen guardados. Se excluyen del motor de slots mientras el estado no sea `ACTIVE`.

## 20. BACKEND API CONTRACT (ENDPOINTS DE STAFF PROVISIONING)

Todos los endpoints requieren el header `x-active-membership-id` (salvo los endpoints públicos de invitación).

### Grupo A: Gestión de Invitaciones (`/api/saas/staff/invitations`)
1. **`POST /api/saas/staff/invitations`**
   - **Autoridad:** `OWNER` (cualquier rol), `MANAGER` (solo `PROFESSIONAL` / `RECEPTIONIST`).
   - **Input:** `{ "email": "string", "role": "PROFESSIONAL", "relation_type": "STAFF_EMPLOYEE" }`.
   - **Output:** `{ "invitation": { "id": "uuid", "email": "...", "role": "...", "status": "PENDING", "expires_at": "..." } }`.
   - **Errores:** `400 INVALID_INPUT`, `403 UNAUTHORIZED_ROLE`, `409 INVITATION_ALREADY_PENDING`, `409 USER_ALREADY_MEMBER`.
2. **`GET /api/saas/staff/invitations`**
   - **Autoridad:** `OWNER`, `MANAGER`.
   - **Output:** `{ "invitations": [ ... ] }` (Lista de invitaciones `PENDING` de la sede).
3. **`DELETE /api/saas/staff/invitations/:id`**
   - **Autoridad:** `OWNER` (todas), `MANAGER` (solo operativas).
   - **Output:** `{ "success": true, "revoked_invitation_id": "uuid" }`.
4. **`POST /api/saas/staff/invitations/:id/resend`**
   - **Autoridad:** `OWNER`, `MANAGER`.
   - **Output:** `{ "success": true, "invitation": { ... } }` (Renueva expiración a $+7$ días).

### Grupo B: Flujo Público de Aceptación (`/api/saas/public/invitations`)
5. **`GET /api/saas/public/invitations/:token`**
   - **Autoridad:** Pública (sin auth requerida).
   - **Output:** `{ "valid": true, "establishment_name": "Salón Chicó", "email": "...", "role": "...", "expires_at": "...", "user_exists": true/false }`.
   - **Errores:** `404 INVITATION_NOT_FOUND`, `410 INVITATION_EXPIRED`, `409 INVITATION_ALREADY_PROCESSED`.
6. **`POST /api/saas/public/invitations/:token/accept`**
   - **Autoridad:** Usuario autenticado o datos de registro `{ full_name, password }` para nuevos.
   - **Output:** `{ "success": true, "membership_id": "uuid", "establishment_id": "uuid", "role": "..." }`.

### Grupo C: Gestión de Personal Activo (`/api/saas/staff`)
7. **`GET /api/saas/staff`**
   - **Autoridad:** `OWNER`, `MANAGER`, `PROFESSIONAL`, `RECEPTIONIST`.
   - **Output:** `{ "members": [ { "membership_id": "...", "user_id": 1, "user_name": "...", "user_email": "...", "role": "...", "relation_type": "...", "status": "ACTIVE", "joined_at": "..." } ] }`.
8. **`PATCH /api/saas/staff/:membershipId/role`**
   - **Autoridad:** `OWNER` (cualquier rol), `MANAGER` (solo conmutación `PROFESSIONAL` $\leftrightarrow$ `RECEPTIONIST`).
   - **Input:** `{ "role": "MANAGER" }`.
   - **Errores:** `403 UNAUTHORIZED_ROLE_MUTATION`, `422 CANNOT_ORPHAN_ESTABLISHMENT`.
9. **`PATCH /api/saas/staff/:membershipId/status`**
   - **Autoridad:** `OWNER` (todos), `MANAGER` (solo `PROFESSIONAL`/`RECEPTIONIST` a `SUSPENDED`/`ACTIVE`).
   - **Input:** `{ "status": "SUSPENDED" | "ACTIVE" | "REVOKED", "reason": "string (opcional)" }`.
   - **Errores:** `403 UNAUTHORIZED_STATUS_MUTATION`, `422 CANNOT_ORPHAN_ESTABLISHMENT`, `422 INVALID_STATE_TRANSITION`.
10. **`PATCH /api/saas/staff/:membershipId/relation-type`**
    - **Autoridad:** Exclusivo `OWNER`.
    - **Input:** `{ "relation_type": "INDEPENDENT_PROVIDER" }`.

## 22. SECURITY CONTRACT

1. **Anti-Account Takeover:** Cero contraseñas asignadas por administradores.
2. **Anti-Privilege Escalation:** Validación estricta en base de datos y controladores backend impidiendo que un Manager se asigne rol de Manager/Owner o modifique pares.
3. **Anti-Orphan Guarantee:** Validación atómica impidiendo dejar una sede sin Owners activos.
4. **Token Security:** Tokens de invitación generados con aleatoriedad criptográfica (`crypto.randomBytes(32)`), almacenados como hashes SHA-256 en base de datos.
5. **Aislamiento Multi-Tenant:** Validación estricta de `tenant_id` en todas las consultas y mutaciones mediante RLS.
