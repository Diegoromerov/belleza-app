## 3. AUDITORÍA DE CONFORMIDAD CON ACTIVE CONTEXT

Se auditó que **todos** los 10 endpoints del enrutador están protegidos por:
```javascript
router.get('/search', authMiddleware, activeContextMiddleware, saasCustomersController.searchCustomers);
```
- **Autoridad Exclusiva:** `x-active-membership-id` es el único canal de autorización contextual.
- **Resolución Server-Side:** `req.activeContext` deriva inquebrantablemente `tenant_id`, `establishment_id`, `active_membership_id` y `role`.
- **Rechazo de Parámetros Externos:** Ningún endpoint acepta `tenant_id`, `establishment_id` o `membership_id` provenientes de query params, headers externos (`x-tenant-id`) o body payloads como autoridad de contexto.
- **Resultado:** ✅ **PASS**.

## 4. AUDITORÍA DE AISLAMIENTO MULTI-TENANT Y RLS

- **Anti-IDOR:** Todas las consultas SQL en `saasCustomersService.js` incluyen cláusulas compuestas parametrizadas `WHERE id = $id AND tenant_id = $tenantId`.
- **Sesión RLS en Transacciones:** Toda transacción mutativa invoca explícitamente `SELECT set_config('app.tenant_id', $1, true)` asegurando que las políticas RLS a nivel de motor de base de datos (`tenant_isolation_saas_customers`) refuercen el aislamiento.
- **Prueba Cruzada:** Test T12 verificó que intentar acceder a un cliente de Tenant 1 con Active Context en Tenant 2 retorna `404 CUSTOMER_NOT_FOUND` sin filtrar metadatos.
- **Resultado:** ✅ **PASS**.

---

## 5. AUDITORÍA DE AISLAMIENTO OPERACIONAL POR ESTABLECIMIENTO

- **Directorio de Sede (`scope=establishment`):** Por defecto, la consulta realiza `JOIN saas_customer_establishments ce` filtrando estrictamente `ce.establishment_id = activeContext.establishment_id`.
- **Directorio Corporativo (`scope=tenant`):** Restringido exclusivamente a roles administrativos (`OWNER`, `MANAGER`). Si un `RECEPTIONIST` o `PROFESSIONAL` solicita `scope=tenant`, el servicio responde `403 Forbidden` (`FORBIDDEN_TENANT_SCOPE`) (Verificado en T10).
- **Afiliación de Sede:** `POST /customers/:id/establishments` asocia el cliente exclusivamente al `establishment_id` del Active Context, ignorando cualquier identificador foráneo.
- **Resultado:** ✅ **PASS**.

## 7. AUDITORÍA DE GESTIÓN DE DUPLICADOS (HUMAN DECISION)

Se auditó rigurosamente el cumplimiento del principio dogmático **Contact match ≠ identity match**:
- **Alerta No Bloqueante:** Si se detecta teléfono o email existente en el tenant y `confirm_duplicate !== true`, el backend responde HTTP `409 Conflict` con código `POSSIBLE_DUPLICATE_FOUND` y el array de candidatos (Test T04).
- **Decisión Humana:** Si el operador envía `confirm_duplicate: true`, el backend **crea un nuevo registro canónico independiente** `saas_customers` (Test T05).
- **Cero Matching Silencioso:** NO existe auto-merge, NO existe inferencia de identidad, NO existe linking automático a cuentas de usuario ni a establecimientos.
- **Resultado:** ✅ **PASS**.

## 8. AUDITORÍA DE ATRIBUCIÓN HISTÓRICA (NODO-06 & NODO-08)

Se auditó el comportamiento del endpoint `GET /api/saas/customers/:id/history`:
1. **Cliente con `user_id` Vinculado:** Deriva exactamente citas de NODO-06 (`saas_appointments`) y tickets de NODO-08 (`saas_service_tickets`) donde `customer_user_id = customer.user_id`. Retorna `attribution_status: 'ATTRIBUTED_VIA_USER_ACCOUNT'`.
2. **Cliente sin `user_id` (`user_id IS NULL`):** Retorna `attribution_status: 'UNLINKED_NO_ATTRIBUTED_HISTORY'`, `appointments: []`, `tickets: []` y `total_spend: '0.00'`.
3. **Cero Atribución GUEST:** Quedó constatado que el código **NO utiliza** `guest_phone`, `guest_email` ni `guest_name` para vincular historial previo. Los registros GUEST permanecen 100% aislados e independientes.
4. **Naturaleza Read-Only:** El endpoint no realiza mutaciones en base de datos.
5. **Resultado:** ✅ **PASS**.
