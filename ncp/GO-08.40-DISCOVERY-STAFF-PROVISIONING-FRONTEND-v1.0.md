## 3. Current Frontend Architecture

The Flutter frontend is structured around an Active Context cockpit:
- **`ActiveContextHolder`:** In-memory singleton storing `activeMembershipId`.
- **`ApiService`:** Injects `Authorization: Bearer <jwt>` and `x-active-membership-id: <uuid>` automatically on all API calls matching `/api/saas/*`.
- **`SaasNavigationOrchestrator`:** Routes between satellite screens and handles demand refreshes.
- **State Segregation:** Screens enforce guard conditions:
  - `active_context_missing`: Displayed when `hasActiveContext == false`.
  - `loading`: Full or skeleton progress indicators.
  - `loaded`: Main UI rendering real data.
  - `error`: Structured retry views with descriptive messages.

## 5. Functional Scope

The frontend implementation will deliver:
1. **Establishment Staff Directory (`SCR-14 / StaffDirectoryScreen`):**
   - Active & Inactive team list with role, relation type, status, and join date.
   - Pending Invitations management tab with resend and revoke triggers.
2. **Staff Invitation Emission Modal (`StaffInviteModal`):**
   - Form capturing `email`, `role`, and `relation_type` with instant RBAC input restriction.
3. **Membership Governance Modals:**
   - Role Modification Dialog (`StaffRoleDialog`).
   - Status Transition Modal (`StaffStatusDialog`: Suspend, Reactivate, Revoke).
   - Relation Type Dialog (`StaffRelationTypeDialog`).
4. **Public Invitation Acceptance Flow (`SCR-15 / InvitationAcceptanceScreen`):**
   - Token inspection state display (Establishment Name, Invited Role, Expiration).
   - Existing Authenticated User acceptance confirmation.
   - New User registration form (Name, Password definition) executing atomic account + membership activation.

## 7. Invitation UX (`SCR-14-M1`)

### 7.1 Emission Workflow
1. User clicks `+ Invitar Colaborador`.
2. Form fields:
   - **Email:** Text input with email format validation.
   - **Rol Contextual:** Dropdown (`PROFESSIONAL`, `RECEPTIONIST`, `MANAGER`, `OWNER`).
     - *RBAC Constraint:* If actor is `MANAGER`, only `PROFESSIONAL` and `RECEPTIONIST` are available in dropdown.
   - **Tipo de Relación:** Dropdown (`STAFF_EMPLOYEE`, `INDEPENDENT_PROVIDER`, `OWNER_PARTNER`).
     - *RBAC Constraint:* Only editable by `OWNER`; defaults to `STAFF_EMPLOYEE` for `MANAGER`.
3. Submit action: Calls `POST /api/saas/staff/invitations`.
4. On success: Shows confirmation snackbar with expiration date (+7 days) and auto-switches to the *Invitaciones Pendientes* tab.

### 7.2 Pending Invitations List
- Displays card per invitation: Destinatario (email), Rol asignado, Tipo de relación, Fecha de expiración, Emitido por.
- Actions:
   - **Reenviar (Resend):** Calls `POST /api/saas/staff/invitations/:id/resend`. Renews token and updates expiration.
   - **Cancelar (Revoke):** Calls `DELETE /api/saas/staff/invitations/:id`.

## 9. Membership Management UX

### 9.1 Role Mutation (`StaffRoleDialog`)
- Shows current role and dropdown of new roles.
- If target is the actor: Role change is disabled with tooltip *"No puedes modificar tu propio rol"*.
- If actor is `MANAGER`: Target must be `PROFESSIONAL` or `RECEPTIONIST`, and options are limited to `PROFESSIONAL` or `RECEPTIONIST`.

### 9.2 Status Mutation (`StaffStatusDialog`)
- **Suspensión (`ACTIVE` $\rightarrow$ `SUSPENDED`):** Explains that the member's login access will be blocked and they will project 0 slots in availability, while past tickets and appointments are retained.
- **Reactivación (`SUSPENDED` $\rightarrow$ `ACTIVE`):** Restores login and scheduling.
- **Revocación Definitiva (`ACTIVE`/`SUSPENDED` $\rightarrow$ `REVOKED`):** Requires typing `"CONFIRMAR"` to execute irreversible termination.

## 12. Identity Boundaries

The UI enforces strict conceptual separation:
- **`MEMBERSHIP` (Staff Context):** Represents the relationship of a person to the salon. Staff screens operate strictly on memberships and do not touch the Customer directory (`saas_customers`).
- **`USER / ACCOUNT` (Global Identity):** Credentials belong strictly to the person. Salon owners cannot set or view staff passwords.
- **`CUSTOMER` (Client Domain):** Completely isolated from Staff Provisioning. No customer fields (`customer_id`, `customer_user_id`) appear in staff workflows.

---

## 13. Active Context Integration

- All requests to `/api/saas/staff/*` rely on `ActiveContextHolder().activeMembershipId`.
- If `hasActiveContext == false`, `StaffDirectoryScreen` immediately renders the `_buildActiveContextMissingView()` with a button to open `AvailableContextSelectorScreen` (`SCR-04`).
- No client-supplied `tenant_id` or `establishment_id` parameters are passed in query or body parameters. Context authority is 100% server-resolved.

## 15. Operational Implications for Appointments, Tickets & Availability

When a staff member is transitioned to `SUSPENDED` or `REVOKED`:
1. **Appointments (`NODO-06`):** The UI must never suggest that past or future appointments were deleted or cancelled. Future appointments remain assigned to the staff member and display the operational warning badge `STAFF_INACTIVE_ACTION_REQUIRED` in `AgendaOperativaScreen` (`SCR-10`).
2. **Checkout & Tickets (`NODO-08`):** Past tickets in `OPEN`, `PAID`, `CLOSED`, or `VOID` retain the original `performed_by_membership_id`. `DRAFT` tickets can be reassigned by a cashier/manager before confirmation.
3. **Availability (`NODO-05`):** Inactive staff members automatically project 0 slots in the booking calendar.
