## 1. Executive Summary

This document certifies the complete, production-grade backend implementation of **Staff Provisioning v1.0** for the GlowApp SaaS platform under directive **GO-08.37**.

Staff Provisioning v1.0 operationalizes the incorporation, role hierarchy governance, and lifecycle management of personnel across multi-tenant beauty establishments without compromising identity boundaries, transactional integrity, or operational scheduling.

All implementations strictly adhere to the contract established in `GO-08.36` and the ratified architectural decisions:
1. **GO-08.33:** Asynchronous Invitation & Token Acceptance Model (Zero silent/direct user creation; uncompromised persona separation).
2. **GO-08.34:** Role Hierarchy & Mutability Authority Matrix (`OWNER` > `MANAGER` > `PROFESSIONAL` / `RECEPTIONIST`).
3. **GO-08.35:** Deactivation Policy & Integrity Preservation (`RETAIN + BLOCK EXECUTION + HUMAN RESOLUTION`).

## 2. DDL & Database Changes (`074_saas_staff_invitations.sql`)

Migration `074_saas_staff_invitations.sql` was created and physically applied to the PostgreSQL database.

### 2.1 Table Schema (`staff_invitations`)
```sql
CREATE TABLE IF NOT EXISTS staff_invitations (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id INTEGER NOT NULL,
    establishment_id UUID NOT NULL,
    email VARCHAR(255) NOT NULL,
    role VARCHAR(50) NOT NULL CHECK (role IN ('OWNER', 'MANAGER', 'PROFESSIONAL', 'RECEPTIONIST')),
    relation_type VARCHAR(50) NOT NULL DEFAULT 'STAFF_EMPLOYEE' CHECK (relation_type IN ('OWNER_PARTNER', 'STAFF_EMPLOYEE', 'INDEPENDENT_PROVIDER')),
    invited_by_membership_id UUID NOT NULL,
    token_hash VARCHAR(64) NOT NULL,
    status VARCHAR(50) NOT NULL DEFAULT 'PENDING' CHECK (status IN ('PENDING', 'ACCEPTED', 'REVOKED', 'EXPIRED')),
    expires_at TIMESTAMPTZ NOT NULL,
    accepted_at TIMESTAMPTZ,
    accepted_user_id INTEGER,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_staff_inv_tenant FOREIGN KEY (tenant_id) REFERENCES tenants(id) ON DELETE RESTRICT,
    CONSTRAINT fk_staff_inv_establishment FOREIGN KEY (establishment_id) REFERENCES establishments(id) ON DELETE RESTRICT,
    CONSTRAINT fk_staff_inv_invited_by FOREIGN KEY (invited_by_membership_id) REFERENCES memberships(id) ON DELETE RESTRICT,
    CONSTRAINT fk_staff_inv_accepted_user FOREIGN KEY (accepted_user_id) REFERENCES usuarios(id) ON DELETE SET NULL
);
```

## 3. Identity & Person Separation Verification

The implementation strictly maintains the core architectural boundary:
$$\text{PERSON} \neq \text{ACCOUNT} \neq \text{IDENTITY} \neq \text{MEMBERSHIP} \neq \text{CUSTOMER}$$

- **Zero Auto-Creation on Invitation:** Creating a staff invitation generates a cryptographic invitation record and raw token. No records in `usuarios`, `memberships`, or `perfiles_prestador` are inserted at invitation time.
- **Independent Acceptance:**
  - **Existing Authenticated User:** Resolves the existing `user_id` from session/JWT and binds it to a new `memberships` record for the specified `establishment_id`.
  - **New User Registration:** Creates a single authenticated account in `usuarios` with role `PRESTADOR`, and creates an active `memberships` record for the target establishment.
- **Multi-Establishment Membership:** A single `user_id` can hold distinct memberships across multiple establishments and tenants without data cross-contamination.

## 4. Invitation Lifecycle & Cryptographic Security

### 4.1 Cryptographic Token Pipeline
1. **Generation:** `crypto.randomBytes(32).toString('hex')` produces a 256-bit entropy raw token (64 hex characters).
2. **Storage:** Only the SHA-256 digest (`token_hash`) is stored in the database.
3. **Transmission:** Plaintext token is only returned to the creating actor at generation/resend time.
4. **Expiration:** Default expiration window is strictly 7 days (`NOW() + INTERVAL '7 days'`).

### 4.2 State Machine
```
  [PENDING] ────(Accept with valid token)──────> [ACCEPTED] (Terminal)
     │
     ├────────(Revoke by Owner/Manager)──────> [REVOKED] (Terminal)
     │
     └────────(Expires after 7 days)─────────> [EXPIRED] (Terminal)
```

## 5. RBAC & Authority Matrix Implementation

| Actor Role | Can Invite | Can Mutate Role Of | Allowed Roles to Assign | Can Deactivate / Suspend | Relation Type Authority |
|---|---|---|---|---|---|
| **OWNER** | Any role (`OWNER`, `MANAGER`, `PROFESSIONAL`, `RECEPTIONIST`) | `MANAGER`, `PROFESSIONAL`, `RECEPTIONIST`, `OWNER` (if >1) | Any role | `MANAGER`, `PROFESSIONAL`, `RECEPTIONIST`, `OWNER` (if >1) | Exclusive Full Authority |
| **MANAGER** | `PROFESSIONAL`, `RECEPTIONIST` | `PROFESSIONAL` $\leftrightarrow$ `RECEPTIONIST` | `PROFESSIONAL`, `RECEPTIONIST` | `PROFESSIONAL`, `RECEPTIONIST` | None (403 Forbidden) |
| **PROFESSIONAL** | None (403) | None (403) | None (403) | None (403) | None (403) |
| **RECEPTIONIST** | None (403) | None (403) | None (403) | None (403) | None (403) |

## 6. Membership Lifecycle & State Machine

```
  [INVITED] ────(Accept Invitation)────> [ACTIVE]
                                            │   ▲
                               (Suspend)   │   │  (Reactivate)
                                            ▼   │
                                         [SUSPENDED]
                                            │
                                (Revoke)    ▼
                                         [REVOKED] (Terminal)
```

- `REVOKED` is strictly terminal: Any attempt to transition `REVOKED` $\rightarrow$ `ACTIVE` or `SUSPENDED` is rejected with HTTP 422 `INVALID_STATE_TRANSITION`.

---

## 7. Anti-Orphan & Self-Mutation Safeguards

1. **Anti-Self Role Mutation:** A staff member cannot mutate their own role (HTTP 403 `SELF_ROLE_MUTATION_PROHIBITED`).
2. **Anti-Orphan Establishment Invariant:**
   - Demoting or deactivating (`SUSPENDED`, `REVOKED`) an `OWNER` is blocked if:
     $$\text{COUNT}(*) \text{ WHERE role='OWNER' AND status='ACTIVE'} \le 1$$
   - Throws HTTP 422 `CANNOT_ORPHAN_ESTABLISHMENT`.

---

## 8. Data Integrity & Retain Policy

In accordance with **GO-08.35**:
- Suspending or revoking a membership **NEVER** executes cascading deletes.
- Historical data (`appointments`, `service_tickets`, `service_assignments`, `staff_schedules`) is permanently retained for legal, financial, and auditing integrity.
- Execution of new operational actions by suspended/revoked staff is blocked at runtime by active context validation and status guards.

---

## 9. Multi-Tenant & Multi-Establishment Isolation

- All queries set and enforce PostgreSQL `app.tenant_id`.
- Establishment boundaries are verified in SQL queries (`WHERE establishment_id = $1 AND tenant_id = $2`).
- Cross-tenant or cross-establishment manipulation attempts return HTTP 404 or 403.

## 10. API Specification & Endpoints Implemented

### 10.1 Protected Management Endpoints (`/api/saas/staff`)
- `POST /api/saas/staff/invitations` — Create new staff invitation (201 Created).
- `GET /api/saas/staff/invitations` — List pending invitations (200 OK).
- `DELETE /api/saas/staff/invitations/:id` — Revoke pending invitation (200 OK).
- `POST /api/saas/staff/invitations/:id/resend` — Resend invitation (200 OK).
- `GET /api/saas/staff` — List all establishment staff (200 OK).
- `PATCH /api/saas/staff/:id/role` — Update staff role (200 OK).
- `PATCH /api/saas/staff/:id/status` — Update staff status (200 OK).
- `PATCH /api/saas/staff/:id/relation-type` — Update staff relation type (200 OK).

### 10.2 Public / Invitation Endpoints (`/api/saas/public/invitations`)
- `GET /api/saas/public/invitations/:token` — Public invitation inspection (200 OK).
- `POST /api/saas/public/invitations/:token/accept` — Accept invitation and join establishment (200 OK).
