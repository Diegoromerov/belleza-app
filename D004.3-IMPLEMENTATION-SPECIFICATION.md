# D004.3-IMPLEMENTATION-SPECIFICATION.md

## Executive Summary

This document specifies the technical implementation for D-004 (Estrategia de retención de datos para RAG y conocimiento organizacional) in the GlowApp system. It details the evolution of the RAG system from a global-only model to a hybrid GLOBAL + TENANT-SCOPED model with comprehensive retention mechanisms, while maintaining compatibility with the existing D-001 multi-tenancy foundation.

**Key Specifications:**
- **beauty_knowledge_embeddings table:** Evolved to include `tenant_id` (nullable), `deleted_at` (soft delete), and `expires_at` (expiration timestamp)
- **GLOBAL knowledge:** Represented by `tenant_id IS NULL`
- **TENANT-SCOPED knowledge:** Represented by `tenant_id = <specific_tenant_id>`
- **RLS Policy:** Conceptual design enabling `tenant_id IS NULL OR tenant_id = current_tenant()` for SELECT, with appropriate INSERT/UPDATE/DELETE controls
- **ragService.js:** Modified to include tenant context in queries, respect soft delete (`deleted_at IS NULL`), and filter by expiration
- **Auxiliary Tables:** 
  - `retention_policies`: Defines retention rules by knowledge category/scope
  - `legal_holds`: Overrides retention for preservation requirements
  - `retention_audit_log`: Tracks all knowledge lifecycle events
- **Cron Job:** Periodic process to apply retention policies, execute soft deletes, and purge expired data
- **Data Safety:** Guarantees against accidental data loss, cross-tenant leakage, and unauthorized modifications
- **Compatibility:** Fully compatible with D-001 (Shared Schema + tenant_id + RLS) and does not affect D-002 workforce functionality

This specification is ready for implementation pending Director authorization and legal review of retention periods.

## 2. Target Architecture

```text
RAG Knowledge Storage
│
├── Global Knowledge (tenant_id IS NULL)
│   ├── Available to all tenants
│   └── Subject to retention policies
│
└── Tenant-Scoped Knowledge (tenant_id = <specific_id>)
    ├── Available only to specific tenant + global knowledge
    └── Subject to tenant-specific retention policies
```

Supporting Systems:
- Retention Policy Engine (defines rules per category/scope)
- Legal Hold Override (temporarily suspends retention)
- Audit Trail (complete lifecycle tracking)
- Periodic Retention Job (applies policies and enforces deletion)

## 4. GLOBAL/TENANT Model

**Definition:**
- **GLOBAL:** `tenant_id IS NULL`
- **TENANT-SCOPED:** `tenant_id = <valid_tenant_id_from_tenants_table>`

**Rationale:**
- Simple, intuitive, and leverages existing D-001 tenant_id foundation
- No additional scope field needed; NULL vs NOT NULL provides clear dichotomy
- Compatible with standard SQL and RLS implementations
- Allows knowledge to be truly global (accessible by all tenants) or strictly isolated

## 5. RLS Design

**Conceptual Policy for beauty_knowledge_embeddings:**
```sql
-- Permits viewing of:
--   1. All global knowledge (tenant_id IS NULL)
--   2. Tenant-scoped knowledge matching current tenant
CREATE POLICY rag_knowledge_access ON beauty_knowledge_embeddings
FOR SELECT
USING (
    tenant_id IS NULL 
    OR tenant_id = current_setting('app.tenant_id')::int
);

-- For INSERT/UPDATE/DELETE, tenants can only modify their own scoped knowledge
-- Global knowledge modifications require special authorization (not covered by RLS alone)
CREATE POLICY rag_knowledge_modify ON beauty_knowledge_embeddings
FOR ALL
USING (
    tenant_id = current_setting('app.tenant_id')::int
)
WITH CHECK (
    tenant_id = current_setting(('app.tenant_id')::int
);
```

**Behavior:**
- **SELECT:** Returns global knowledge + current tenant's scoped knowledge
- **INSERT:** Requires explicit tenant_id (can be NULL for global, but note: global inserts may need separate authorization)
- **UPDATE:** Only allowed on rows matching current tenant's tenant_id
- **DELETE:** Same as UPDATE (soft delete handled via UPDATE on deleted_at)
- **Note:** True global knowledge modifications (INSERT/UPDATE/DELETE with tenant_id=NULL) would require bypassing RLS via elevated privileges or application-level controls, consistent with D-001's treatment of RAG as globally managed.

## 6. RAG Service Changes

**Required Modifications to ragService.js:**

### 6.1 Query Modifications
- Add `tenant_id IS NULL OR tenant_id = $tenantParam` to all SELECT queries
- Add `AND deleted_at IS NULL` to exclude soft-deleted records
- Add `AND (expires_at IS NULL OR expires_at > NOW())` to exclude expired records
- Parameterize tenant context (passed from auth middleware)

### 6.1 Insertion Logic
- Determine knowledge scope at ingestion time:
  - If knowledge is designated as global → set `tenant_id = NULL`
  - If knowledge is tenant-specific → set `tenant_id = <ingesting_tenant_id>`
- Ingestion source (API, seed script, etc.) must provide scope designation

### 6.2 Update Logic
- Preserve existing `tenant_id` during updates (do not allow changing scope via update)
- Update `updated_at` timestamp on modification

### 6.3 Deletion Logic (Soft Delete)
- Implement soft delete by setting `deleted_at = NOW()` instead of physical removal
- Prevents immediate data loss while allowing retention policy enforcement

### 6.4 Retrieval Filtering
- All retrieval queries automatically exclude:
  - Records where `deleted_at IS NOT NULL`
  - Records where `expires_at IS NOT NULL AND expires_at <= NOW()`

### 6.5 Metadata Handling
- Continue to use `metadata` field for existing filters (skin_type, category, etc.)
- No changes required to metadata processing logic

## 7. Retention Architecture

### 7.1 Retention Policy Engine
- Policies evaluated by periodic cron job
- For each knowledge record:
  1. Find matching retention policies (by category, scope, tenant_id)
  2. Calculate expiration date: `created_at + period.unit`
  3. If `expires_at` is NULL or calculated expiration > stored `expires_at`, update `expires_at`
  4. If current time >= `expires_at` and no active legal hold → initiate soft delete

### 7.2 Legal Hold Override
- Legal hold takes precedence over retention policy
- While a legal hold is active (`status = 'ACTIVE'`), knowledge is exempt from expiration and deletion
- Legal hold can be applied to specific knowledge records or broad categories
- Release of legal hold allows normal retention processing to resume

### 7.3 Audit Trail
- All knowledge lifecycle events logged to `retention_audit_log`:
  - Creation (initial insert)
  - Updates (content/metadata changes)
  - Soft delete (deleted_at set)
  - Expiration reached (trigger for soft delete)
  - Physical purge (record deletion)
  - Legal hold applied/released
- Audit records include actor, tenant, timestamp, and action details

## 8. Cron Architecture

**Periodic Retention Job (`retention_worker.js` concept):**

### 8.1 Responsibilities
1. Scan for knowledge records nearing expiration or past expiration
2. Exclude records with active legal holds
3. Apply retention policies to calculate/update expiration timestamps
4. Execute soft delete on expired records (set `deleted_at`)
5. Identify soft-deleted records past retention period for physical purge
6. Perform physical deletion (DELETE) on records eligible for purge
7. Log all actions to retention_audit_log
8. Emit operational metrics (records processed, deleted, purged)

### 8.2 Configuration
- **Frequency:** Recommended daily at low-traffic hours (configurable via cron expression)
- **Batch Size:** Process records in batches of 1000 to avoid long transactions
- **Timeout:** 30 minutes per batch run
- **Retries:** Exponential backoff for transient failures (max 3 attempts)
- **Concurrency:** Single instance recommended (use distributed lock if scaling)
- **Error Handling:** Log errors, continue processing, alert on persistent failures

### 8.3 Idempotency
- Designed to be safely re-runnable:
  - Already processed records skipped based on expiration state
  - Audit log prevents duplicate action recording
  - Physical purge only affects records marked for deletion beyond grace period

## 10. Index Strategy

**Required Indexes for Performance:**
1. `idx_beauty_knowledge_category` (category) - Speeds up category-based filtering
2. `idx_beauty_knowledge_tenant` (tenant_id) - Critical for tenant-scoped queries and RLS
3. `idx_beauty_knowledge_deleted` (deleted_at) - Efficient soft delete filtering
4. `idx_beauty_knowledge_expires` (expires_at) - Efficient expiration scanning
5. **Composite Index:** `(tenant_id, deleted_at, expires_at)` - Optimizes retention worker scans
6. Maintain existing vector similarity search index (pgvector's native indexing)

**Justification:** Each index supports a specific access pattern in the target architecture without over-indexing.

## 11. Vector Search Strategy

**Verification:** Introduction of `tenant_id`, `deleted_at`, `expires_at` does not break vector search strategy because:
- Vector search (`<=>` operator) operates on the `embedding` column exclusively
- Additional filters are applied in WHERE clause (tenant scope, soft delete, expiration)
- No change to the vector distance calculation or indexing approach
- Performance maintained through proper indexing on filtered columns

**No modification to vector search query structure required beyond adding WHERE conditions.**

## 14. Security Model

**Threat Mitigation:**
- **Cross-tenant Retrieval:** Prevented by RLS/query restrictions (tenant_id filtering + global access)
- **Cross-tenant Insertion:** Prevented by application-layer validation (must specify valid tenant_id or NULL)
- **Cross-tenant Update:** Prevented by RLS/update restrictions (tenant_id must match)
- **Cross-tenant Deletion:** Prevented by RLS/delete restrictions + soft delete design
- **RLS Bypass:** Mitigated by least-privilege database connections; administrative connections restricted
- **Worker/Job Security:** Retention worker runs with service account; limited to necessary operations
- **Raw SQL Protection:** Application uses parameterized queries; ORM/sequealize prevents injection
- **app.tenant_id Integrity:** Set by authentication middleware; not editable by end-users
- **Metadata Sanitization:** Existing filtering logic prevents metadata-based cross-tenant leakage
- **GLOBAL Knowledge Protection:** Application-level controls restrict global knowledge modification to authorized roles

## 20. Rollback/Recovery Strategy

**Pre-implementation:**
- Full database backup
- Test migration on staging copy of production schema

**Post-issue:**
- **Migration failure:** Since we're using `CREATE TABLE IF NOT EXISTS` and `ADD COLUMN`, failures are unlikely; if occurs, restore from backup
- **Incorrect data:** Soft delete allows recovery until purge; audit log enables forensic reconstruction
- **Performance issues:** Indexes can be added/dropped without table rebuild (PostgreSQL 11+)
- **Logic errors:** Application is stateless; fix code and redeploy
